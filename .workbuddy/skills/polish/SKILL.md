# Polish

优化已有技术文章。目标是技术表述可靠、结构清楚、语言自然，修改后仍保留作者的观点和表达层级。

## 核心原则

- 先理解全文和章节职责，再修改局部句子；
- 以正确性和完整性为优先，修改范围由实际问题决定。必要时可以重写、补充或重组，不能为了少改而保留错误或缺口；
- 区分事实、观点和教学简化，只把事实、因果、边界或术语问题视为技术错误；
- 易变化的 API、兼容性、性能、安全和最佳实践应查阅当前一手资料，无法确认时标为“疑似”；
- 用户和项目规范优先，用户要求保留的章节、示例、术语、参考资料和格式不得改动。

若修改只是换一种同样成立的说法，没有提升正确性、逻辑或可读性，保留原文。

## 判断任务范围

先按以下优先级判断流程：

1. 用户要求只诊断或只给建议时，只输出诊断，不修改文件；
2. 用户提供完整文件或完整文章文本，且未限定章节、行号或段落时，按整篇优化处理；
3. 用户明确指定章节、行号或段落时，按局部优化处理；
4. 范围会显著影响结果且无法从上下文判断时，先询问一个聚焦问题。

整篇优化必须先审查标题结构。只有标题存在优化空间时才需要用户确认修改方案；即使用户已经要求直接修改，也不能跳过这次确认。标题已经合理时直接优化正文。局部优化不进入标题审查流程。

## 修改前准备

1. 读取项目规范和目标文件；
2. 查看目标文件的 Git 状态，区分暂存区与工作区，避免覆盖用户已有修改；
3. 整篇优化时通读全文，局部优化时读取目标范围及必要上下文；
4. 记录用户要求冻结的内容，必要时保存原文用于逐字比较；
5. 识别文章已有的术语、代码块、图表和叙述层级。

只有系列文章的职责边界确实影响当前修改时，才读取相邻文章。

## 整篇优化

整篇优化使用两个状态。状态一完成前，不得进入状态二。

### 状态一：审查标题结构

本状态只读，不修改文件，也不诊断或优化正文。

标题范围包括 frontmatter 中的文章标题和正文 Markdown 标题。文章标题计为第一层，正文通常只保留第二层和第三层。

标题必须满足：

- 不带数字、序号或编号前缀；
- 不使用反引号包裹术语、代码标识符或 API；
- 不使用中文或英文冒号；
- 最多三层，优先压缩为两层；
- 同级标题处于相同抽象层级，父子标题不重复表达同一含义；
- 直接概括章节职责，不使用口号、噱头或目录预告。

发现优化空间时，只用缩进展示建议优化后的完整标题树，并简要说明调整原因。不要重复输出当前标题结构：

```markdown
## 标题结构建议

- 文章标题；
  - 二级标题；
    - 三级标题。

调整说明：……
```

如果当前结构合理且没有实质优化空间，不输出标题方案，也不请求确认，直接进入状态二。

只有需要调整标题时，才输出建议结构和调整说明。输出标题方案后立即结束当前轮次。在后续消息收到用户明确确认前，不得修改文件，不得继续处理正文。用户提出调整时，更新方案并再次结束当前轮次。

### 状态二：优化全文

标题无需调整时直接处理正文；标题需要调整时，先应用用户确认的方案。技术诊断在内部完成；只有疑似技术问题、作者意图不明确或需要超出已确认结构时才暂停确认。

逐段优化的核心是让每个章节准确、完整地回应其标题。先明确标题承诺回答的问题、覆盖范围和叙述层级，再判断正文是否匹配。

按以下顺序处理：

1. **开头**：先在原文基础上优化，自然、简洁地交代文章要处理的问题、必要背景或切入场景，并顺势引出后文。不要总结全文、复述目录或提前集中给出后续结论；
2. **标题与内容**：逐节检查正文是否回应标题。与标题无关的内容应删除、移动或改写；标题承诺但正文没有解释的内容需要补齐；
3. **正文**：逐段检查技术正确性和逻辑完整性。必要时重写或重组段落，不受最小修改限制；
4. **查漏补缺**：检查定义、前提、输入输出、执行步骤、因果关系、适用边界、异常情况和必要示例是否缺失。只补充理解主题所必需的内容，新增技术事实需要核验；
5. **段落**：每段保留一个完整小观点，删除赘述并合并重复表达。合并语义连续的短段落，只有长段落包含多个独立观点时才拆分；
6. **图表与列表**：把图片、图表、代码块和列表作为叙述的一部分，不要直接插入正文。前文应说明展示目的、覆盖范围或与当前论点的关系，让读者知道为什么需要查看；后文应承接其中的关键信息、差异或下一步推导，让叙述继续向前。不要只用“如下图所示”“具体如下”等空泛语句过渡，也不要在内容已经清楚时强行补写总结。列表仅在并列关系、步骤或对照比自然段更清楚时使用，除最后一项外以中文分号结尾，最后一项以中文句号结尾；
7. **结尾**：仅在能够收束核心判断、取舍或适用边界时保留或重写总结。不要为了形式完整而新增总结。

正文和结尾优化完成后，重新评估开头。若局部调整仍无法准确引出优化后的内容，可以推翻原开头并整体重写。新开头应以最终正文为依据，保持文章主题、作者立场和叙述层级，不得新增原文没有的观点，也不能改写成全文摘要。

按文章顺序逐节处理，修改当前段落时同时检查所属标题、上一段和下一段。遇到图片、图表、代码块或列表时，将其与前后的自然段作为一个连续叙述单元处理。逐段处理不需要逐段向用户确认或汇报。

## 局部优化

局部优化不审查整篇标题结构，也不设置逐条确认或全量修复模式。读取目标范围及必要上下文，完成内部诊断后直接修改。

局部内容仍以正确性和完整性为优先，检查它是否回应所属标题，并在授权范围内纠正错误、调整结构和补齐必要内容。只有疑似技术问题、作者意图不明确或修改会超出指定范围时才暂停确认。

修改后重新阅读目标范围及上下文，确认没有引入逻辑断点、术语不一致或重复内容。范围外的既有问题只说明，不顺手修改。

## 检查维度

### 技术正确性

- 文字、代码、类型、图表和示例保持一致；
- 术语、因果关系、适用前提和版本边界准确；
- 关键定义、前提、步骤、边界和异常情况没有缺失；
- 示例在当前讲解层级内闭合，省略部分明确为示意；
- 按需读取 `references/tech-domains.md` 中与主题相关的部分。

### 结构与逻辑

- 章节职责清楚，概念在使用前已有必要说明；
- 每个章节的内容准确回应标题，范围和叙述层级一致；
- 结论能从前文得出，过渡表达真实的承接、转折或因果；
- 图片、图表、代码块和列表与前后文衔接自然，前文说明展示目的，后文承接关键信息或后续推导；
- 同一细节只在最合适的位置完整说明；
- 图表主链路正确，并与正文和代码对应；
- 不套用固定文章骨架，也不强制添加总结。

### 作者语气与语言

- 删除无信息量的开场、目录预告、万能总结和模板化转折；
- 不凭空加入第一人称经历、情绪、比喻或立场；
- 句子主干、指代、条件和因果清楚，术语前后一致；
- 自然段不过度零散，也不堆叠多个独立观点；
- 根据句法选择“的、地、得”：定语或省略中心语的结构用“的”，动词前的状语用“地”，动词或形容词后的补语用“得”；
- 遇到“动词 + de + 越……”结构时，先判断“越……”修饰的是对象、动作还是状态，再确定结构助词。修饰由前面结构限定的对象或省略的中心语时使用“的”，直接补充动作程度或状态时才使用“得”，在动词前作状语时使用“地”。例如“生成的越快”使用“的”，不能写成“生成得越快”或“生成地越快”；
- 全文统一使用“其它”，不使用“其他”；
- 需要详细判断 AI 味时读取 `references/ai-voice.md`。

## 修改边界

- 不改变核心观点和立场；
- 可以补充保证正确性和完整性所需的事实、定义、前提、步骤与边界，但不得添加无关观点，新增技术内容必须经过核验；
- 不把通用概念改成某个框架或产品的专属解释；
- 不凭空构造反面说法来引出结论；
- 不为了形式感添加表格、流程图、代码或总结；
- 参考文章只用于学习语气、节奏和表达密度，不复制其结构或模板；
- 全文不使用中文或英文破折号，应按语义改用句号、逗号、冒号或括号；
- 不扩展到构建、暂存、提交或其它仓库操作，除非用户明确要求。

## 完成前验证

整篇优化必须从头到尾重新通读全文，并完成三轮 review。

技术 review：

- 技术结论、代码、类型、图表和示例正确且相互一致；
- 每个关键结论都有必要的前提、因果和适用边界；
- 标题范围内没有遗漏关键定义、步骤、异常情况或必要示例；
- 新增内容有可靠依据，没有为了显得完整而扩展主题。

结构 review：

- 标题与用户确认的方案一致；若标题无需调整，则保持审查通过的原结构；
- 每个章节都准确、完整地回应标题，没有内容错位或明显缺口；
- 开头自然引出最终正文，没有写成全文摘要；必要时已根据优化后的内容整体重写；
- 章节和段落之间没有逻辑跳跃；
- 图片、图表、代码块和列表没有打断叙述，前后文不存在空泛、机械的引导语；
- 结尾与全文内容匹配，确有必要时才保留总结。

表达 review：

- 同一概念、角色、阶段和 API 的用词一致；
- 没有跨段、跨节重复结论或冗余赘述；
- 段落密度自然，列表标点符合规则；
- “的、地、得”符合句法和上下文，全文统一使用“其它”；
- 全文没有破折号，替换后的句意自然；
- 原意、作者语气和冻结内容得到保留。

整篇优化完成后运行：

```bash
rtk python3 .agents/skills/polish/scripts/validate_markdown.py <target-file>
rtk git diff --check -- <target-file>
```

校验失败时修正问题并重新运行。校验通过前不得汇报完成。复杂嵌套列表仍需人工检查。局部优化只检查本次改动及其上下文，不为通过全文校验而修改范围外的既有问题。

## 完成反馈

只报告实际发生的改动、验证结果和仍需用户确认的事项，不重复诊断报告或展示完整 diff。
