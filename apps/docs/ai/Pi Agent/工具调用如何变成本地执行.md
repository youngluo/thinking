# 工具调用如何变成本地执行

模型只能在消息中提出工具调用，不能直接读取文件或启动进程。本篇沿着一条工具调用，观察它如何经过描述、参数校验、执行控制，最后变成本地副作用和下一轮模型输入。

下面的实现以 Pi commit `936aff00918de1187f085f123c2812d8f2d67745` 为基准。重点放在 `AgentTool` 和 Agent Loop 的边界，不展开具体工具如何实现文件系统、Shell 或网络访问。

## 工具调用的边界

一次工具调用至少包含三个角色：

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 模型 | 根据上下文选择工具并生成参数 | 不直接执行本地函数 |
| Agent Runtime | 校验参数、执行工具、发出事件并回注结果 | 不替工具决定业务副作用 |
| 工具实现 | 读取文件、执行命令或调用外部服务 | 不决定下一步调用哪个工具 |

因此，工具不是模型能力的延伸函数，而是模型和本地环境之间的受控边界。模型输出的是结构化调用，运行时决定这个调用是否能执行，工具实现才真正接触文件、进程和网络。

## 工具定义与参数

Pi 用 `AgentTool` 描述一个可调用工具。对模型来说，名称、描述和参数 schema 组成工具说明；对运行时来说，`execute` 才是产生副作用的入口。

```ts fold title="read-file-tool.ts"
import { readFile } from "node:fs/promises";
import { Type } from "typebox";

const readFileTool: AgentTool = {
  name: "read_file",
  label: "Read File",
  description: "Read a file's contents",
  parameters: Type.Object({
    path: Type.String({ description: "File path" }),
  }),
  execute: async (_toolCallId, params, _signal, onUpdate) => {
    onUpdate?.({
      content: [{ type: "text", text: "Reading..." }],
      details: {},
    });

    const content = await readFile(params.path, "utf-8");
    return {
      content: [{ type: "text", text: content }],
      details: { path: params.path },
    };
  },
};
```

这里的 `parameters` 不是 TypeScript 类型注解，而是运行时可以检查的 schema。模型生成的参数先经过 schema 校验，再传入 `execute`。`execute` 可以通过 `onUpdate` 报告进度，最终返回给模型的主要是 `content`，`details` 则可以承载供产品界面或运行时使用的结构化信息。

## 执行前检查

工具调用进入执行阶段后，运行时不会直接调用 `execute`，而是先完成参数校验和执行前检查。`beforeToolCall` 发生在 `tool_execution_start` 之后、参数解析完成之后，可以用于权限确认、路径限制或策略拦截。

```d2 fold
direction: right

call: "assistant tool call"
start: tool_execution_start
validate: "参数校验"
preflight: beforeToolCall
decision: "允许执行？" {
  class: decision
}
execute: AgentTool.execute()
blocked: "blocked tool result"
end: tool_execution_end
result: "toolResult message"

call -> start -> validate -> preflight -> decision
decision -> execute: 是
decision -> blocked: 否
execute -> end
blocked -> end
end -> result
```

拦截结果仍然会回到事件流和上下文，模型可以知道工具为什么没有执行。这样，权限策略不会被隐藏成界面层的异常，而是成为 Agent Loop 能够处理的一部分。

## 并发与结果顺序

同一条 assistant 消息可能包含多个工具调用。Pi 默认允许并行执行，但把「执行顺序」和「结果顺序」分开处理：

| 阶段 | 顺序 |
| --- | --- |
| 参数解析与执行前检查 | 按工具调用顺序进行 |
| 工具实际执行 | 默认可以并行 |
| `tool_execution_end` 事件 | 按工具实际完成顺序发出 |
| `toolResult` 消息 | 按 assistant 消息中的调用顺序回注 |

这样既能缩短互不依赖的工具调用耗时，又不会让下一轮模型看到顺序漂移的工具结果。如果某个工具声明使用 `sequential` 执行模式，整批工具调用会退回串行执行；具体的模式可以由 Agent 全局配置或单个工具覆盖。

## 结果回注与副作用

工具完成后，运行时会先发出工具结束事件，再把结果包装成 `toolResult` 消息。下一轮模型调用看到的是这条消息，而不是工具函数的返回对象本身：

1. 工具实现产生本地副作用，并返回 `content` 和可选的 `details`；
2. Agent Runtime 将成功结果或错误转换为标准 `toolResult`；
3. 工具结果进入消息上下文，模型据此决定继续调用工具、修改方案或结束任务。

工具失败时应抛出错误，而不是把错误伪装成普通文本。运行时会捕获异常，并将其作为带 `isError` 标记的工具结果交给模型。工具或 Hook 也可以返回 `terminate: true`，提示当前工具批次完成后不要自动发起下一次模型调用；只有批次中的所有结果都要求终止时，这个提示才会生效。

工具执行完成并不等于代码已经安全。文件权限、命令沙箱、网络访问和凭证隔离都属于产品或部署环境的责任，Agent Runtime 只提供调用边界和执行钩子。

在 `coding-agent` 产品层，`agent-session.ts` 会把 Runtime 的低层工具事件和 Hook 结果映射为扩展系统可以订阅的 `tool_call` 与 `tool_result` 事件。这样，扩展可以观察或影响产品层的工具生命周期，而 Agent Core 仍然只负责执行边界。两层事件不能混同：前者是产品扩展契约，后者是 Runtime 的执行事件。

## 小结

工具调用的完整链路是「模型提出调用，运行时校验和调度，工具产生副作用，结果回到消息上下文」。其中参数 schema 负责输入形状，Hook 负责执行前后的策略，执行模式负责并发和保序，`toolResult` 则把本地执行重新接回 Agent Loop。
