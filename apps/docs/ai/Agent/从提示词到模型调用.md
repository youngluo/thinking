# 从提示词到模型调用

在 Claude Code 中输入「把登录接口的报错修一下」后，这句话不会单独发送给模型。Claude Code 会把系统指令、工具定义、项目指令和对话历史一起组织成请求，再发起模型调用。

如果模型决定调用工具，Claude Code 会执行工具并把结果写回上下文，继续下一轮调用。本文从这条提示词出发，说明模型每一轮实际收到什么，以及工具结果如何进入下一轮。

## 链路总览

Claude Code 是模型外部的运行时，也就是 Harness。它收集当前任务需要的上下文，构造模型请求，并在模型返回工具调用后负责权限检查和实际执行。整条链路如下。

```d2
direction: right

I: 用户输入\n“把登录接口的报错修一下”
C: 收集上下文\n项目指令、记忆、技能、历史
R: 构造请求\nsystem + tools + messages
M: 模型响应\ntext 或 tool_use

I -> C -> R -> M

T: Harness 执行工具\n权限检查 + 实际运行
B: 回注 tool_result\n写入 messages

M -> T: tool_use
T -> B -> R: 下一轮
```

模型不会在两次 API 请求之间自动保留状态。Claude Code 每轮都会重新发送当前所需的上下文，提示词缓存只负责复用未变化的请求前缀，不会替代上下文本身。

## 收集上下文片段

### 用户输入与运行环境

用户输入会作为本轮任务进入对话。显式引用的文件、粘贴的内容和附带的图片也可以成为本轮上下文，但「用户在终端里能看到」不等于「模型已经看到」。文件内容、命令输出和 Git 状态只有经过 Claude Code 注入，或由模型调用工具读取后，才会进入模型上下文。

工作目录、权限模式和可用工具集合属于 Harness 的运行状态。它们不一定以同一种形式发送给模型。有些内容会影响 system prompt 或工具定义，有些只在执行工具时生效。判断模型知道什么，应以实际写入请求的内容为准。

### 项目记忆

Claude Code 使用 `CLAUDE.md` 保存由开发者维护的长期指令，例如项目约定、常用命令和架构边界。根据[官方加载规则](https://code.claude.com/docs/en/memory)，当前工作目录及其父目录中的 `CLAUDE.md` 和 `CLAUDE.local.md` 会在启动时加载，子目录中的文件则在 Claude 读取该目录下的文件时按需加载。

例如，项目可以在 `CLAUDE.md` 中记录这些约定。

```text
# 项目约定
- 所有 shell 命令必须加 rtk 前缀。
- 修改文档后不要自动执行 docs:build。
- 提交必须使用 commit skill，遵循 Conventional Commits。
```

Claude Code 还可以维护自动记忆。启动时只加载记忆入口，详细内容需要时再读取。两类内容的职责不同，`CLAUDE.md` 由开发者明确维护，自动记忆则保存工具在工作过程中提炼的信息。

`CLAUDE.md` 不属于 system prompt。Claude Code 官方文档明确说明，它作为项目上下文以 `user` 消息的形式放在 system prompt 之后。它能引导模型，但不能替代权限检查、输入校验或其它确定性约束。

### 技能加载

技能也是上下文来源，但加载方式与 `CLAUDE.md` 不同。每个技能以 `SKILL.md` 为入口，frontmatter 描述用途，正文提供完整指令。[Claude Code 的技能加载](https://code.claude.com/docs/en/skills)分为两层。

| 部分           | 加载时机             | 作用                             |
| -------------- | -------------------- | -------------------------------- |
| 技能名称与描述 | 会话启动时           | 让模型发现可以自动调用的技能     |
| SKILL.md 正文  | 用户或模型调用技能时 | 提供本次任务需要的完整指令       |

默认允许模型调用的技能会在启动时暴露名称和描述；禁止模型自动调用的技能只能由用户显式触发，描述不会提前进入上下文。技能被调用后，渲染后的正文会作为消息进入当前会话，并在后续轮次继续占用上下文。任务专用的长指令适合放在技能中，跨任务始终有效的短规则更适合放在 `CLAUDE.md`。

## 构造模型请求

每次发送消息，Claude Code 都会构造新的 API 请求，重新带上模型完成当前任务所需的上下文。[提示词缓存](https://code.claude.com/docs/en/prompt-caching)通过匹配请求前缀减少重复处理的成本和延迟，但模型看到的上下文仍然需要完整表达。

### system prompt

system prompt 由 Claude Code 提供，主要承载产品级的核心行为、运行规则和输出方式。用户通过配置追加的 system prompt 或输出样式也可能进入这一层。

这里需要区分 system prompt 和项目指令。`CLAUDE.md`、自动记忆以及无条件加载的项目规则属于 system prompt 之后的项目上下文，不能因为它们也在指导模型，就统称为 system prompt。

### 工具定义

Claude Code 通过 API 的 `tools` 字段向模型提供工具。每个工具至少包含名称、用途说明和 `input_schema`。名称与说明帮助模型判断何时调用，schema 约束参数结构。

schema 只能约束输入形状，不能证明参数符合业务规则，也不会授予执行权限。路径是否允许访问、命令是否需要确认、输入是否安全，仍由 Harness 在模型之外判断。运行时也可能提供额外的自然语言工具说明，具体组织方式不应视为稳定 API。

### messages

[Messages API](https://platform.claude.com/docs/en/api/messages/create) 使用 `messages` 承载项目上下文和对话历史，包括 `user` 与 `assistant` 消息、已经调用的技能正文以及当前输入。`tool_result` 不是独立角色，而是 `user` 消息中的内容块。对于客户端执行的工具，它必须紧跟在对应的 `assistant` 工具调用之后。

```d2
direction: right

P: 项目上下文\nCLAUDE.md、记忆、规则
H: 对话历史\nuser、assistant、工具结果
S: 已加载技能\nSKILL.md 正文
N: 本轮用户输入\n任务 + 显式附加内容

P -> MSG
H -> MSG
S -> MSG
N -> MSG
MSG: messages\n按顺序送入模型
```

本轮输入通常追加在已有上下文之后。它负责说明当前目标，但模型能否正确执行，还取决于前文提供的项目约束、相关文件内容和工具结果。system prompt、工具定义和 `messages` 共同构成模型上下文，不能只查看其中一个字段。

### 完整请求示例

下面展示工具执行后，下一轮请求的大致结构。它用于说明各类内容的边界，不是 Claude Code 实际网络请求的逐字段转储。

```json fold title="Anthropic Messages API 请求示意"
{
  "model": "<model-id>",
  "max_tokens": 8192,
  "system": [
    {
      "type": "text",
      "text": "<Claude Code 核心指令>"
    }
  ],
  "tools": [
    {
      "name": "Grep",
      "description": "搜索文件内容",
      "input_schema": {
        "type": "object",
        "properties": {
          "pattern": { "type": "string" }
        },
        "required": ["pattern"]
      }
    }
  ],
  "messages": [
    { "role": "user", "content": "<项目指令、记忆与前置上下文>" },
    { "role": "user", "content": "把登录接口的报错修一下" },
    {
      "role": "assistant",
      "content": [
        {
          "type": "tool_use",
          "id": "toolu_01",
          "name": "Grep",
          "input": { "pattern": "login" }
        }
      ]
    },
    {
      "role": "user",
      "content": [
        {
          "type": "tool_result",
          "tool_use_id": "toolu_01",
          "content": "<搜索结果>"
        }
      ]
    }
  ]
}
```

这个示例保留了三条关键边界。核心运行指令位于 `system`，工具通过 `tools` 单独声明，项目上下文和对话进入 `messages`。模型返回 `tool_use` 后，Harness 再用 `tool_result` 把执行结果写回下一轮。

## 执行工具调用循环

模型不会直接读取文件、执行命令或修改代码。对于 Claude Code 的本地工具，[工具调用循环](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)由 Harness 驱动。

1. 模型返回一个或多个 `tool_use` 内容块，并以 `stop_reason: "tool_use"` 暂停当前响应；
2. Harness 检查工具参数和权限，在允许的执行环境中运行工具；
3. Harness 保留模型的 `assistant` 消息，并把执行结果包装为下一条 `user` 消息中的 `tool_result`；
4. 更新后的 `messages` 再次发送给模型，直到模型结束当前轮次、用户中断或 Harness 触发其它停止条件。

修复登录接口时，这个循环可能依次读取代码、定位问题、修改文件并运行测试。每次工具调用都会增加新的上下文，较长的任务还可能触发上下文压缩。API 返回 `end_turn` 只表示当前模型响应结束，不等于代码已经通过验证，任务完成仍应由验收条件判断。

## 上下文构成与信任边界

进入上下文的内容来自不同控制方，不能简单分成「提示词」和「其它内容」。更有用的划分方式是看来源、加载时机以及谁负责约束。

| 内容                       | 主要来源                   | 加载时机         | 处理原则                                   |
| -------------------------- | -------------------------- | ---------------- | ------------------------------------------ |
| system prompt 与工具定义   | Claude Code 或应用配置     | 每轮请求         | 作为运行时配置维护，保持稳定且可审查       |
| CLAUDE.md、规则与自动记忆  | 用户、团队或当前仓库       | 启动或按需加载   | 作为模型指令使用，不能替代强制校验         |
| 技能描述与技能正文         | 技能作者                   | 启动或调用时加载 | 第三方技能应先审查，再授予工具和执行权限   |
| 用户输入与附加内容         | 当前用户                   | 本轮请求         | 视为动态输入，校验其中的路径和操作意图     |
| 文件、命令和外部工具结果   | 本地环境或外部系统         | 工具执行后       | 视为数据，防范错误内容和间接提示词注入     |
| 模型输出与工具调用请求     | 模型                       | 每轮响应         | 视为建议或待执行请求，由 Harness 决定是否执行 |

[工具结果](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)尤其需要单独处理。网页、第三方 API、仓库文件和用户上传内容都可能包含试图改变模型行为的文本。它们应保留在数据或 `tool_result` 边界内，不能直接提升为 system prompt，也不能绕过权限控制。

## 上下文设计原则

理解这条链路后，提示词、项目指令和运行时约束的职责可以分开设计。

- `CLAUDE.md` 只保留跨任务长期有效的项目规则，并写成具体、可验证的指令；
- 任务专用流程和较长参考材料放入技能或按路径加载的规则，避免在无关任务中占用上下文；
- 本轮提示词明确目标、范围和验收条件，不重复已经存在于项目指令中的内容；
- 用户输入、文件内容和工具结果始终作为动态数据处理，不能因为进入上下文就获得更高权限；
- 文件访问、命令执行、参数校验和审批由 Harness 强制控制，不能只依赖自然语言约束；
- 长任务需要管理历史和工具结果，必要时使用压缩、子 Agent 或结果裁剪，避免上下文持续膨胀；
- 稳定配置尽量少变，让 Claude Code 的提示词缓存能够复用请求前缀，降低重复处理成本。

一句提示词决定本轮要做什么，Harness 决定模型还能看到什么、可以调用什么，以及调用结果如何进入下一轮。把这三层分开，才能同时控制任务质量、上下文成本和执行风险。
