# 从一句提示词到模型上下文

在 Claude Code 里敲下「把登录接口的报错修一下」并回车，你以为发给模型的就是这句话。其实模型收到的上下文往往有几千到上万 token，你的那一句占比可能不到 1%，而且排在序列最后。多出的一切，都是 Agent 的运行时（Harness）在调用前替你组合、组装并传递进去的。

本文追踪这一句提示词从输入到进入模型的完整链路，看清 Agent 项目的提示词是怎么来的。链路以 Claude Code 为例，不同 Agent 产品的实现细节不同，但组合、组装、传递的结构一致。

## 链路总览

整条链路可以分成三个阶段：

- 组合：把身份、指令、环境、记忆、工具定义、技能这些片段准备好；
- 组装：每轮请求时把它们拼成 system prompt 和 messages；
- 传递：请求进入模型，工具结果再回注并推动下一轮。

```d2
direction: right

I: 用户输入\n"把登录接口的报错修一下"
C: 组合：上下文采集\n环境、记忆、工具定义、技能
S: 组装：system prompt\n身份 + 指令 + 环境 + 记忆
M: 组装：拼装 messages\n历史轮次 + 本轮输入
A: 传递：调用 API\nsystem + tools + messages
L: 模型推理

I -> C -> S -> M -> A -> L

T: 传递：工具执行\nHarness 受控运行
R: 传递：tool_result 回注\n追加为 user 消息

L -> T: tool_use
T -> R -> M: 下一轮重新组装
```

链路里每一次模型调用都走这套流程，用户敲的那一句只是起点。

## 捕获用户输入

回车那一刻，Claude Code 捕获的不只是你敲的字，还包括当前运行环境：

- 工作目录、操作系统、当前日期时间；
- git 仓库状态（分支、近期改动）；
- 你选中的文件、终端可见输出、附带的图片；
- 当前权限模式与可用工具集合。

环境事实（cwd、日期、OS）通常稳定，用于组装 system prompt；选中内容和终端输出属于「本轮附加上下文」，随这次输入一起进入最后的 user 消息。

## 加载 CLAUDE.md

Claude Code 在启动时读取项目级和用户级的 `CLAUDE.md`，也可能读取其它记忆文件。这些内容描述项目约定、常用命令、禁忌事项，是跨请求稳定、但来自文件系统的上下文。

一段 `CLAUDE.md` 可能长这样：

```text
# 项目约定
- 所有 shell 命令必须加 rtk 前缀。
- 修改文档后不要自动执行 docs:build。
- 提交必须使用 commit skill，遵循 Conventional Commits。
```

它和你的那一句性质不同：前者是可信、由开发者维护的指令；后者是单次、不可信的动态输入。这类内容通常被注入 system prompt（或作为独立上下文块，取决于版本）。

## 组装技能提示词

技能是另一类进入上下文的片段，加载方式和 CLAUDE.md 不同。每个技能是一个带 `SKILL.md` 的目录，frontmatter 声明 `name` 和 `description`，正文写具体指令。Claude Code 分两层处理：

- 摘要常驻：启动时扫描全部技能，把每个技能的 `name` 和 `description` 注入 system prompt，形成技能目录。模型借此知道有哪些技能、各干什么，但此时看不到正文；
- 正文按需：模型根据 `description` 判断当前任务匹配某个技能（或你手动输入 `/skill-name`）后，才读取完整 `SKILL.md` 正文注入上下文，供后续轮次使用。

两层在上下文占用上的差别很大：

| 部分     | 注入方式           | 占用上下文 |
| -------- | ------------------ | ---------- |
| 摘要     | 常驻 system prompt | 小，`description` 与 `when_to_use` 截断到 1536 字符 |
| 完整正文 | 命中才加载         | 命中前几乎为零 |

技能与 CLAUDE.md 形成对照：CLAUDE.md 每次请求都常驻，固定占用 token；技能正文只有命中才加载，长参考材料在用到之前几乎不占成本。摘要进 system prompt 成为稳定前缀，正文命中后作为动态片段参与组装，这就是「稳定前缀 + 按需组装」。

## 组装 system prompt

system prompt 是一段体积大、结构固定的模板，也是整段上下文里最大的稳定前缀。它大致由这几部分按顺序拼成：

| 区段         | 内容                               | 变化频率 |
| ------------ | ---------------------------------- | -------- |
| 身份与定位   | 「你是 Claude Code，一个命令行 Agent」 | 低       |
| 通用指令     | 如何思考、如何汇报、何时求助       | 低       |
| 工具使用指南 | 各工具的用途与调用时机             | 低       |
| 环境事实     | cwd、OS、日期、git 状态            | 中       |
| 注入记忆     | `CLAUDE.md` 与记忆文件内容         | 中       |
| 技能目录     | 各 SKILL.md 的名称与描述           | 中       |

前面几段长期不变，正是提示词缓存（Prompt Caching）能命中的部分。环境事实、记忆和技能目录会变化，但相对单次请求仍然稳定。

## 下发工具定义

Read、Edit、Bash、Glob、Grep 等工具，一方面在 system prompt 里用自然语言说明「何时、怎么用」；另一方面通过 API 的 `tools` 字段以结构化 schema 下发，让模型能生成合法的 `tool_use` 请求。

模型看到的工具定义同时包含「语义说明」和「结构契约」：语义说明帮助它判断该不该调用，结构契约保证它填对参数。两者必须一致，否则模型会按自然语言理解、却生成不符合 schema 的调用。

## 拼装 messages

`messages` 数组承载对话历史。如果之前已经聊了几轮、调用过工具，数组里已积累若干轮 `user` / `assistant` / `tool_result` 消息。你这一句作为最后一条 `user` 消息追加在末尾：

```d2
direction: right

H: 之前的轮次\nuser / assistant / tool_result
N: 本轮用户输入\n你的句子 + 附加上下文

H -> MSG
N -> MSG
MSG: messages 数组\n送入模型的对话历史
```

注意位置：你的输入在序列最后，前面是全部历史和环境。模型通常对靠近末尾的内容更敏感，但前面的工具结果和历史决定了它「知道什么」。一句提示词能否被正确执行，取决于它和前面上下文的衔接，而不只是它本身写得好。

## 发出 API 请求

把前面几步合起来，一次调用大致是这样（示意，省略了部分字段）：

```json fold title="Anthropic Messages API 请求（示意）"
{
  "model": "claude-opus-4-...",
  "max_tokens": 8192,
  "system": [
    {
      "type": "text",
      "text": "<身份 + 指令 + 环境事实 + CLAUDE.md 记忆 + 技能目录，约数千 token>",
      "cache_control": { "type": "ephemeral" }
    }
  ],
  "tools": [
    { "name": "Read", "description": "读取文件", "input_schema": { "type": "object", "properties": { "file_path": { "type": "string" } } } }
  ],
  "messages": [
    { "role": "user", "content": "之前的问题和上下文" },
    { "role": "assistant", "content": [ { "type": "tool_use", "id": "t1", "name": "Grep", "input": { "pattern": "login" } } ] },
    { "role": "user", "content": [ { "type": "tool_result", "tool_use_id": "t1", "content": "..." } ] },
    { "role": "user", "content": "把登录接口的报错修一下" }
  ]
}
```

你的那一句，就是 `messages` 最后一条 `user` 的 `content`。其余所有内容都由 Harness 在运行时组装，你没有直接写出它们。

## 回注与循环

模型可以返回纯文本，也可以返回 `tool_use`。返回工具调用时，Harness 受控执行该工具，把结果包装成 `tool_result` 追加为新的 `user` 消息，再带着更新后的 `messages` 调用模型。

于是「一句提示词」常常不是一次调用就结束：

- 第一轮：模型读代码、定位登录逻辑；
- 第二轮：模型编辑文件；
- 第三轮：模型跑测试、读结果；
- 直到模型判断任务完成或达到终止条件。

每一轮都重新组装 `messages`，历史越滚越长。初始那一句始终留在序列里，但后续每轮实际依据的是「历史 + 最新工具结果」。

## 回顾上下文构成

链路走到最后，模型最终收到的上下文由这几部分组成：

| 组成部分       | 来源                     | 可信度   | 是否每轮变化 |
| -------------- | ------------------------ | -------- | ------------ |
| system prompt  | 模板 + 环境 + CLAUDE.md  | 可信     | 低           |
| 工具定义       | 代码注册                 | 可信     | 低           |
| 对话历史       | 之前的轮次               | 混合     | 是           |
| 工具结果       | 工具执行输出             | 不可信   | 是           |
| 你的那一句     | 本次用户输入             | 不可信   | 单次         |
| 附加上下文     | 选中内容、终端、图片     | 不可信   | 单次         |
| 技能正文       | SKILL.md 正文           | 可信     | 仅命中时     |

你敲的那一句在整段上下文里占比可能不到 1%。它之所以起作用，是因为前面已经接好了 Harness 准备的环境、记忆、历史和工具结果。

## 设计启示

上面的链路落到工程上，是三个阶段的权衡。

**组合阶段：准备好片段**

- 记忆要克制：`CLAUDE.md` 和记忆文件每轮都参与组装，只保留跨请求长期有效的约束，过长会拖慢每一轮调用；
- 稳定前缀前置：身份、指令、工具指南尽量前置且少变，才能命中提示词缓存，降低成本和延迟。

**组装阶段：每轮拼出 messages**

- 提示词是「追加」不是「全部」：写提示词时考虑它接在已有上下文之后的效果，而不是假设模型只看到这一句；
- 循环会放大上下文：多轮工具调用让 `messages` 膨胀，需要裁剪历史、压缩早期轮次，否则会撞上上下文窗口。

**传递阶段：进入模型并回注**

- 约束落地代码：`CLAUDE.md` 写「禁止」只是引导，真正的拦截由 Harness 的权限和校验执行；
- 不可信数据标记：工具结果、检索内容、用户输入统一视为数据，关键校验放在模型之外做。

## 总结

在 Agent 项目里，用户的一句提示词只是入口。Claude Code 在它前后补上 system prompt、工具定义、CLAUDE.md 记忆、环境事实和对话历史，命中技能时还会加载对应的正文，才拼成模型真正看到的上下文；触发工具调用时，结果还会回注并推动下一轮重新组装。理解这条链路，才会意识到「写好提示词」真正的难点是设计它前后所有被组合、组装和传递的片段。
