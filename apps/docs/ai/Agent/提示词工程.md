# 提示词工程

提示词工程很容易被讲成“写 prompt 的技巧”。这会让人误以为，只要找到一段万能模板，模型就会稳定工作。

真实项目里并不是这样。模型面对的输入通常很乱：用户只说半句话，知识来自 RAG，工具结果可能很长，历史对话会撑爆上下文，输出还要被程序继续解析。prompt 写得松一点，模型就会自行补全；补得像，不代表补得对。

所以提示词工程不是写一句漂亮的话，而是设计一条可控链路：

```d2
direction: right

A: 用户输入
B: Prompt 模板
C: 上下文构建
D: 记忆选择
E: 模型调用
F: 输出校验
G: 返回或降级 {
  class: ok
}

A -> B -> C -> D -> E -> F -> G
```

这条链路要回答几个问题：

- 模型这次到底要做什么；
- 它能依赖哪些材料；
- 哪些内容不能编；
- 信息不够时怎么处理；
- 输出如何被程序稳定消费；
- 哪些历史信息要保留到下次；
- 成本、缓存和失败重试怎么控制。

如果只用一句话概括：**提示词工程的本质是把模糊的人类意图，变成模型可稳定执行、系统可验证的任务接口。**

## 先看一个坏例子

假设你在做企业知识库问答。最粗的 prompt 可能是：

```text
请根据下面内容回答用户问题。
```

这句话能跑，但一上线就会出问题：

- 上下文不足时，模型可能用常识补答案；
- 多段资料互相冲突时，模型不知道信哪一段；
- 用户问得模糊时，模型不知道要不要追问；
- 输出格式不稳定，下游解析经常失败；
- 历史对话太长时，成本和延迟很快上升；
- 用户纠正过的偏好，下次又被忘掉。

更可控的写法不是单纯把 prompt 写长，而是把任务拆成稳定结构：

```text
# Role
你是企业知识库问答助手。

# Task
仅基于给定上下文回答用户问题。

# Rules
- 不要使用上下文之外的信息。
- 如果上下文不足，返回 insufficient_context=true。
- 回答必须附带引用编号。

# Output Schema
{{json_schema}}

# Context
{{context}}

# Question
{{question}}
```

这段 prompt 仍然只是第一步。生产环境里，还要处理模板管理、上下文组装、短期记忆和长期记忆读写、缓存命中、输出校验，以及 prompt 改动后的评测。

## 一个可落地的 prompt runtime

落到代码里，prompt runtime 至少要拆出这些职责。它的重点不是生成文本，而是把一次模型调用前后的工程环节串起来：

| 模块            | 解决的问题                              |
| --------------- | --------------------------------------- |
| Prompt template | 固定任务、边界、变量和输出格式          |
| Context builder | 把 RAG、工具结果、历史摘要组装进 prompt |
| Memory manager  | 管理短期记忆和长期记忆                  |
| Cache layer     | 缓存稳定结果，降低成本和延迟            |
| Output parser   | 校验结构化输出，失败时重试或降级        |
| Evaluation      | 用样例集验证 prompt 改动是否真的变好    |

一次请求的大致流程是：

```ts
async function answerQuestion(input: UserInput): Promise<Answer> {
  const template = loadPromptTemplate('knowledge-base-qa@v3')
  const shortTermMemory = await loadShortTermMemory(input.sessionId)
  const longTermMemories = await selectLongTermMemories({
    userId: input.userId,
    scope: input.workspaceId,
    query: input.question,
  })
  const retrievedDocs = await retrieveDocs(input.question)

  const context = buildContext({
    question: input.question,
    retrievedDocs,
    shortTermMemory,
    longTermMemories,
    maxTokens: 6000,
  })

  const prompt = renderPrompt(template, {
    question: input.question,
    context,
    json_schema: answerSchema,
  })

  const answer = await callModelWithSchema<Answer>({
    prompt,
    schema: answerSchema,
    cacheKey: getCacheKey({
      templateVersion: template.version,
      model: 'reasoning-model',
      permissionHash: await getPermissionHash(input.userId, input.workspaceId),
      question: input.question,
      contextHash: hash(context),
    }),
  })

  await updateShortTermMemory({
    sessionId: input.sessionId,
    question: input.question,
    answer,
    retrievedDocs,
  })

  await writeLongTermMemoryCandidates({
    userId: input.userId,
    scope: input.workspaceId,
    question: input.question,
    answer,
  })

  return answer
}
```

这段代码表达的是职责边界：prompt 不是孤立字符串，而是由模板、上下文、记忆、缓存、输出校验共同组成的一次模型请求。

## 1. 管理 prompt 模板

模板要解决的是稳定性。不要把 prompt 散落在业务代码里，也不要让每个调用点自己拼字符串。模板应该像代码一样有名称、版本、变量和输出约束。

一个最小模板结构可以这样定义：

```ts
type PromptTemplate = {
  name: string
  version: string
  description: string
  variables: string[]
  body: string
}

const knowledgeBaseQaTemplate: PromptTemplate = {
  name: 'knowledge-base-qa',
  version: 'v3',
  description: '基于知识库上下文回答用户问题',
  variables: ['question', 'context', 'json_schema'],
  body: `
# Role
你是企业知识库问答助手。

# Task
仅基于 Context 回答 Question。

# Rules
- 不要使用 Context 之外的信息。
- 如果 Context 不足，返回 insufficient_context=true。
- 引用必须来自 Context 中的 source_id。

# Output Schema
{{json_schema}}

# Context
{{context}}

# Question
{{question}}
`,
}
```

渲染模板时要做变量检查，不要静默漏填：

```ts
function renderPrompt(template: PromptTemplate, variables: Record<string, string>) {
  for (const key of template.variables) {
    if (!(key in variables)) {
      throw new Error(`Missing prompt variable: ${key}`)
    }
  }

  return template.body.replace(/\{\{(\w+)\}\}/g, (_, key: string) => {
    return variables[key] ?? ''
  })
}
```

实践里建议把稳定指令放在前面，动态内容放在后面。这样读起来清楚。如果模型服务支持 prompt caching，稳定前缀也更容易被复用。

## 2. 组装上下文

上下文不是越多越好。真正的问题是：在有限 token 预算内，哪些内容最值得放进去。

常见来源包括：

- 当前用户问题；
- RAG 召回文档；
- 工具调用结果；
- 当前会话的短期记忆；
- 跨会话的长期记忆；
- 系统规则和输出 schema。

可以按优先级组装：

```ts
type ContextSection = {
  name: string
  content: string
  priority: number
  sourceIds?: string[]
}

function buildContext(input: { question: string; retrievedDocs: RetrievedDoc[]; toolResults?: ToolResult[]; shortTermMemory?: ShortTermMemory; longTermMemories: LongTermMemory[]; maxTokens: number }) {
  const sections: ContextSection[] = [
    {
      name: 'Question',
      priority: 100,
      content: input.question,
    },
    {
      name: 'Retrieved Docs',
      priority: 90,
      content: formatRetrievedDocs(input.retrievedDocs),
      sourceIds: input.retrievedDocs.map((doc) => doc.sourceId),
    },
    {
      name: 'Tool Results',
      priority: 80,
      content: formatToolResults(input.toolResults ?? []),
    },
    {
      name: 'Short Term Memory',
      priority: 60,
      content: input.shortTermMemory?.summary ?? '',
    },
    {
      name: 'Long Term Memory',
      priority: 50,
      content: formatLongTermMemories(input.longTermMemories),
    },
  ]

  return fitIntoTokenBudget(sections, input.maxTokens)
}
```

这里的重点是“先排序，再裁剪”。当前问题和 RAG 证据通常比历史摘要更重要，长期偏好也不能覆盖当前用户的明确指令。

```d2
direction: down

A: 候选上下文
B: 按来源分区
C: 相关性排序
D: 超出 token 预算? {
  shape: diamond
  class: decision
}
E: 摘要或丢弃低优先级内容 {
  class: fail
}
F: 注入 prompt {
  class: ok
}

A -> B -> C -> D
D -> E: 是
E -> D
D -> F: 否
```

不要把上下文管理写成“把数组 join 一下”。一旦上下文变长，系统必须知道每段材料来自哪里、优先级多少、能不能裁剪，以及裁剪后会不会影响引用。

## 3. 实现短期记忆

短期记忆解决的是：**这次会话做到哪了。**

它不是长期档案，也不是完整聊天记录。它只服务当前任务，帮助模型在多轮对话里记住阶段性状态。

短期记忆通常保存这些内容：

- 当前任务目标；
- 用户已经确认的约束；
- 已完成步骤；
- 失败尝试和原因；
- 关键工具结果；
- 下一步待办。

一个简单的数据结构可以这样设计：

```ts
type ShortTermMemory = {
  sessionId: string
  summary: string
  goals: string[]
  constraints: string[]
  completedSteps: string[]
  openQuestions: string[]
  updatedAt: string
}
```

更新短期记忆有三个常见触发点：

- 一轮模型回答结束后；
- 工具调用返回关键结果后；
- 会话历史接近 token 预算，需要压缩时。

实现上，不要每次都把全部历史塞回 prompt，而是把历史压成摘要：

```ts
async function updateShortTermMemory(input: { sessionId: string; question: string; answer: Answer; retrievedDocs: RetrievedDoc[] }) {
  const previous = await loadShortTermMemory(input.sessionId)

  const summary = await summarizeSessionState({
    previousSummary: previous?.summary ?? '',
    latestUserQuestion: input.question,
    latestAnswer: input.answer.answer,
    usedSources: input.retrievedDocs.map((doc) => doc.sourceId),
  })

  await saveShortTermMemory({
    sessionId: input.sessionId,
    summary,
    goals: previous?.goals ?? [],
    constraints: previous?.constraints ?? [],
    completedSteps: inferCompletedSteps(input.answer),
    openQuestions: inferOpenQuestions(input.answer),
    updatedAt: new Date().toISOString(),
  })
}
```

短期记忆的注入优先级要低于当前用户输入和最新工具结果，因为用户这轮说的话，永远比旧摘要更可信。

## 4. 实现长期记忆

长期记忆解决的是：**下次还应该知道什么。**

它跨会话存在，但不能什么都存。长期记忆一旦写错，会在很多后续任务里持续污染上下文，所以写入比读取更要谨慎。

长期记忆可以分三类：

| 类型     | 例子                                                            | 写入条件                     |
| -------- | --------------------------------------------------------------- | ---------------------------- |
| 用户偏好 | 喜欢中文回答、喜欢表格、代码示例用 TypeScript                   | 用户明确表达，或多次稳定出现 |
| 项目事实 | 仓库使用 pnpm、文档图表用 D2、提交信息遵循 Conventional Commits | 工具验证或项目文档确认       |
| 经验教训 | 某类问题必须先查配置，某个接口曾被用户纠正                      | 用户明确纠正或失败案例确认   |

长期记忆至少要带 metadata：

```ts
type LongTermMemory = {
  id: string
  userId?: string
  scope: string
  type: 'preference' | 'project_fact' | 'lesson'
  content: string
  source: 'user' | 'tool' | 'document' | 'eval'
  confidence: 'high' | 'medium' | 'low'
  createdAt: string
  updatedAt: string
  expiresAt?: string
}
```

读取长期记忆时，不要全量注入，要按任务相关性、作用域、时效性筛选：

```ts
async function selectLongTermMemories(input: { userId: string; scope: string; query: string }) {
  const candidates = await memoryStore.search({
    userId: input.userId,
    scope: input.scope,
    query: input.query,
    limit: 20,
  })

  return candidates
    .filter((memory) => !isExpired(memory))
    .filter((memory) => memory.confidence !== 'low')
    .sort(compareByRelevanceAndFreshness)
    .slice(0, 5)
}
```

写入长期记忆时，要先判断这条信息是否值得长期保存：

```ts
function shouldWriteLongTermMemory(candidate: { content: string; source: LongTermMemory['source']; confidence: LongTermMemory['confidence']; repeatedCount: number }) {
  if (candidate.confidence === 'low') return false
  if (candidate.source === 'user') return true
  if (candidate.source === 'tool' && candidate.confidence === 'high') return true
  return candidate.repeatedCount >= 3
}
```

写入前还要去重和处理冲突：

```ts
async function writeLongTermMemory(memory: LongTermMemory) {
  const existing = await memoryStore.findSimilar({
    scope: memory.scope,
    content: memory.content,
  })

  if (existing && isSameMeaning(existing, memory)) {
    await memoryStore.update(existing.id, {
      updatedAt: new Date().toISOString(),
      confidence: maxConfidence(existing.confidence, memory.confidence),
    })
    return
  }

  if (existing && isConflict(existing, memory)) {
    await memoryStore.archive(existing.id)
  }

  await memoryStore.insert(memory)
}
```

到这里可以把三类信息的边界收一下。短期记忆、长期记忆和 RAG 很容易混在一起，但它们解决的问题不同：

| 来源     | 解决什么           | 生命周期 | 注入策略       |
| -------- | ------------------ | -------- | -------------- |
| 短期记忆 | 当前会话做到哪了   | 会话级   | 只注入摘要     |
| 长期记忆 | 下次还应该知道什么 | 跨会话   | 只注入相关片段 |
| RAG      | 外部知识在哪里     | 文档级   | 注入可引用证据 |

记忆读写流程可以这样看：

```d2
direction: down

A: 当前会话
B: 生成短期摘要
C: 发现长期记忆候选
D: 值得长期保存吗 {
  shape: diamond
  class: decision
}
E: 丢弃候选 {
  class: fail
}
F: 去重和冲突处理
G: 写入长期记忆 {
  class: ok
}
H: 后续请求
I: 相关性检索
J: 注入 prompt {
  class: ok
}

A -> B
A -> C -> D
D -> E: 否
D -> F: 是
F -> G
H -> I -> J
G -> I
```

长期记忆最重要的原则是：宁可少存，也不要乱存。未经确认的模型推测，不能写成后续请求会反复继承的事实。

## 5. 做缓存和成本控制

缓存要解决两个问题：降低重复成本，减少重复工具调用带来的不确定性。

可以缓存的内容包括：

- RAG 检索结果；
- 外部工具返回值；
- 稳定 prompt 前缀；
- 低风险分类和路由结果；
- 结构化输出校验后的最终结果。

缓存 key 必须包含会影响结果的因素：

```ts
function getCacheKey(input: { templateVersion: string; model: string; permissionHash: string; question: string; contextHash: string }) {
  return hash({
    templateVersion: input.templateVersion,
    model: input.model,
    permissionHash: input.permissionHash,
    question: normalizeQuestion(input.question),
    contextHash: input.contextHash,
  })
}
```

不要只用用户问题做 key。模板版本、模型版本、权限范围、上下文内容变了，结果都可能变。

成本控制也要放进设计里，而不是上线后才补：

- 用小模型做分类、路由、摘要；
- 用强模型做复杂推理和最终生成；
- 限制 RAG 召回数量和上下文总长度；
- 对历史对话做短期摘要，而不是原样回放；
- 设置最大重试次数和 Agent 最大轮次；
- 记录输入 token、输出 token、延迟、缓存命中率和失败原因。

成本优化不是简单少给上下文。上下文给少了会答错，给多了会慢且贵。工程上要做的是让每段上下文都有来源、优先级和预算。

更完整的缓存 key、RAG 检索缓存、工具结果缓存和失效策略，可以看[《LLM 应用中的缓存设计》](./LLM 应用中的缓存设计.md)。

## 6. 结构化输出和失败降级

如果输出要给程序消费，不能只靠“请返回 JSON”。更稳的做法是用 schema 校验结果，并对失败原因做不同处理。

```ts
type Answer = {
  answer: string
  confidence: 'high' | 'medium' | 'low'
  citations: string[]
  insufficient_context: boolean
}

async function callModelWithSchema<T>(input: { prompt: string; schema: JsonSchema; cacheKey: string }): Promise<T> {
  const cached = await cache.get<T>(input.cacheKey)
  if (cached) return cached

  const raw = await model.generate(input.prompt)
  const parsed = parseJson(raw)
  const result = validateSchema<T>(parsed, input.schema)

  await cache.set(input.cacheKey, result)
  return result
}
```

解析失败、上下文不足、工具失败，不应该用同一种重试策略：

| 失败类型        | 处理方式                           |
| --------------- | ---------------------------------- |
| JSON 解析失败   | 发起一次格式修复请求，仍失败再降级 |
| schema 校验失败 | 带校验错误重试一次                 |
| 上下文不足      | 返回无法确认或触发追问             |
| 工具失败        | 重试工具或降级为人工处理           |
| 成本超预算      | 减少低优先级上下文或换小模型       |

重试要有上限。无限重试通常只会把错误变贵。

## 7. 用评测迭代 prompt

prompt 变更不能只靠感觉。每次改模板、上下文策略、记忆策略，都应该用固定样例集比较。

评测集至少覆盖：

- 正常问题能否回答准确；
- 上下文不足时能否拒答；
- 引用是否来自给定材料；
- 输出 schema 是否稳定；
- 短期记忆是否保留了任务状态；
- 长期记忆是否只在相关场景使用；
- 冲突记忆是否被正确覆盖；
- token、延迟、缓存命中率、费用是否可接受。

一个最小评测入口可以这样写：

```ts
type EvalCase = {
  id: string
  question: string
  context: RetrievedDoc[]
  expected: {
    mustContain?: string[]
    mustRefuse?: boolean
    citations?: string[]
  }
}

async function runPromptEval(cases: EvalCase[]) {
  const results = []

  for (const item of cases) {
    const answer = await answerQuestion({
      userId: 'eval-user',
      sessionId: `eval-${item.id}`,
      workspaceId: 'eval-workspace',
      question: item.question,
    })

    results.push({
      id: item.id,
      passed: checkAnswer(answer, item.expected),
      tokenUsage: collectTokenUsage(),
      latencyMs: collectLatency(),
    })
  }

  return summarizeEvalResults(results)
}
```

评测不是为了追求一个完美分数，而是为了知道每次改动影响了什么。比如新 prompt 让拒答更稳了，但引用准确率下降了，这说明改动带来了新的取舍。

## 到了 Agent，prompt 会变成行为规则

前面讨论的主要是一次问答请求。到了 Agent 场景，模型不只是回答，还要决定是否调用工具、是否继续推进、是否停下来确认。普通问答里，prompt 主要影响模型怎么说；Agent 接了工具、记忆和环境信息之后，prompt 还会影响模型怎么行动。

Agent 的 prompt 至少要约束这些决策点：

- 如何识别用户意图；
- 下一步如何规划；
- 哪些操作必须先确认；
- 什么时候可以调用工具；
- 工具失败时怎么恢复；
- 什么条件下认为任务完成；
- 最终结果怎么汇报。

工具描述也是 prompt 的一部分。工具名、参数、返回值、使用时机写得含糊，模型就容易误用、漏用，或者在该停下的时候继续往前冲。

```d2
direction: down

A: 用户请求
B: 意图识别
C: 规划下一步
D: 下一步需要确认吗 {
  shape: diamond
  class: decision
}
E: 请求用户确认 {
  class: fail
}
F: 继续执行
G: 停止或调整 {
  class: fail
}
H: 需要调用工具吗 {
  shape: diamond
  class: decision
}
I: 调用工具
J: 观察结果
K: 任务完成了吗 {
  shape: diamond
  class: decision
}
L: 组织回答
M: 返回结果 {
  class: ok
}

A -> B -> C -> D
D -> E: 需要
E -> F: 同意
E -> G: 拒绝
D -> F: 不需要
F -> H
H -> I: 需要
I -> J -> K
H -> L: 不需要
K -> C: 未完成
K -> L: 已完成
L -> M
```

Agent 场景下，短期记忆尤其重要。它记录“任务推进到哪一步”，避免模型在多轮工具调用后忘记原始目标。长期记忆则只应该注入稳定偏好和项目事实，不能替代当前工具结果。

## 总结

提示词工程不是 prompt 模板大全，而是一套让模型稳定参与软件系统的工程方法。

一个可靠的实现至少要做到：

- 模板有版本；
- 上下文有来源和预算；
- 短期记忆记录当前任务状态；
- 长期记忆只保存稳定、可追踪、可覆盖的信息；
- 缓存 key 能反映真实输入变化；
- 输出有 schema 校验；
- prompt 变更有评测对比。

做到这些，prompt 才不只是“写给模型看的话”，而是 LLM 系统里可维护、可验证、可迭代的一部分。
