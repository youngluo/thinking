# RAG 是什么

很多人一开始理解 RAG，容易把它说成“大模型加知识库”。这句话不能算错，但太粗了。真到项目里，RAG 解决的不是“模型会不会说”，而是“模型回答前，能不能先找到对的资料”。

所以这篇文章只讲四件事：

- RAG 是什么；
- 为什么需要它，适合哪些场景；
- 它的处理流程是什么，离线和在线分别干什么；
- 一个 RAG 系统通常怎么优化。

目标很简单：看完以后，至少能把意图识别、问题改写、召回、重排这些词放回完整链路里，不会只记概念，不知道它们各自解决什么问题。

## 核心概念

RAG 全称是 Retrieval-Augmented Generation，中文一般叫检索增强生成。

拆开看就两步：

- Retrieval：先检索外部知识；
- Generation：再让模型基于这些知识生成答案。

如果只用一句话概括：

**RAG 的本质，是让模型回答前先查资料，而不是只靠参数记忆现编。**

这里有两个关键点。

第一，RAG 不是单一模型能力，而是一条完整链路。它至少包含文档处理、索引构建、问题理解、内容召回、结果重排、上下文组装和答案生成。

第二，RAG 不是让模型“知道更多”，而是让模型“回答得更有根据”。模型本身还是那个模型，变化在于回答时多了一份外部证据。

## 为什么需要 RAG

理解 RAG，最好先看纯大模型问答为什么不够。

### 1. 模型知识不是实时的

模型训练有截止时间。你昨天刚更新的制度、今天刚改的接口、刚上线的产品规则，模型并不会自动知道。

这类问题如果只靠模型参数，很容易答成旧版本。

### 2. 私有知识不在模型参数里

很多业务问答本质上不是公共知识问答，而是私域知识问答，比如：

- 公司制度和流程；
- 内部 API 文档；
- 客服知识库；
- 项目资料和会议纪要；
- 代码库和运维手册。

这些内容，模型要么没见过，要么没见过你当前这版。

### 3. 用户的问题往往很具体

用户问的通常不是“介绍一下退款体系”，而是：

- 退款被驳回后怎么走；
- 错误码 40321 是什么；
- 这个接口为什么鉴权失败；
- 某个流程在第二种情况下怎么处理。

答案常常藏在某个段落、某个表格、某条规则里。这类问题靠模型泛化，不稳定；靠检索证据，才更稳。

### 4. 长上下文不是万能解法

有人会说，现在模型上下文已经很长，为什么不把资料全部塞进去？

因为这样通常会带来几个问题：

- 成本高；
- 延迟高；
- 噪声大；
- 真正相关的信息反而容易被淹没。

RAG 的价值就在这里：先筛，再答。先把相关资料找出来，再把最值得看的那部分交给模型。

## 什么场景适合用 RAG

RAG 适合的是“答案依赖外部知识，而且知识可以被整理和检索”的场景。

常见场景包括：

- 企业内部知识问答；
- 客服知识库；
- 制度和流程助手；
- 产品文档、接口文档问答；
- 代码库检索问答；
- 带引用来源的文档助手。

它不太适合的场景也要分清：

- 问题主要依赖开放式推理，而不是查资料；
- 没有稳定知识源，资料本身就不完整；
- 任务重点不是回答问题，而是多步执行、调用工具、推进流程。

后两类场景，往往更接近工作流或 Agent，而不是纯 RAG。

1. 离线阶段：先把知识整理成可检索资产；

### 离线阶段：先把知识整理好

离线阶段做的事，本质上是把“原始文档”变成“可被稳定检索的知识单元”。

#### 1. 数据接入与清洗

原始数据可能来自 PDF、Word、Markdown、网页、数据库、工单系统。第一步不是建向量，而是先把内容读对、洗干净。

这里常见问题包括：

- PDF 解析顺序错乱；
- 表格被拆坏；
- 标题层级丢失；
- 页眉页脚和噪声混进正文。

如果这一步做差了，后面召回通常也不会好。

#### 2. 切块

切块就是把文档拆成适合检索的 chunk。

这是 RAG 里最关键的一步之一，因为系统真正检索的往往不是整篇文档，而是文档块。

- 切太大：信息太杂，噪声多；
- 切太小：语义不完整，答不上来；
- 切错边界：明明文档里有答案，也召不出来。

工程里常见做法是：**结构优先，长度兜底，必要时加少量 overlap。**

这里的 `overlap`，说白了就是**相邻两个 chunk 之间保留一小段重叠内容**。

它主要解决一个问题：有些关键信息刚好卡在切分边界上，如果完全硬切，前一块没说完，后一块又少了前文，结果两块单独看都不完整。加一点 `overlap`，就是把边界附近那小段内容同时放进前后两个 chunk，减少语义被切断的概率。

但它也不是越大越好：

- 太小，补不到上下文断裂；
- 太大，会造成重复内容变多，召回和排序噪声也会增加。

所以它更像一个缓冲带，用来保住上下文连续性，不是主切分策略本身。

#### 3. 元数据补充

除了文本本身，还要给 chunk 带上元数据，比如：

- 文档标题；
- 章节路径；
- 更新时间；
- 来源链接；
- 业务域；
- 权限标签。

元数据的作用很直接：后面可以做过滤、引用、权限控制和结果解释。

#### 4. 向量化与索引

文本块准备好后，会做 embedding，把文本变成向量表示，再写入索引系统。

这里要分清两个概念：

- embedding 模型：负责把文本表示成语义向量；
- 索引系统：负责高效检索这些向量或关键词。

真实项目里，往往不只有向量索引，还会有关键词索引。因为错误码、接口名、表名、版本号这类问题，关键词匹配常常比纯语义匹配更稳。

下面几个词，经常一起出现，但各自负责的问题不同。

#### 1. 意图识别

意图识别，解决的是“用户现在到底想干什么”。

比如同样一句话，系统要先判断它是：

- 在问知识库问题；
- 在追问上一轮上下文；
- 在让系统执行操作；
- 还是只是闲聊。

如果连任务类型都判断错了，后面整条链路都会跑偏。所以意图识别本质上是在做路由。

#### 2. 问题改写

问题改写，解决的是“用户原话不一定适合直接拿去检索”。

常见情况有：

- 问题太短，比如“退款怎么走”；
- 带指代，比如“这个接口为什么失败”；
- 依赖上下文，比如“那第二种情况呢”；
- 用户说法和文档写法不是一套词。

这时系统会把用户问题改写成更适合检索的形式，比如补足上下文、展开缩写、改成知识库里的标准说法，或者并发生成多个检索 query。

#### 3. 召回

召回，解决的是“从很大的知识库里，先捞出一批可能相关的候选内容”。

注意，召回阶段的目标不是一步命中最准答案，而是先尽量**别漏掉**真正有用的内容。

常见方式有：

- 向量召回：按语义相似度找内容；
- 关键词召回：按术语、错误码、接口名精确匹配；
- 混合召回：两路一起做，再合并结果；
- 多路召回：不同 query、不同索引、不同数据域并行召回。

很多 RAG 问题，本质不是模型答错了，而是正确材料根本没被召回来。

#### 4. 重排

召回拿到的候选，通常不止几条。重排，解决的是“这些候选里，谁最该排前面进上下文”。

它和召回的分工可以这样理解：

- 召回强调范围，要先尽量找全；
- 重排强调精度，要把最相关的内容顶上来。

很常见的一种情况是：正确答案其实已经在 top20 里，但没进 top3。这说明不是没找到，而是没排好。重排就是解决这个问题的。

#### 5. 上下文组装

不是把 topK 原样拼给模型就完了。上下文组装，解决的是“怎么把检索结果整理成模型看得懂、看得有效的一份材料”。

这里通常会做：

- 去重；
- 合并相邻 chunk；
- 控制总 token；
- 按主题或来源排序；
- 给证据加标题、编号、来源。

这一层做得粗，模型即使拿到了证据，也可能读不清重点。

#### 6. 生成答案

最后才是让模型生成答案。

这一步通常会明确约束模型：

- 优先依据给定上下文回答；
- 上下文不足时直接说不知道；
- 不要编造文档里没有的信息；
- 尽量给出引用来源。

所以生成阶段的重点，不是“让模型更会说”，而是“让模型按证据说”。

## RAG 一般怎么优化

RAG 的优化，最好别一上来就想着换大模型。先判断问题出在哪一层，再动手，效率高很多。

一个好用的排查顺序通常是：

1. 有没有召回到正确内容；
2. 召回到了，是否排进了前几名；
3. 排进去了，组装给模型时有没有被噪声淹没；
4. 证据已经给够了，模型是不是还是答偏了。

顺着这条链路看，优化路径通常集中在下面几类。

### 1. 优化切块

切块策略经常决定系统上限。

常见改法：

- 不同文档类型用不同切块策略；
- 先按结构切，再按长度补切；
- 调整块大小和 overlap；
- 保住表格、标题、代码块这类结构信息。

很多时候，RAG 效果差，不是检索模型不行，而是 chunk 从一开始就切坏了。

### 2. 优化召回

如果正确内容经常“根本没进候选池”，就优先看召回。

常见做法：

- 从纯向量改成混合召回；
- 增加问题改写；
- 做多 query 召回；
- 用元数据做过滤，缩小搜索空间；
- 按业务域拆索引，避免不同知识混在一起互相干扰。

### 3. 优化重排

如果正确内容能召回来，但总排不到前面，就该看重排。

重排通常是很高性价比的一步，因为它直接决定哪些证据能进模型上下文。

### 4. 优化上下文与回答模板

有些问题不是没找到证据，而是证据喂给模型的方式太粗。

可以优化的点包括：

- 合并重复或相邻 chunk；
- 控制上下文长度；
- 让高置信证据排前面；
- 给上下文增加来源标记；
- 明确回答模板和引用规则。

### 5. 做权限、缓存和评测

这是工程里很容易被后置，但实际上不能后补的部分。

- 权限：先过滤再检索，避免把不该看的内容召回来；
- 缓存：缓存解析、embedding、召回或答案，降低成本和延迟；
- 评测：建立失败案例集，区分是切块问题、召回问题、重排问题还是生成问题。

没有评测，优化就只能靠感觉；没有失败案例，系统就很难持续变好。

## 最后总结一下

如果要把 RAG 讲到最本质，其实就一句：

**先把资料找对，再让模型回答。**

它真正拼的，不是某个单点技巧，而是整条链路是否可靠：

- 离线阶段有没有把知识整理好；
- 在线阶段有没有把问题理解对；
- 召回和重排有没有把证据送到位；
- 生成阶段有没有做到基于证据回答。

这条链路顺了，RAG 才会像一个可靠系统；不然就只是“大模型加点文档”，看起来像，实际上不稳。
