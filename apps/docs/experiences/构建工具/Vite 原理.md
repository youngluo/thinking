# Vite

Vite 的核心是把开发阶段和生产阶段拆成两套策略。开发阶段尽量不提前打包业务代码，把源码按浏览器原生 ESM 方式直接交给浏览器加载；生产阶段才走完整构建流水线，做 Tree Shaking、代码分块和资源优化。

整体可以理解成这条主线：`启动 dev server -> 解析配置 -> 预构建依赖 -> 按需转换源码 -> 浏览器原生 ESM 加载 -> 文件变化 -> HMR 精准更新`

## 开发流程

Vite 开发模式的核心，是让浏览器参与模块图加载。传统打包器通常先把整个应用依赖图扫描、转换、打包，然后浏览器再加载一个或几个 bundle。Vite 则先启动服务，把 `index.html` 返回给浏览器，浏览器解析到 ESM import 后，再一个模块一个模块地向 dev server 请求。

大致流程如下：

```d2
direction: down

A: 执行 vite dev
B: 加载配置和插件
C: 创建 dev server
D: 扫描入口依赖
E: 依赖预构建
F: 返回 index.html
G: 浏览器解析 ESM import
H: 请求源码模块

server: Vite Dev Server {
  class: group

  I: resolveId（解析模块路径）
  J: load（读取模块内容）
  K: transform（按需转换源码）
  L: 返回浏览器可执行模块
}

M: 浏览器继续请求子模块
N: 建立模块图
O: 页面运行

A -> B -> C -> D -> E -> F -> G -> H -> server.I -> server.J -> server.K -> server.L -> M -> N -> O
M -> H
```

这条链路可以拆成几个关键步骤。

### 1. 启动 dev server

执行 `vite dev` 后，Vite 会先加载配置、解析插件、创建开发服务器，并注入一段客户端运行时代码。这个客户端负责和服务端建立连接，后续接收 HMR 消息、错误覆盖层消息以及页面重载指令。

这一步做的不是打包整个应用，而是准备一个能“按需响应模块请求”的服务：

- 能返回 `index.html`。
- 能把裸模块导入改写成浏览器可请求的 URL。
- 能对源码文件做转换。
- 能记录模块之间的依赖关系。
- 能监听文件变化并触发 HMR。

所以 Vite 冷启动通常很快。它不需要在一开始就把所有页面、所有路由、所有业务模块都处理完。

### 2. 依赖预构建

浏览器原生 ESM 不能直接理解这种裸模块导入：

```ts
import React from 'react'
import { debounce } from 'lodash-es'
```

浏览器需要的是一个明确的 URL，比如：

```ts
import React from '/node_modules/.vite/deps/react.js?v=hash'
```

Vite 的依赖预构建主要解决两个问题。

第一个问题是兼容性。很多 npm 包仍然可能以 CommonJS、UMD 或复杂入口形式发布，不能直接作为浏览器 ESM 使用。Vite 会把这些依赖转换成 ESM。

第二个问题是请求数量。有些依赖内部会拆成大量小模块，浏览器按原样逐个请求会让页面首屏变慢。预构建会把这类依赖整理成更少、更稳定的文件。

简化逻辑如下：

```text
扫描入口文件
  -> 找到裸模块导入
  -> 解析依赖入口
  -> 预构建到 node_modules/.vite/deps
  -> 改写 import URL
  -> 浏览器加载预构建产物
```

依赖和源码的处理方式不同：

- 依赖通常变化少，适合预构建和强缓存。
- 源码变化频繁，适合按需转换和 HMR。

### 3. 按需转换源码

业务源码不会在启动时全部转换。浏览器请求到哪个模块，Vite 才处理哪个模块。

例如浏览器请求：

```text
/src/App.tsx
```

Vite 会在服务端完成几件事：

```text
解析模块路径
  -> 读取文件
  -> 执行插件 transform
  -> 处理 TS / JSX / CSS 等语法
  -> 重写 import URL
  -> 返回浏览器可执行的 ESM
```

每个源码文件在开发时仍然以模块为单位存在，浏览器天然知道自己还需要请求哪些子模块。这就是 Vite 的开发模式更像“模块服务”而不是“提前打包”的原因。

不过按需转换不等于每次都重新转换。Vite 会结合文件时间戳、缓存、HTTP 协商和依赖缓存，尽量避免重复工作。

### 4. 建立模块图

Vite 在服务端会维护一份模块图。它记录模块之间的关系：

```text
ModuleNode {
  url
  id
  file
  importers
  importedModules
  acceptedHmrDeps
  transformResult
}
```

模块图在加载阶段帮浏览器建立依赖视图，HMR 阶段要靠它定位边界。

当某个文件变化时，Vite 需要知道：

- 这个文件对应哪个模块。
- 哪些模块 import 了它。
- 它自己是否接受热更新。
- 它的上游有没有 HMR 边界。
- 如果没有边界，是否需要整页刷新。

所以模块图可以理解成 Vite dev server 的运行时索引。浏览器负责真实加载模块，Vite 负责记录模块关系、转换结果和热更新边界。

## HMR 流程

HMR 解决的是开发阶段的反馈速度问题。文件变化后，Vite 不希望重新打包整个应用，也不希望总是整页刷新，而是尽可能只替换受影响的模块。

大致流程如下：

```d2
direction: down

A: 文件保存
B: chokidar 监听变化
C: 定位 ModuleNode
D: 清理转换缓存
E: 存在 HMR 边界? {
  shape: diamond
  class: decision
}
F: 生成 update 消息
G: 通过 WebSocket 推送
H: 浏览器 HMR client 接收
I: 重新 import 新模块
J: 执行 accept 回调
K: 局部更新视图
L: 整页刷新

A -> B -> C -> D -> E
E -> F: 是
E -> L: 否
F -> G -> H -> I -> J -> K
```

HMR 的关键不是“文件变了就重新加载文件”，而是要找到一个可以接住变化的边界。

### HMR 边界

一个模块如果显式调用了 `import.meta.hot.accept`，就表示它可以接受自己或某些依赖的热更新：

```ts
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // 使用新模块更新当前页面状态
  })
}
```

框架插件通常会帮业务代码生成这些逻辑。例如 Vue SFC、React Fast Refresh 都会把组件级更新接入 Vite 的 HMR API。

当某个模块变化时，Vite 会沿着模块图向上找 importers：

```text
变化模块
  -> 查找 importers
  -> 判断当前模块是否 accept
  -> 当前模块不 accept，则继续向上找
  -> 找到 HMR 边界，推送局部更新
  -> 找不到边界，触发整页刷新
```

这解释了一个常见现象：有些改动可以保留页面状态，有些改动会导致页面刷新。不是 Vite 随意决定的，而是模块图里是否存在合适的热更新边界。

### 浏览器端更新

服务端推送 HMR 消息后，浏览器端的 HMR client 会重新请求变化后的模块。为了绕过浏览器缓存，Vite 会在请求 URL 上追加时间戳或版本参数。

简化流程如下：

```text
收到 update 消息
  -> import('/src/App.tsx?t=timestamp')
  -> 拿到新模块实例
  -> 执行 accept 回调
  -> 框架运行自己的局部更新逻辑
```

对于 React 来说，组件状态能不能保留取决于 React Fast Refresh 的边界判断。Vite 提供 HMR 通道和模块更新机制，框架插件负责把这个能力翻译成框架内部能理解的刷新方式。

## 插件机制

Vite 的很多能力都通过插件串起来。插件不是只服务生产构建，也会参与开发服务器的模块解析、加载、转换和 HMR。

一个 Vite 插件可以简化理解成一组钩子：

```ts
export default {
  name: 'example-plugin',

  config(config) {},
  configureServer(server) {},

  resolveId(source, importer) {},
  load(id) {},
  transform(code, id) {},

  handleHotUpdate(ctx) {},

  buildStart() {},
  generateBundle() {},
}
```

开发阶段最常见的是这几个钩子：

- `resolveId`：把 import 路径解析成模块 id。
- `load`：自定义模块内容读取。
- `transform`：把源码转换成浏览器可执行代码。
- `configureServer`：扩展 dev server 中间件或 WebSocket 行为。
- `handleHotUpdate`：自定义文件变化后的 HMR 处理。

生产阶段则更接近完整构建工具链，会进入打包、分块、压缩和产物生成相关钩子。

同一套插件系统能同时覆盖开发体验和生产构建，Vite 会根据当前命令选择不同的执行路径，这也是 Vite 插件生态丰富的原因。

## 生产构建

开发模式追求的是启动快、更新快；生产构建追求的是资源体积、缓存命中、加载顺序和浏览器兼容。

所以 `vite build` 不会沿用开发时“浏览器按需请求每个源码模块”的方式，而是会重新构建完整依赖图，生成适合线上部署的静态资源。

大致流程如下：

```d2
direction: down

A: 执行 vite build
B: 加载生产配置
C: 以 index.html 为入口
D: 构建完整模块图
E: 执行插件构建钩子
F: Tree Shaking
G: 代码分块
H: CSS 和静态资源处理
I: 压缩与哈希命名
J: 生成 dist

A -> B -> C -> D -> E -> F -> G -> H -> I -> J
```

生产构建会做开发阶段不适合做的事情：

- Tree Shaking：移除未使用代码。
- Code Splitting：按入口和动态导入拆分 chunk。
- CSS Code Splitting：把异步 chunk 相关 CSS 拆出并按需加载。
- 资源哈希：生成长期缓存友好的文件名。
- modulepreload：为入口 chunk 和直接依赖生成预加载提示。
- 压缩：减小 JS、CSS 和资源体积。

开发阶段追求反馈速度，生产阶段追求加载效率，这是两个不同的问题，所以 Vite 才把开发与生产拆成两套策略。

## 为什么快

Vite 的快来自几个关键决策：

- **启动时少做事**：传统打包器启动时要先构建完整依赖图再输出开发 bundle；Vite 启动时只准备服务器、插件、依赖预构建和入口 HTML，源码等请求到时再转换。所以启动时间不会随源码数量线性增长。

- **更新时少做事**：传统打包器每次变化都要重新生成受影响 bundle；Vite 的模块天然分开，文件变化只让浏览器重新 import 这个模块或 HMR 边界模块，HMR 成本接近“变化模块的转换成本”。

- **依赖和源码分开处理**：第三方依赖体积大、层级深但变化少，适合预构建加缓存；业务源码变化多但单文件成本低，适合按需转换加 HMR。两边互换处理方式都会出问题：把依赖当源码处理会拖慢首屏，把源码当依赖处理会拖慢启动。

- **转换和检查分离**：Vite 默认只做 TS 转译不做类型检查，因为转译可按文件完成，类型检查要解析整个类型图会拖慢请求。把类型检查交给 `tsc --noEmit --watch` 独立跑，既不阻塞请求链路，也不丢类型质量。

## 和传统打包器的差异

可以用一句话概括：

`Webpack dev 更像先构建 bundle 再服务 bundle，Vite dev 更像先服务源码模块再按需转换模块。`

这里的传统打包器，主要以 Webpack 为代表。Webpack 的开发模式建立在 bundle 之上：先从入口开始分析依赖图，把源码、依赖、样式、资源都纳入构建流程，生成开发环境下的 bundle，然后浏览器加载这个 bundle。

Vite 的开发模式建立在浏览器原生 ESM 之上：先启动一个模块服务，把 `index.html` 返回给浏览器；浏览器解析到 `import` 后，再向 dev server 请求具体源码模块。Vite 只在模块被请求时做转换。

对比如下：

| 维度       | Webpack 开发模式                                                | Vite 开发模式                                                    |
| ---------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| 启动       | 先从 entry 构建应用级依赖图，再生成开发 bundle                  | 先启动 dev server，业务源码等浏览器请求时再转换                  |
| 源码       | 通常在启动阶段进入打包图，由 loader 统一处理                    | 保持源码模块形态，浏览器按 ESM import 逐个请求                   |
| 依赖       | 和源码一起进入构建链路，再通过缓存、splitChunks 等方式优化      | 先预构建为稳定的 ESM 产物，并放入 `node_modules/.vite/deps` 缓存 |
| HMR        | 文件变化后重新编译受影响模块，生成 hot update chunk             | 文件变化后定位模块图和 HMR 边界，让浏览器重新 import 新模块      |
| 浏览器角色 | 主要加载 Webpack 输出的 bundle，模块关系由 Webpack runtime 管理 | 参与原生 ESM 模块加载，模块请求本身暴露给 dev server             |
| 生产构建   | 构建完整依赖图，输出压缩、分块、带 hash 的静态资源              | 同样构建完整依赖图，输出适合部署的静态资源                       |

两者真正不同的地方，主要在开发阶段。Webpack 走统一构建图，loader 和 plugin 能处理各种复杂资源和历史模块格式；代价是项目越大，冷启动和热更新越容易被构建图规模拖慢。Vite 把业务源码推迟到浏览器按需加载，文件变化时只处理 HMR 边界附近的模块；代价是 dev 和 build 不是完全同一条路径，某些只在生产构建中暴露的问题仍要靠 `vite build` 验证。Webpack 更像通用构建平台，Vite 更像面向现代 ESM 项目的开发体验优化方案，这正是 Vite 重新划分开发阶段职责的结果。

## 常见边界

Vite 的开发体验很快，但它不是没有成本：

- **首屏模块请求可能变多**：因为业务源码没有提前打包，浏览器会按模块发起请求。小项目几乎无感，超大项目或路由首屏依赖复杂时，仍然可能出现请求数量多的问题。Vite 依靠缓存、预构建、浏览器并发请求和按需加载来缓解这个问题，但它的开发模式本质上仍然是多模块请求。

- **TypeScript 默认不做类型检查**：Vite 能直接处理 `.ts` 文件，但默认只做转译。如果项目需要严格类型质量，应该在开发和 CI 中单独运行：

  ```bash
  tsc --noEmit
  ```

  或者使用插件把类型检查结果接入浏览器错误提示。

- **HMR 依赖边界质量**：HMR 能不能精准更新，取决于模块是否能形成稳定边界。纯工具模块、全局副作用模块、复杂状态初始化模块，可能无法安全热替换。这类场景下，整页刷新反而是更稳妥的选择。

- **开发和生产不是完全同一条链路**：Vite dev 和 Vite build 的目标不同，内部路径也不同。所以有些问题只会在生产构建暴露：

  - 动态导入路径无法静态分析。
  - 构建目标浏览器不支持某些语法。
  - 第三方包的 ESM/CJS 入口在构建时解析不同。
  - 资源路径依赖 `base` 配置。
  - chunk 拆分后出现加载失败或缓存问题。

  因此一个 Vite 项目不能只跑 dev server。关键改动仍然需要执行 `vite build`，并在必要时预览构建产物。

## 总结

Vite 的设计核心，是把开发阶段从“先全量打包”改成“按需模块服务”。

开发时，它利用浏览器原生 ESM，让源码模块按请求转换、按模块更新；依赖则通过预构建和缓存提前稳定下来。生产时，它再回到完整构建流程，做 Tree Shaking、代码分块、资源哈希、压缩和预加载优化。

所以理解 Vite，不该只记"快"。把开发与生产拆成两套策略，各按各自场景的优化目标设计，才是它快的原因。
