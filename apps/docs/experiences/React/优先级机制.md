# React 优先级机制

React 会为每笔更新分配 lane，再由 Root 从待处理的 lanes 中选择下一轮工作。对于并发任务，React 还会把 lane priority 映射为 Scheduler priority，用于安排 callback 的执行顺序。

这套机制解决三个问题：哪些更新更紧急、哪些更新可以一起处理，以及任务进入宿主环境后如何排序。

本文只展开优先级模型；更新如何汇总到 Root、时间切片如何暂停和恢复，见[《React 调度机制》](./调度机制.md)。

```d2 maxHeight=520
direction: right

next: 选择 nextLanes
sync: 包含同步 lane? {
  shape: diamond

```

## Lane 模型

Lane 使用 bitmask 表达更新类别和优先级集合，既能高效合并多笔工作，也能让不同优先级的 update 在 Render 中分批处理。

### 位模型

每条 lane 占用一个 bit，多条 lanes 可以通过按位或合并到同一个数字中：

```text fold
SyncLane              = 0b0000000000000000000000000000010
InputContinuousLane   = 0b0000000000000000000000000001000
DefaultLane           = 0b0000000000000000000000000100000
TransitionLane1       = 0b0000000000000000000001000000000
TransitionLane2       = 0b0000000000000000000010000000000
```

如果 Root 上同时存在同步更新和 Transition 更新，可以用按位或合并：

```ts
const pendingLanes = SyncLane | TransitionLane1
```

判断集合中是否包含某条 lane，则使用按位与：

```ts
const hasSyncLane = (pendingLanes & SyncLane) !== 0
```

因此，一个整数就能表示一组 lanes，并通过位运算快速合并、筛选和删除。

### 优先级选择

Lane 模型中，通常越靠低位的 lane 优先级越高。React 通过取最低位的 `1`，从 lanes 集合中得到最高优先级 lane：

```ts
function getHighestPriorityLane(lanes: Lanes): Lane {
  return lanes & -lanes
}
```

例如，`0b101000 & -0b101000` 的结果是 `0b001000`。React 不需要遍历数组，就能从一组 lanes 中取出最紧急的 lane。

### Lane 组

某些更新类型对应一组 lanes。例如，Transition 拥有多条 transition lanes：

```text fold
TransitionLanes =
  TransitionLane1 |
  TransitionLane2 |
  TransitionLane3 |
  ...
```

不同 Transition 可以分配到不同 bit，再由 React 根据上下文合并、挂起或重试。由此，lane 模型主要表达两类信息：

- 优先级类别：哪类更新更紧急；
- 批次边界：哪些更新可以在同一轮 Render 中处理。

pending、suspended、pinged 和 expired 并不是 lane 自身的属性，而是 Root 使用多组 lanes 集合记录的调度状态。

## 分配 lane

React 通过 `requestUpdateLane` 为更新选择 lane。lane 的选择会结合当前执行上下文：

- Legacy Root 中的更新使用同步 lane；
- Transition 作用域内的更新使用 transition lane；
- Render 阶段更新有单独的兼容逻辑；
- 其他更新根据当前事件优先级选择 lane。

不同更新入口的内部顺序不完全相同，但 lane 最终会随 update 一起进入更新队列。后续 Root 选择工作、Render 消费 update，以及 Fiber 判断是否可以 bailout，都会围绕本轮 `renderLanes` 进行。

## Root 选择下一批 lanes

处理 Root 调度的微任务执行时，React 会通过 `scheduleTaskForRootDuringMicrotask` 为每个 Root 选择后续工作。Root 上与选择相关的核心状态包括：

```text fold
root.pendingLanes      // 等待处理的 lanes
root.suspendedLanes    // 当前被 Suspense 挂起的 lanes
root.pingedLanes       // 已被唤醒、可以重试的 lanes
root.expiredLanes      // 已经过期，需要尽快处理的 lanes
root.callbackNode      // 当前注册的 Scheduler task
root.callbackPriority  // 当前 task 对应的 lane 优先级
```

`getNextLanes` 会结合这些状态选择下一轮 Render：

- 从仍然 pending 的 lanes 中选择工作；
- 暂时跳过被挂起且尚未唤醒的 lanes；
- 允许已经 ping 的 lanes 重试；
- 优先处理已经过期的 lanes；
- 判断当前 Render 的 lanes 是否可以继续处理。

最终结果通常是一组 lanes，而不是单条 lane，因为 React 可以在同一轮 Render 中处理多个兼容优先级的更新。

### Lane 如何影响 Render

调度选出的 lanes 会成为本轮 Render 的 `renderLanes`。React 消费更新队列时，会检查每个 update 的 lane 是否包含在 `renderLanes` 中。

假设某个 Fiber 的 update queue 中有两笔更新：

```text
update A: SyncLane
update B: TransitionLane
```

如果本轮 `renderLanes` 只包含 `SyncLane`，React 会先处理 update A，跳过 update B。被跳过的 update 会保留在队列中，并在 transition lanes 被选中时重新参与计算。

因此，lane 不只决定更新的先后顺序，还决定本轮 Render 消费哪些 update。

## Lane priority 与 Scheduler priority

React 中有两套相关但不同的优先级：

- Lane priority：属于 React 更新模型，决定下一轮 Render 处理哪些 update；
- Scheduler priority：属于 Scheduler task，决定 callback 在任务队列中的排序。

Root 先通过 lanes 选择下一批更新。对于需要 Scheduler 执行的并发工作，React 会将 lanes 转换为 event priority，再映射成 Scheduler priority。同步 lane 则走微任务末尾的同步 flush，不注册 `ImmediatePriority` Scheduler task。

### 同步 lane 的微任务路径

`scheduler` 包仍然提供 `ImmediatePriority`，但当前 Root 调度不会把同步 lane 映射为 `ImmediatePriority` 再注册普通 task。React 会先把 Root 加入调度链表，然后在微任务中选择 lanes，并在微任务末尾统一 flush 仍包含同步工作的 Root。

```d2 maxHeight=460
direction: down

update: 触发 SyncLane 更新
ensure: ensureRootIsScheduled
list: Root 加入调度链表
microtask: 处理 Root 调度的微任务
select: 选出包含同步 lane 的 nextLanes
flush: flushSyncWorkAcrossRoots_impl
render: performSyncWorkOnRoot

update -> ensure -> list -> microtask -> select -> flush -> render
```

这条路径既能合并同一轮调用栈中的多个同步更新，又能保证它们不会等到后续 Scheduler 宏任务才处理。一旦进入 `performSyncWorkOnRoot`，本轮 Render 不再使用时间切片。

### 并发 task 的优先级映射

对于不包含同步 lane 的 `nextLanes`，React 会先转换为 event priority，再映射为 Scheduler priority：

| Event priority | Scheduler priority |
| -------------- | ------------------ |
| `DiscreteEventPriority` | `UserBlockingSchedulerPriority` |
| `ContinuousEventPriority` | `UserBlockingSchedulerPriority` |
| `DefaultEventPriority` | `NormalSchedulerPriority` |
| `IdleEventPriority` | `IdleSchedulerPriority` |

如果 Root 上已有 task 的 callback priority 与新结果相同，React 会复用已有 task；如果优先级变化，则取消旧 task，再按新优先级注册 task。

## Scheduler task 的排序

Scheduler 不理解 Fiber 或 update 队列，只负责安排 task 的执行顺序。下面是当前默认配置中的 timeout；它们属于内部实现，并不是稳定 API。

| Scheduler priority | 默认 timeout |
| ------------------ | ------------ |
| `ImmediatePriority` | `-1ms` |
| `UserBlockingPriority` | `250ms` |
| `NormalPriority` | `5000ms` |
| `LowPriority` | `10000ms` |
| `IdlePriority` | 接近 31 位有符号整数上限 |

Scheduler 注册 task 时会计算：

```ts
const startTime = currentTime + delay
const expirationTime = startTime + timeout
```

带有 delay 且尚未到 `startTime` 的 task 会先进入 timer queue，按 `startTime` 排序；到达开始时间后，它会转入 task queue，按 `expirationTime` 排序。越早过期的 task 越靠前执行。

## 常见问题

### lane 和 Scheduler priority 是一回事吗？

不是。lane 属于 React 更新模型，决定本轮 Render 消费哪些 update；Scheduler priority 属于任务执行层，决定 callback 在 Scheduler 队列中的排序。React 会根据 lanes 推导 Scheduler priority，但两者不等价。

### startTransition 降低了什么优先级？

`startTransition` 会把作用域内安排的状态更新标记为 Transition。它改变的是 UI 更新在 React 调度中的优先级，不会延迟执行 `startTransition` 的回调函数。Transition Render 可以被更紧急的更新打断并重新开始。

### 低优先级更新被打断后会怎样？

Root 会在调度任务执行前重新选择 `nextLanes`。如果低优先级 Render 期间出现更紧急的 lane，React 会先处理高优先级更新，再重新评估低优先级工作。如果原有渲染现场仍可继续，就复用已有工作；否则基于最新状态重新 Render，并通过 bailout 跳过无关子树。
