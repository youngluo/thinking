# React 调度机制

调用 `setState` 后，页面为什么不会总是立即变化？如果短时间内连续产生多个更新，React 应该先处理哪一个？当一次 Render 持续太久时，它能不能先停下来，让浏览器响应用户操作？

这些问题都由调度机制处理。React 不会立即执行每次更新，而是先记录更新并汇总到 Root，再选择下一轮工作，决定以同步还是并发方式执行。确定执行时机和方式后，React 才进入 Render 计算 Fiber 树，并在 Commit 阶段提交结果。

要理解这个过程，可以从一次更新如何进入调度开始。

## 调度流程

从触发更新到进入 Render，完整的调度链路如下：

```d2 maxHeight=820
direction: down

trigger: 触发状态更新
create: 创建 update 并分配 lane
enqueue: update 进入对应更新队列
propagate: 向上标记 lane，找到 Root

rootSchedule: Root 调度 {
  class: group

  pending: 合并到 pendingLanes
  ensure: ensureRootIsScheduled
  list: 将 Root 加入调度链表
  microtask: 预约处理 Root 调度的微任务
  next: getNextLanes 选择下一批 lanes
  type: 包含同步 lane? {
    shape: diamond
    class: decision
  }
  sync: 微任务末尾同步 flush
  reuse: 现有 Scheduler task 可复用? {
    shape: diamond
    class: decision
  }
  keep: 复用现有 task
  replace: 取消旧 task，注册新 task

  pending -> ensure -> list -> microtask -> next -> type
  type -> sync: 是
  type -> reuse: 否
  reuse -> keep: 是
  reuse -> replace: 否
}

syncEntry: performSyncWorkOnRoot
concurrentEntry: performWorkOnRootViaSchedulerTask
render: 进入 Render 阶段

trigger -> create -> enqueue -> propagate -> rootSchedule.pending
rootSchedule.sync -> syncEntry -> render
rootSchedule.keep -> concurrentEntry -> render
rootSchedule.replace -> concurrentEntry -> render
```

### 触发更新

更新可能来自 `setState`、`dispatch`、`root.render` 和 `forceUpdate` 等调用。`startTransition` 本身不会产生更新，但会把作用域内安排的状态更新标记为 Transition。

不同入口的内部顺序并不完全相同，但都会完成三项工作：

- 创建描述更新内容的 update；
- 为更新分配 lane；
- 将 update 放入对应 Fiber 或 Root 的更新队列。

因此，调用 `setState` 后页面不一定立刻变化。React 此时只是登记了一笔更新，后续还要经过批处理、Root 调度、Render 和 Commit。

### 分配 lane

React 通过 `requestUpdateLane` 为更新选择 lane。lane 会随 update 一起进入更新队列，供 Root 选择下一批工作，并在 Render 中决定消费哪些 update。

### 更新入队并标记到 Root

不同类型的更新进入不同队列：

- 函数组件的 `useState` 和 `useReducer` 更新进入 Hook queue；
- 类组件的 `setState` 和 `forceUpdate` 更新进入 class component update queue；
- `root.render` 产生的更新进入 HostRoot update queue。

update 记录“要修改什么”，lane 记录“在哪一类优先级下处理”。调度阶段不会立即消费 update；真正的计算发生在后续 Render 中。

更新入队后，React 会从触发更新的 Fiber 沿 `return` 指针向上标记 lane，并找到对应 Root。这个过程产生两类结果：

- 沿途 Fiber 的 `childLanes` 记录子树中存在待处理工作；
- Root 的 `pendingLanes` 合并本次更新的 lane。

调度任务以 Root 为单位，因此 Render 通常从 Root 开始。不过，从 Root 开始不等于整棵树都会重新计算；如果某棵子树在当前 `renderLanes` 下没有相关工作，React 仍可通过 bailout 跳过它。

### 将 Root 加入调度

更新标记到 Root 后，`scheduleUpdateOnFiber(root, fiber, lane)` 会调用 `ensureRootIsScheduled(root)`。当前实现中，`ensureRootIsScheduled` 不会立刻选择 lanes 或执行 Render，而是完成两件事：

- 将 Root 加入 React 维护的调度链表；
- 确保已经预约一个用于处理 Root 调度的微任务。

同一轮调用栈中即使多个更新反复调用 `ensureRootIsScheduled`，同一个 Root 也只需保留一份调度记录，并且只需预约一次微任务。这为后续批处理提供了基础。

### Root 选择下一批 lanes

微任务执行时，React 会遍历调度链表，并通过 `scheduleTaskForRootDuringMicrotask` 为每个 Root 选择后续工作。`getNextLanes` 会结合 pending、suspended、pinged 和 expired 等状态，选出下一轮 Render 要处理的一组 lanes。

### 安排同步或并发任务

选出 `nextLanes` 后，React 会根据其中是否包含同步 lane 选择执行路径。

同步工作不注册普通 Scheduler task。React 会记下 Root 存在同步工作，并在当前微任务末尾统一调用 `flushSyncWorkAcrossRoots_impl`，随后进入 `performSyncWorkOnRoot`。

并发工作通过 Scheduler task 执行。React 会根据 `nextLanes` 判断能否复用已有 task；如果不能复用，则取消旧 task 并注册新 task。

### 进入 Render

任务执行时会进入两类入口：

- `performSyncWorkOnRoot`：处理同步工作，不使用时间切片；
- `performWorkOnRootViaSchedulerTask`：处理 Scheduler 调起的并发工作，可以使用时间切片。

进入 Render 后，React 根据选出的 lanes 准备 `workInProgress`，再执行 `beginWork`、`completeWork` 等流程。调度到这里完成了主要职责：决定本轮处理哪些更新，以及以同步还是并发方式执行。

## 时间切片

时间切片让并发 Render 有机会归还主线程。浏览器不会主动暂停 React 的 JavaScript；React 会在 Fiber 工作单元之间调用 Scheduler 提供的 `shouldYield()`，判断是否退出当前 work loop。

### 基本流程

同步 Render 的 work loop 会持续处理 Fiber，直到工作完成：

```ts
while (workInProgress !== null) {
  performUnitOfWork(workInProgress)
}
```

并发 Render 会在每个 Fiber 工作单元之间检查是否需要让出主线程：

```ts
while (workInProgress !== null && !shouldYield()) {
  performUnitOfWork(workInProgress)
}
```

`performUnitOfWork` 会执行当前 Fiber 的 `beginWork`；没有子 Fiber 可继续处理时，再通过 `completeUnitOfWork` 向上完成工作。React 只能在一个工作单元结束后暂停，不能在组件函数执行到一半时中断。

### shouldYield

Scheduler 默认会在一段连续工作达到约 5ms 后让出执行权；如果宿主环境已经请求绘制，也可能提前让出。可以将核心判断简化为：

```ts
function shouldYieldToHost() {
  if (needsPaint) return true
  return now() - startTime >= frameInterval
}
```

这里的 5ms 是默认时间片，不是浏览器的硬中断点。若某个组件函数本身执行了 20ms，React 仍要等函数返回，才能再次检查 `shouldYield()`。

### 暂停与恢复

并发 Render 暂停后，React 保留 `workInProgress`、`renderLanes` 等渲染现场；如果当前 Root 的 task 仍可复用，`performWorkOnRootViaSchedulerTask` 会返回 continuation。Scheduler 将这个函数保存到当前 task，等待下一次宿主任务继续执行。

```d2 maxHeight=680
direction: down

run: Scheduler 执行 Root callback
render: React 执行 Render，直到完成或让出
done: Render 已完成? {
  shape: diamond
  class: decision
}
commit: Render 完成，进入 Commit
keep: 当前 Root task 仍可复用? {
  shape: diamond
  class: decision
}
continuation: 返回并保存 continuation
host: 预约下一次宿主任务
reselect: 重新选择 nextLanes
reschedule: 结束当前 callback，由 Root 重新调度

run -> render -> done
done -> commit: 是
done -> keep: 否
keep -> continuation: 是
keep -> reschedule: 否
continuation -> host -> reselect -> run
```

在浏览器中，宿主任务通常通过 `MessageChannel` 安排；在不同环境下，Scheduler 也可能使用 `setImmediate` 或 `setTimeout`。关键不在具体 API，而在于 continuation 进入后续宿主任务，使浏览器有机会在两段 React 工作之间处理输入和绘制。

恢复时，React 会重新计算 `nextLanes`。如果原 task 的优先级仍然适用，就继续执行该 task；进入 work loop 后，React 再判断能否沿用已有渲染现场。如果期间出现更高优先级更新或调度条件发生变化，React 会结束当前 callback，并按最新状态重新调度。

时间切片有两个边界：

- 它切分的是 Render 阶段，Commit 一旦开始仍会同步完成；
- 并发不等于多线程，React 仍主要运行在浏览器主线程上。

即使某轮低优先级 Render 需要重做，也不代表整棵树的工作都会重复。React 仍可结合 props、state、lanes 和 `childLanes`，在 `beginWork` 中 bailout 没有变化的子树。

## 批处理

批处理解决的是多个更新能否合并到较少的 Render 中。React 会先让 update 入队并将 lanes 汇总到 Root，再统一处理 Root 调度，而不是每次调用状态更新函数都立即执行完整 Render。

```d2 maxHeight=420
direction: right

context: 同一次事件或回调
updateA: setState A
updateB: setState B
updateC: setState C
queue: 多个 update 入队
root: lanes 汇总到 Root
schedule: 统一安排 Root 调度
render: 一轮 Render 处理兼容更新

context -> updateA -> queue
context -> updateB -> queue
context -> updateC -> queue
queue -> root -> schedule -> render
```

批处理通常具有这些表现：

- 同一个事件处理函数或异步回调中的多次状态更新通常会被批处理；
- update 可以位于不同 Fiber，但最终汇总到同一个 Root；
- Root 会根据 lanes 决定本轮一起处理哪些更新。

批处理不会把所有待处理更新强行塞进同一轮 Render。更高优先级的更新可以先执行，低优先级更新则保留在队列和 Root 上，等待后续轮次。因此，批处理负责尽量合并更新，lane 负责划分每轮 Render 的优先级边界。

## 常见问题

### 调度机制和渲染机制是什么关系？

调度机制决定何时执行、处理哪些 lanes，以及使用同步还是并发方式。渲染机制根据这些 lanes 计算 `workInProgress` 树，并在 Commit 阶段提交结果。

### 为什么一次 setState 不一定立刻更新页面？

`setState` 会先登记 update、分配 lane 并调度 Root。页面要等 Render 计算完成，并在 Commit 阶段提交结果后才会变化；处于同一批次的多个更新还可能合并处理。

### 并发渲染是不是多线程？

不是。并发 Render 仍主要运行在浏览器主线程上，只是可以在 Fiber 工作单元之间暂停，并在后续宿主任务中恢复。

### 为什么同步更新在微任务末尾 flush？

同步更新不需要 Scheduler 提供的时间切片和 continuation。React 先汇总同一轮调用栈中的 Root 更新，再在微任务末尾统一进入同步渲染入口，既保留批处理能力，也避免把同步工作推迟到后续宏任务。

### 为什么并发任务使用宿主任务恢复？

如果每次暂停后都用 microtask 继续，浏览器可能在 microtask 队列清空前一直得不到输入和绘制机会。将 continuation 安排到后续宿主任务，才能让 React 工作分段，并在段与段之间把主线程交还给浏览器。
