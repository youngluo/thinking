# Chrome 浏览器渲染机制

打开一个页面时，Chrome 需要协调导航、网络和渲染等多条工作链路。下图按首次显示页面的主线展开，实际执行中的资源下载、HTML 解析和部分渲染工作可以交错进行：

```d2 maxHeight=220
direction: right

url: 输入 URL
navigation: 导航调度
network: 网络请求
commit: 提交文档
parse: 解析 HTML 与加载子资源
script: 执行脚本
render: 样式计算与布局
paint: 分层与绘制
raster: 光栅化
composite: 合成与显示

url -> navigation -> network -> commit -> parse -> script -> render -> paint -> raster -> composite
```

这条主线分布在 Chrome 的多个进程中：

- 浏览器进程：负责地址栏、标签页、导航管理、权限、历史记录和进程协调；
- 网络进程：负责缓存、DNS、连接、请求、响应、代理和证书校验；
- 渲染进程：负责 HTML 和 CSS 解析、JavaScript 执行，以及样式计算、布局和绘制；
- GPU 进程：负责光栅化和屏幕绘制等 GPU 任务，同时承担显示合成职责。

渲染进程内部最关键的是主线程和合成线程。主线程负责 HTML 解析、脚本执行和文档生命周期中的多数渲染工作，因此最容易成为响应性瓶颈。合成线程则负责滚动、部分动画、分块和光栅任务调度，让部分帧能够绕过主线程生成。

## URL 导航

导航的入口在浏览器进程的 UI 线程。

用户在地址栏输入内容后，浏览器先判断它是搜索词还是 URL。搜索词会交给默认搜索引擎；URL 会补全协议，解析协议、域名、端口、路径、查询参数和哈希。

如果当前页面注册了 `beforeunload`，浏览器会在离开前让页面有机会展示确认对话框。该事件需要用户与页面交互过才可能生效，且在移动端等场景下并不可靠，不应用于常规状态保存。

如果本次是前进或后退导航，且命中前进后退缓存，页面可能直接从内存中恢复，不再完整走后面的网络请求和渲染流程。

容易慢在这里：

- 不必要的离页确认会打断导航，也可能在移动端因未触发而丢失未保存状态；
- 重定向链过长会重复执行导航和网络工作。

常见优化：

- 只在存在未保存数据时注册 `beforeunload`，数据保存后立即移除监听；
- 让请求直达最终地址，减少 HTTP 重定向；
- 使用 Chrome DevTools 检查页面未命中前进后退缓存的原因，再针对性处理。

## 网络请求阶段

导航确认后，请求交给网络进程。网络进程负责缓存判断、DNS 解析、连接建立、请求发送和响应接收。

### 缓存策略

网络进程在发起请求前，会先判断当前资源的浏览器缓存是否可用。这套规则同时适用于 HTML 主文档和 CSS、JavaScript、图片、字体等子资源：

- 强缓存：缓存仍然新鲜时，浏览器直接使用本地副本，不向服务器发起本次验证请求；
- 协商缓存：缓存需要重新验证时，浏览器带上缓存标识请求服务器判断资源是否变化；
- 强缓存主要由 `Cache-Control` 和 `Expires` 控制，前者在两者同时存在时优先；
- 协商缓存常使用 `ETag` 或 `Last-Modified` 作为验证器，服务器通常优先校验 `ETag`；
- 强缓存命中时没有新的 HTTP 响应。协商缓存命中时通常返回 `304 Not Modified`，资源已变化时则返回新的响应体。

容易出问题的地方：

- HTML 长时间命中强缓存，可能让用户继续使用旧入口文件；
- 静态资源缺少有效缓存，会导致重复下载；
- 资源更新与缓存策略不匹配，容易出现新旧版本混用。

常见优化：

- HTML 根据发布方式使用协商缓存或较短的强缓存，避免用户长期停留在旧入口；

```http
Cache-Control: no-cache
```

- 带内容 hash 的 CSS、JavaScript 和图片使用长期强缓存；

```http
Cache-Control: public, max-age=31536000, immutable
```

- 构建时让文件名包含内容 hash，内容变化后通过新 URL 绕过旧缓存；
- 包含敏感信息且不应存储的响应使用 `Cache-Control: no-store`。

### DNS 解析

DNS 解析由网络进程发起，必要时调用操作系统的解析能力。浏览器会先尝试使用已有结果，未命中时再通过系统和配置的 DNS 服务把域名解析成 IP 地址。具体缓存层级和查询顺序受浏览器、操作系统和网络配置影响。

DNS 解析完成后，网络进程才知道要连接哪台服务器。如果一个域名背后有多个 IP，浏览器或 DNS 服务还可能按可用性、地理位置和负载情况选择其中一个。

容易慢在这里：

- 首次访问域名时，DNS 查询会增加资源请求延迟；
- 页面依赖过多第三方源，会产生更多 DNS 查询和连接建立工作；
- DNS 解析不稳定会推迟对应源上的所有资源请求。

常见优化：

- 对大概率会请求、但无需立即建立连接的第三方源使用 `dns-prefetch`；

```html
<link rel="dns-prefetch" href="//cdn.example.com" />
```

- 对首屏确定需要的少量跨源资源使用 `preconnect`，提前完成 DNS 解析和建立连接所需的握手；

```html
<link rel="preconnect" href="https://cdn.example.com" crossorigin />
```

- 删除低价值第三方依赖，避免一个页面同时连接过多源。

### HTTP 连接和握手

连接建立由网络进程调度。

在 HTTP/1.1 和 HTTP/2 中，网络进程需要先建立 TCP 连接。TCP 三次握手可以简化为：

```text
客户端 -> 服务端：SYN，请求建立连接
服务端 -> 客户端：SYN + ACK，确认并请求建立连接
客户端 -> 服务端：ACK，确认连接建立
```

三次握手完成后，HTTP 请求才能通过这条 TCP 连接发送出去。

HTTP/1.1 可以复用 TCP 连接，但同一连接上的请求需要按顺序处理，浏览器通常通过建立多条连接提高并发能力。HTTP/2 仍基于 TCP，但能在一条连接上多路复用多个流。HTTP/3 基于 QUIC，通过 UDP 传输，不再让一个流的丢包阻塞其它流的数据交付。

容易慢在这里：

- TCP 握手通常需要一次网络往返；
- HTTP/1.1 并发能力有限，请求较多时容易排队；
- HTTP/2 的多个流共享一条 TCP 连接，丢包时仍可能同时影响多个流。

服务端可以根据自身软件和托管环境开启 HTTP/2。例如，新版 Nginx 可以使用以下配置：

```nginx
listen 443 ssl;
http2 on;
```

如果网关、CDN 和客户端都支持 HTTP/3，也可以开启 QUIC 监听并通过 `Alt-Svc` 声明 HTTP/3 服务：

```nginx
listen 443 ssl;
listen 443 quic reuseport;
http2 on;
add_header Alt-Svc 'h3=":443"; ma=86400';
```

除了升级协议，还要减少不必要的建连：

- 保持连接复用，不要为同类静态资源拆分过多源；
- 只对关键源使用 `preconnect`，避免空闲连接浪费系统资源。

```html
<link rel="preconnect" href="https://static.example.com" crossorigin />
```

### HTTPS 握手

HTTPS 握手也在网络进程这一层完成，证书校验属于这条链路的一部分。

HTTPS 在 HTTP/1.1 和 HTTP/2 下，通常先建立 TCP 连接，再进行 TLS 握手。TLS 握手主要完成以下工作：

- 协商 TLS 版本和加密参数；
- 服务端提供证书链；
- 浏览器校验证书链、有效期和域名等信息；
- 双方建立会话密钥，后续 HTTP 数据通过加密通道传输。

简化流程：

```text
TCP 三次握手
  -> ClientHello，浏览器发送支持的 TLS 能力
  -> ServerHello，服务端选择加密参数并返回证书
  -> 浏览器校验证书
  -> 双方协商会话密钥
  -> 使用加密通道发送 HTTP 请求
```

命中 TLS 会话复用时，浏览器可以减少重复访问的握手成本。HTTP/3 使用 QUIC，不再进行 TCP 三次握手，而是把传输层连接建立和 TLS 1.3 握手整合起来。

容易慢在这里：

- TLS 握手会增加建立新连接的延迟；
- 证书链过长或证书状态检查缓慢，会拖慢连接建立；
- 未启用会话复用时，重复访问的成本更高。

常见优化：

- 使用 TLS 1.2 或 TLS 1.3 等现代协议；
- 开启 TLS 会话复用，降低重复访问的握手成本；
- 配置 OCSP Stapling，由服务端在握手时提供证书状态信息；
- 对首屏必需的少量 HTTPS 源使用 `preconnect`。

### 发送 HTTP 请求

连接可用后，网络进程发送 HTTP 请求，其中包含请求方法、目标地址、请求头和可选的请求体。Cookie 和缓存验证器也会根据匹配规则加入请求。请求可能经过代理、网关、CDN 或负载均衡，最终到达目标服务器。

服务端收到请求后，执行路由匹配、鉴权、业务逻辑、数据查询、模板渲染或接口响应，然后返回 HTTP 响应。

容易慢在这里：

- Cookie 和其它请求头过大，会增加每次请求的上行传输成本；
- 请求体过大，会延长上传时间，并可能推迟服务端完整处理请求。

常见优化：

- 收紧 Cookie 的 `Domain` 和 `Path` 范围，避免与请求无关的 Cookie 被携带；
- 删除无意义的自定义请求头，避免在跨源请求中触发不必要的 CORS 预检；
- 大文件上传根据业务需求使用分片和断点续传，降低失败后的重传成本。

### 网络阶段的选择建议

首屏链路的优化重点是减少不必要的请求和建连，并让关键资源更早到达。可以先按以下顺序检查：

- 首屏关键资源是否过多，是否存在重复或可延后请求；
- 资源的缓存策略是否与更新方式匹配；
- 关键跨源资源是否需要 DNS 预解析或预连接；
- 连接是否充分复用，服务端是否支持 HTTP/2 或 HTTP/3；
- 请求头、Cookie 和请求体是否过大；
- 服务器或 CDN 的位置和响应速度是否符合预期。

确认排查方向后，再用工具查看对应证据。例如，使用 `curl` 检查缓存头：

```bash
curl -I https://example.com/index.html
curl -I https://static.example.com/assets/app.8d3f1a.js
```

如果首屏耗时仍然较长，可以在 DevTools 的 Network 面板查看 DNS、Initial connection 和 SSL 等分阶段耗时。确认瓶颈来自关键跨源连接后，再添加资源提示：

```html
<link rel="preconnect" href="https://static.example.com" crossorigin />
```

同一面板中的 Protocol 列可用于确认实际协议，请求和响应头则可用于检查 Cookie 体积与缓存策略。这些数据能够帮助区分网络延迟、服务端响应和资源调度问题。

## 接收响应

网络进程收到响应后，会根据状态码、响应头和内容类型决定后续处理：

- 301、302、307、308：根据 `Location` 响应头发起新的导航请求；
- 304：复用本地缓存中的响应体，并按规则更新元数据；
- 2xx：继续读取和处理响应体；
- 4xx、5xx：仍然是 HTTP 响应，浏览器会继续按响应类型展示内容，页面脚本或中间层也可能执行错误处理。

如果响应被判定为下载文件，它会交给下载管理器。对于可导航的 HTML 响应，网络进程会把数据流转交给渲染进程。如果响应体使用 gzip 或 Brotli 等方式压缩，浏览器会在后续解析前解压，并可以边接收边处理。

容易慢在这里：

- 服务端首字节时间过长，会推迟 HTML 解析和关键子资源的发现；
- HTML 过大会增加传输和解析成本；
- 重定向过多会重复进入网络请求阶段。

常见优化：

- 对 HTML、CSS 和 JavaScript 等文本资源启用 gzip 或 Brotli；
- 在支持流式输出的页面中尽早返回包含关键资源声明的 HTML；
- 使用缓存、查询优化或架构调整降低服务端首字节时间。

## 提交文档

浏览器进程会根据站点隔离和当前进程状态，为新页面选择或创建渲染进程。跨站点导航通常需要切换到不同的渲染进程。

渲染进程准备好后，浏览器进程会提交这次导航，更新地址栏、历史记录和标签页状态，并把响应数据流交给渲染进程。

这一步之后，HTML 数据会持续流入渲染进程，页面解析和资源加载可以并行推进。

容易慢在这里：

- 新建渲染进程需要初始化运行环境；
- 多层跨站重定向会同时增加网络延迟和进程切换工作。

常见优化：

- 对需要保留应用状态的同站交互，可以使用前端路由避免整页导航；
- 在确认用户大概率会访问且不会浪费流量时，再预取同站页面；

```html
<link rel="prefetch" href="/dashboard" />
```

- 登录和鉴权等流程避免多层跨域中转，尽量让服务端直接返回最终跳转地址。

## 解析 HTML

响应数据进入渲染进程后，主线程会增量解码和解析 HTML，逐步构建 DOM，无需等待整份 HTML 下载完成。同时，预加载扫描器会尝试越过当前解析位置提前发现可下载资源。

解析过程中遇到外部资源，会按资源类型触发不同处理：

- CSS：外部样式表下载后被解析为 CSSOM。匹配当前媒体条件的样式表默认会阻塞渲染，但不会直接暂停 HTML 解析；
- JavaScript：没有 `async`、`defer` 或 `type="module"` 的经典脚本会暂停 HTML 解析，等待脚本可用并执行完成。如果脚本前面存在尚未完成的阻塞样式表，脚本还需等待对应 CSSOM；
- 图片、字体和视频：通常不阻塞 HTML 解析，但下载、解码和尺寸变化可能影响后续布局与绘制。

预加载扫描器不构建 DOM，它的职责是在主解析器被脚本阻塞时继续发现部分 CSS、JavaScript、图片和字体 URL，尽早把下载任务交给网络进程。

容易慢在这里：

- HTML 过大会增加主线程的解析和 DOM 构建时间；
- 位于关键位置的同步脚本会暂停 HTML 解析；
- 阻塞渲染的样式表过大或到达过晚，会推迟首次渲染。

常见优化：

- 优先输出页面基本结构和关键资源声明，避免用脚本迟到创建首屏内容；
- 需要按文档顺序执行且依赖 DOM 的经典脚本使用 `defer`；

```html
<script defer src="/assets/app.js"></script>
```

- 与其它脚本无顺序依赖、下载后可以立即执行的脚本使用 `async`，例如独立的统计 SDK；
- 仅在能够度量收益时内联少量首屏关键 CSS，其它样式仍通过可缓存文件加载；

```html
<style>
  .hero {
    min-height: 60vh;
  }
</style>
```

- 只对当前页面很快会使用、且浏览器无法及时发现的关键资源使用 `preload`。

```html
<link rel="preload" href="/images/hero.webp" as="image" />
```

### 子资源加载

解析过程中发现的 CSS、JavaScript、图片、字体、视频等资源，由网络进程下载。网络进程会根据优先级、缓存状态、协议能力和连接复用情况调度下载。

资源优先级会根据类型、发现位置、是否阻塞渲染、是否在视口中以及 `fetchpriority` 等信息动态调整。不应依赖一份固定的优先级顺序，而应在 Network 面板中检查关键资源的实际调度结果。

容易慢在这里：

- 关键资源过多会竞争带宽和连接资源；
- 字体到达过晚会导致文字短暂不可见或字形切换；
- 图片尺寸和编码不合理会增加下载、解码和内存成本。

常见优化：

- 首屏只加载必要脚本，按路由或功能动态导入其它模块；
- 图片使用与展示尺寸匹配的像素数和合适编码格式；
- 视口外的图片可以使用原生懒加载；

```html
<img src="/list-item.webp" loading="lazy" width="320" height="180" alt="item" />
```

- 根据对字形切换和可见性的要求选择 `font-display` 策略；
- 当首屏核心图片在 HTML 中可直接发现时，可以使用 `fetchpriority="high"` 提示其优先级，但不要同时标记过多图片。

```html
<img src="/hero.webp" fetchpriority="high" width="1200" height="600" alt="hero" />
```

## 执行脚本

页面 JavaScript 默认在渲染进程主线程执行，与事件处理、样式计算、布局和绘制等工作共享执行时间。Web Worker 可以在工作线程执行计算，但不能直接操作 DOM。

主解析器遇到同步经典脚本时，会在脚本可用后暂停 HTML 解析并执行它。`defer` 脚本和没有 `async` 属性的模块脚本在文档解析完成后执行，`async` 脚本则在下载完成后尽快执行，不保证文档顺序。

脚本可以读写 DOM 和样式。如果它修改了会影响几何信息的内容，紧接着又读取 `offsetWidth` 或 `getBoundingClientRect()` 等布局信息，浏览器可能必须立即完成样式计算和布局，这称为强制同步布局。在循环中反复交错读写会形成布局抖动。

容易慢在这里：

- 长任务会持续占用主线程，推迟输入处理和新帧生成；
- 交错读写 DOM 和布局信息可能触发布局抖动；
- JavaScript 体积过大会同时增加下载、解析、编译和执行成本。

常见优化：

- 按路由或功能拆分代码，只在需要时加载和执行；
- 把非关键工作延后执行，并把无法在一帧内完成的长任务拆分成多个短任务；
- 先批量读取布局信息，再批量修改 DOM 和样式；
- 将不依赖 DOM 的重计算放到 Web Worker，避免持续占用主线程。

## 样式计算

CSS 解析后生成 CSSOM。在需要更新渲染结果时，浏览器会针对相关元素执行选择器匹配，再根据层叠、继承和默认样式得到计算样式（computed style）。这个过程还会把部分声明值转换为后续布局和绘制可使用的值。

容易慢在这里：

- DOM 规模过大会增加选择器匹配和样式更新的潜在范围；
- 影响范围过大的样式变化会让更多元素重新计算样式；
- 频繁切换 class 或内联样式，会持续使计算结果失效。

常见优化：

- 控制 DOM 规模，长列表使用虚拟列表等方式只渲染必要节点；
- 保持选择器简洁且易于维护，但应优先根据 Performance 记录确认样式计算是否真的构成瓶颈；
- 在同一次任务中批量完成样式修改，避免频繁触发中间状态的样式更新。

## 布局

样式确定后，浏览器会为需要参与布局的内容构建布局树，并计算各布局对象的尺寸和位置。布局树与 DOM 不是一对一关系：`display: none` 元素不会生成布局对象，`visibility: hidden` 元素仍然参与布局，伪元素和文本内容则可能生成 DOM 中没有对应元素节点的布局对象。

后续 DOM 或样式变化如果影响几何信息，相关范围就需要重新布局，也就是常说的 reflow。变化的影响范围取决于布局依赖关系，并非每次都会重新计算整个页面。

容易慢在这里：

- DOM 和布局树规模过大，会放大布局更新成本；
- 修改尺寸、位置或内容等影响文档流的信息，容易使更多布局结果失效；
- 读写布局信息交错会导致强制同步布局。

常见优化：

- 不依赖文档流重新排列的位移和淡入淡出动画，优先使用 `transform` 和 `opacity`；

```css
/* 避免 */
.box:hover {
  left: 20px;
}

/* 推荐 */
.box:hover {
  transform: translateX(20px);
}
```

- 对内外布局依赖较少的独立区域使用合适的 `contain` 值，缩小样式、布局或绘制的影响范围；
- 给图片、广告位和异步内容预留尺寸，减少布局偏移；

```html
<img src="/cover.webp" width="640" height="360" alt="cover" />
```

- 先批量读取布局信息，再批量写入 DOM。

## 分层

布局之后，浏览器还需要计算变换、裁剪、效果和滚动等绘制属性，再决定哪些内容适合分配到独立的合成图层。分层不与 DOM 结构一一对应，具体策略也由浏览器根据内容和设备状态决定。

视频、canvas、变换动画、滚动内容和某些裁剪或视觉效果，都可能产生独立合成图层。合理分层可以缩小后续更新范围，并让部分动画和滚动由合成线程处理；图层过多则会占用更多内存，增加光栅化和合成成本。

容易慢在这里：

- 需要频繁更新的内容未被有效隔离，可能导致较大范围重绘；
- 合成图层过多，会增加内存、光栅化和合成压力；
- 滥用 `will-change` 可能提前创建没有收益的合成资源。

常见优化：

- 只对已确认存在合成瓶颈、且即将发生变化的少量元素使用 `will-change`；

```css
.dragging {
  will-change: transform;
}
```

- 在动画结束后移除 `will-change`，不要给列表中的每一项长期声明该属性。

## 绘制

绘制阶段不直接在屏幕上生成像素，而是把背景、边框、文字、图片和阴影等内容记录为有顺序的绘制指令。后续光栅化阶段再把这些指令转换为像素。

如果变化只影响颜色、背景或阴影等视觉结果，可能只需要重新绘制（repaint），而无需重新布局。重绘后相关区域仍需重新光栅化并参与合成。

容易慢在这里：

- 复杂阴影、滤镜、渐变和大面积半透明效果会增加绘制或合成成本；
- 背景、边框和阴影等绘制属性频繁变化，会持续使相关绘制记录失效。

常见优化：

- 高频动画尽量避免持续改变 `box-shadow`、`filter` 和 `background-color` 等可能触发绘制的属性；

```css
/* 避免 */
.card:hover {
  box-shadow: 0 24px 80px rgba(0, 0, 0, 0.3);
}

/* 推荐：用 transform 做主要反馈 */
.card:hover {
  transform: translateY(-4px);
}
```

- 复杂阴影可以由伪元素预先绘制，交互时只改变伪元素的透明度。

## 光栅化

主线程提交绘制结果后，合成线程会把合成图层划分为图块（tile），按视口位置和预测的滚动方向确定优先级，再调度光栅任务。Chrome 通常在 GPU 进程中把绘制指令转换为 GPU 纹理图块，必要时也可以回退到 CPU 光栅化。

光栅化完成后，合成线程会根据图块在内存中的位置、页面中的绘制位置和合成属性生成 draw quads，再组成一个合成帧。

容易慢在这里：

- 大图片解码和大面积图层光栅化会占用大量时间与内存；
- 快速滚动时，如果新进入视口的图块来不及光栅化，可能出现内容缺失或掉帧。

常见优化：

- 使用响应式图片，通过 `srcset` 和 `sizes` 让浏览器选择合适的图片候选项；
- 长列表使用虚拟滚动控制 DOM 和绘制规模；
- canvas 根据设备像素比设置绘图缓冲区尺寸，同时限制最大像素面积。

```ts
const ratio = Math.min(window.devicePixelRatio, 2)
canvas.width = Math.floor(width * ratio)
canvas.height = Math.floor(height * ratio)
```

## 合成与显示

渲染进程的合成线程把 draw quads 组成合成帧，提交给 GPU 进程中的显示合成器。显示合成器还会汇总来自其它渲染进程和浏览器界面的帧，最终交给 GPU 绘制并显示到屏幕。

当元素已经拥有独立合成资源，且动画只改变可合成的 `transform` 或 `opacity` 时，新帧通常可以绕过主线程的布局和绘制。这是这两类属性更容易实现平滑动画的原因，但具体是否分层仍由浏览器决定。

容易慢在这里：

- 合成图层过多会增加 GPU 内存和合成成本；
- 主线程长任务会让需要主线程更新的新帧无法及时提交，也会推迟输入事件处理；
- 低端设备上过大的图块、过多图层或复杂视觉效果，都可能让 GPU 无法及时完成新帧。

常见优化：

- 使用 DevTools 的 Layers 和 Performance 面板查看分层原因、图层数量和合成耗时；
- 对位移和透明度动画优先修改 `transform` 和 `opacity`，同时检查它们是否实际走合成路径；
- 拆分主线程长任务，给浏览器处理输入和渲染的机会。

## 页面完成

首屏出现不等于页面已经加载完成或可以及时响应交互。加载过程中常用的事件节点有：

- `DOMContentLoaded`：HTML 已解析完成，`defer` 脚本和非 `async` 模块脚本已下载并执行。该事件不会等待图片、子框架和 `async` 脚本等资源；
- `load`：文档以及当前需要加载的样式表、脚本、图片和子框架等依赖资源已完成加载。原生懒加载资源不会阻塞该事件；
- 可交互状态：这不是单一浏览器事件。它取决于交互所需 JavaScript 是否就绪，主线程能否及时处理输入。

因此，性能评估不能只看 `load` 事件，还要结合以下用户体验指标：

- FCP：页面首次绘制来自 DOM 的文本、图片、非白色 canvas 或 SVG 等内容的时间；
- LCP：视口中最大候选内容元素的渲染时间，用于衡量加载体验；
- INP：页面在整个访问期间对用户交互的整体响应性；
- CLS：页面在整个访问期间未预期布局偏移的累积程度。

排查页面性能时，可以回到开头的三条工作链路：浏览器进程是否在导航和页面管理上等待，网络进程是否没有及时拿到关键资源，渲染与 GPU 链路是否无法及时生成和显示新帧。先用时间线、网络瀑布和帧数据定位瓶颈，再选择缓存、资源提示、任务拆分或合成优化，才能避免让局部技巧代替实际证据。
