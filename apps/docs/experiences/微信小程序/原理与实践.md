# 微信小程序原理与实践

小程序在用户视角看起来像一个轻量 App，在工程视角看起来像一个跑在客户端里的 WebView 容器。但它的运行模型既不是传统 Web，也不是 React Native 那一类原生组件树，而是自成一类：把 JS 逻辑和 UI 渲染拆到两条独立的线程里运行，通过客户端原生层通信。

## 运行环境

小程序运行环境由四部分组成：**Native、逻辑层、渲染层、基础库**。下面先把每一部分讲清楚。

```text
Native
  -> 注入基础库
  -> 创建逻辑层 JS 引擎
  -> 创建渲染层 WebView / Native
  -> 桥接两条线程
  -> 暴露 wx.* API
  -> 装载用户代码
```

Native 是微信客户端提供宿主能力的那一层。逻辑层是跑用户 JS 的引擎，iOS 上通常是 JavaScriptCore，Android 侧由客户端内置的 JS 引擎承载。渲染层是 WXML/WXSS/原生组件真正绘制的地方，主要承载在 WebView 上，少数原生组件（`map`、`video`、`canvas` 等）由客户端原生层直接渲染。基础库（`wx`）是微信自己实现的一套运行时，一部分以 JS 代码形式注入到逻辑层，一部分以原生代码形式驻留在客户端里。

这四部分都不归用户代码控制。开发者写下的 JS 只会跑在逻辑层；样式和模板经过编译后送进渲染层；任何越界操作（DOM 操作、动态执行代码）都会失败。

### 基础库与版本约束

小程序的可用能力，由**客户端版本、基础库版本、用户代码版本**三者共同决定。基础库由微信发布，可能内置在某个客户端版本里，也可能由用户端在打开小程序时按需下载；用户代码版本由开发者上传。三者对本次运行环境的约束关系大致如下：

```d2
direction: right

client: 客户端版本
base: 基础库版本
code: 用户代码版本

runtime: 本次运行环境 {
  class: group

  base_range: 可运行的基础库范围
  api: API 行为
  wx_subset: wx.* 能力子集
  component: 组件能力
  exparser: Exparser 行为
  assets: JS / WXML / WXSS
}

client -> runtime.base_range: 决定
base -> runtime.api: 决定
base -> runtime.wx_subset: 决定
base -> runtime.component: 决定
base -> runtime.exparser: 决定
code -> runtime.assets: 决定
```

同一个 `wx.request` 在不同基础库下行为可能有差别。`wx.canIUse` 就是用来在运行时检查当前环境是否支持某项能力。

### 为什么采用双线程模型

逻辑层和渲染层分线程运行，是小程序运行模型的关键设计。它通常服务于几个目标。

**运行时隔离**。用户的 JS 跑在独立的逻辑层沙箱里，不能直接读写 DOM、Cookie 和宿主环境，攻击面因此收窄。逻辑层和渲染层分线程运行，也让脚本执行和页面渲染的压力相互隔开。

**可控渲染**。WXML/WXSS 不直接暴露为普通 Web 页面，而是经过基础库和客户端渲染层统一处理。渲染层底层仍然依赖 WebView，但组件、样式能力和更新流程被平台约束，能减少 iOS 和 Android 浏览器内核差异带来的兼容问题。

**能力收口**。小程序不能直接调用系统能力，网络、文件、媒体、定位等宿主能力通常需要通过 `wx.*` 进入基础库，再由客户端侧承接实现。这样平台可以在统一入口做权限校验、能力开关和兼容处理；新增能力也需要随客户端和基础库发布，并受版本与权限条件约束。

**审核管控**。小程序的代码包、页面结构、能力调用都运行在平台定义的框架里，客户端和后台可以围绕这套框架做审核、拦截、灰度和下线。相比把一段网页完整交给浏览器执行，这种运行模型给平台留下了更明确的治理边界。

### 与 Web 运行环境的关键差异

把小程序环境当成普通 Web，是很常见的误解。两者的关键差异包括：

- 没有 `window` / `document`，但有 `wx` 全局。
- JS 引擎由客户端提供，不等同于当前 WebView 里的浏览器 JS 环境。
- WXML 模板在构建阶段被编译，WXSS 有样式作用域，原生组件由客户端直接渲染。
- 没有 Cookie，持久化数据使用小程序 Storage API。
- 没有跨域、没有 `<iframe>`，所有外链要走 `web-view` 组件，并且走单独的域名配置。
- 渲染层仍以 WebView 为主要承载，但模板、组件和数据更新流程受基础库约束，不等同于普通 Web 页面。

## 双线程模型

逻辑层和渲染层分开之后，跨线程通信是小程序最核心的运行机制。页面数据更新、用户事件和大部分 UI 变更都沿着这条链路走。

```d2
direction: down

native: Native {
  class: group
  direction: right

  bridge: 桥接层
  wxapi: wx.* API 实现
  nativecom: 原生组件容器
}

threads: 双线程 {
  class: group
  direction: right

  logic: 逻辑层 {
    class: group

    appjs: app.js
    pagejs: page.js
    component: 组件 js
    worker: Worker
  }

  view: 渲染层 {
    class: group

    exparser: Exparser 组件框架
    wxml: WXML 编译产物
    wxs_runtime: wxs 运行时
    webview: WebView
    native_component: 原生组件
  }
}

# 启动阶段
native -> threads.logic: 注入基础库 / 启动 JS
native -> threads.view: 加载模板 / 启动渲染

# 运行时通信
threads.logic -> threads.view: setData {
  style.stroke-width: 2
}
threads.view -> threads.logic: 事件 {
  style.stroke-width: 2
}

# 宿主能力
threads.logic -> native: wx.* 调用 / 回调

# 原生组件
threads.view -> native: 原生组件渲染
```

### 逻辑层

逻辑层负责执行用户 JS，包括根入口 `app.js`、页面 `page.js`、自定义组件 `js`，以及用 `new Worker()` 创建的 Worker。它管理的是 `Page` / `Component` 的 `data` 和生命周期，不能直接操作视图；影响 UI 的主要出口是 `setData`，外部输入则来自事件回调和生命周期回调。

`wxs` 不属于逻辑层，而是运行在渲染层里的小脚本。它访问不到 `Page` 的 `this.data`，只能通过 `data-*` 属性和事件与逻辑层交换信息，适合处理格式化、滑动联动这类高频但简单的 UI 逻辑。

### 渲染层

渲染层负责承载页面结构和样式，把 WXML/WXSS 编译产物更新到页面上。它的核心包括 WebView 渲染环境、Exparser 组件框架、样式系统，以及原生组件的承接机制。

Exparser 是小程序自研的组件框架，运行在渲染层。它按组件实例维护内部状态，并根据数据变化做增量更新。页面中的内置组件和自定义组件会被组织成组件树，父子关系、slot、事件冒泡都由 Exparser 调度。

WXML 经过编译后会进入渲染层的内部节点表示，后续 `setData` 触发更新时，Exparser 会按数据变化更新对应的组件节点。这说明两点：

- 逻辑层只持有 `data`；组件树和节点更新由渲染层维护。
- `setData` 触发的更新流程大致是“数据快照传输 → 渲染层增量更新 → Exparser 更新组件节点 → 必要时通知原生层更新组件”，跨线程传输依赖 Native Bridge，渲染层内部更新不等同于桥接调用。

原生组件（`map`、`video`、`canvas` 等）由客户端侧特殊承载，不完全等同于普通 WXML 节点。它们通常能调用更贴近系统能力的渲染路径，但也会带来层级和覆盖关系上的特殊规则；旧版本里常见“原生组件层级最高”的限制，新版本则需要结合同层渲染、`cover-view` 等能力判断。

### 通信链路

通信链路按方向可以分为四类。

```text
逻辑层 -> 渲染层: setData
渲染层 -> 逻辑层: 用户事件 / 组件事件 / 滚动回调
逻辑层 -> Native: wx.* API 调用
Native -> 逻辑层: API 回调 / 事件通知
```

`setData` 不是“把数据同步过去”，而是把本次变更传给渲染层，让渲染层按变更更新组件节点。底层通道随客户端和基础库版本变化，业务侧只需要关注数据体积、调用频率和受影响的组件范围。

`bindtap`、`bindinput`、`catchtouchmove`、自定义事件，都会把事件对象整理后发回逻辑层。组件上声明的 `methods` 接收到的就是这些事件对象。

`wx.*` API 则由逻辑层发起，经过基础库和客户端侧承接，再通过回调、Promise 或事件把结果送回逻辑层。网络、文件、媒体、定位等宿主能力都属于这一类调用。

跨层通信通常涉及数据整理、跨线程消息和调度开销。这一代价在 `setData` 上尤其明显，下一节展开。

## setData 性能

`setData` 是小程序性能优化里最常碰到的环节。一个“看起来很快”的赋值，背后要经过逻辑层更新、数据整理、跨线程消息、渲染层写入、Exparser 增量更新，必要时还会通知原生层更新组件。

```d2
direction: right

call: 调用 setData(data)
merge: 更新 this.data
serialize: 数据整理
bridge: 跨线程消息
write: 写入渲染层数据池
diff: Exparser 增量更新
patch: 更新组件节点
native: 通知原生层更新

call -> merge -> serialize -> bridge -> write -> diff -> patch -> native
```

`setData` 的语义是把“本次变更的数据”传给渲染层，渲染层按这份新数据更新对应的组件节点。`setData` 的回调表示这次数据更新流程已经完成，但不要把它简单等同于“像素已经稳定绘制到屏幕”，后续布局、图片解码或原生组件更新仍可能继续发生。

### 性能瓶颈分布

`setData` 的耗时分散在整条流水线上。

```d2
direction: right

logic: 逻辑层 {
  class: group

  A: 数据整理
}

bridge_layer: 跨线程 {
  class: group

  B: 消息调度
  C: 消息体传输
}

view: 渲染层 {
  class: group

  D: 写入数据池
  E: 组件节点更新
  F: 原生层更新
}

logic.A -> bridge_layer.B -> bridge_layer.C -> view.D -> view.E -> view.F
```

**逻辑层数据整理**：数据体积和对象深度都会增加开销，循环引用则可能导致传输失败。`setData({ a: { b: { c: 1 } } })` 的代价通常比 `setData({ 'a.b.c': 1 })` 高，因为前者要携带更大的对象结构。

**跨线程消息**：开销主要受数据体积和调用频率影响，具体表现会随客户端和基础库版本变化。能合并的状态变更尽量一次下发，避免每次小更新都单独产生一次通信成本。

**渲染层更新**：组件树深度、被影响的组件数量。`wx:for` 嵌套深、组件粒度过细都会放大更新成本。

**原生层更新**：实际绘制成本。触发布局、动画、图片解码都会在这里发生。

### 路径写法

`setData` 支持路径写法，只更新目标字段对应的子树，不动其它字段。

```js
this.setData({ 'user.name': 'Tom' })
this.setData({ 'list[2].title': 'New Title' })
```

路径写法会把变更范围收敛到具体字段。最终跨线程消息只需要表达“`user.name` 这一个字段变了”，数据体积更小，渲染层需要检查的范围也更小。

如果用对象写法传整棵子树：

```js
this.setData({ user: { name: 'Tom', age: this.data.user.age } })
```

跨线程消息里就要带整个 `user` 对象，渲染层收到后也需要按这个对象重新更新相关节点。表面上看起来一样，实际成本可能差很多。

### 合并多次 setData

循环里逐项 `setData` 是最常见的反模式。

```js
list.forEach((item, index) => {
  this.setData({ [`list[${index}].done`]: true })
})
```

100 项就有 100 次跨线程消息。改成一次合并：

```js
const patch = {}
list.forEach((item, index) => {
  patch[`list[${index}].done`] = true
})
this.setData(patch)
```

一次 `setData` 落地，只产生一次跨线程消息，渲染层再按这些路径更新对应列表项。

### 行为约束

使用 `setData` 时有几个边界要注意。

- 单次 `setData` 数据**建议不超过 1MB**，数据过大会显著增加通信和渲染压力。
- 频繁调用 `setData` 会带来多次跨线程通信和调度开销，合并边界最好在业务代码中控制。
- `setData` 回调只能说明本次数据更新流程完成，不代表屏幕像素已经稳定。需要等待后续渲染时，应结合基础库能力选择 `wx.nextTick` 或其它调度方式。
- `setData` **不要传 `Function`、循环引用、`Date` 等不适合序列化的数据**。传入前先整理成可序列化的普通对象，会更稳。

### 设计原则

`setData` 优化的核心不是某一处技巧，而是三条原则。

**能合并就合并**。同一帧内的多次状态变更合并成一次 `setData`。

**能不传就不传**。只传真正变化的字段，不传整张表、整棵树、整个 `this.data`。

**能不在主流程就不在主流程**。滚动、动画、手势这类高频更新，优先用 WXS 处理渲染层内的简单计算，或按基础库能力选择合适的帧调度方式。

## 小程序启动

启动阶段会把前面讲的运行环境和双线程模型串起来：客户端准备资源，初始化逻辑层和渲染层，再完成首屏渲染。

```d2
direction: right

start: 用户点击入口
init: 客户端拉起小程序
pkg: 资源准备
inject: 注入基础库
logic_init: 逻辑层初始化
view_init: 渲染层初始化
page_load: 首屏 Page.onLoad
fetch: 首屏业务请求
setdata: 首屏 setData
patch: 渲染层 patch
ready: 首屏可见

start -> init -> pkg -> inject
inject -> logic_init
inject -> view_init
logic_init -> page_load
view_init -> page_load
page_load -> fetch -> setdata -> patch -> ready
```

### 资源准备

点击入口后，客户端会做几件事：

- 校验小程序包：检查本地缓存、版本、签名。
- 准备用户态：解析启动参数 `scene`、`path`、`query`，确定要打开哪个页面。
- 准备运行环境：检查基础库版本，准备逻辑层 JS 上下文和首屏 WebView。

这一段对应用户点击入口后、页面开始呈现前的等待时间。资源已经缓存时，主要开销在校验和解压；首次打开或缓存失效时，还要叠加下载耗时。

### 逻辑层初始化

逻辑层初始化是注入式的。客户端把基础库的 JS 注入到逻辑层 JS 上下文里，然后执行用户的 `app.js`，完成 `App({ ... })` 注册。随后框架触发 `onLaunch`、`onShow` 等生命周期。

`onLaunch` 是整个小程序的“启动钩子”，通常用来读取本地存储、发起首屏数据请求、登录态校验。它里面的同步代码会占用逻辑层启动阶段；异步任务的返回值不会自动阻塞页面流程，如果首屏依赖这些结果，需要业务自己处理加载态和等待关系。

```js
App({
  onLaunch(options) {
    const sys = wx.getSystemInfoSync()
    this.globalData.system = sys

    login().then((user) => {
      this.globalData.user = user
    })
  },
})
```

### 渲染层初始化

渲染层通常会和逻辑层并行准备。首屏页面的 WebView 被创建后，WXML 编译产物、WXSS 和自定义组件模板会被加载，页面和组件实例也会随之建立。页面定义本身由 `Page({ ... })` 注册，`onLoad`、`onShow`、`onReady` 则是在后续页面生命周期里由框架触发。

首屏数据更新需要等逻辑层和渲染层都具备处理条件后，才会真正落到渲染层上。`onReady` 表示页面首次渲染完成，但不等于所有异步数据、图片或原生组件都已经稳定展示。

### 冷启动 / 热启动 / 前后台

启动耗时通常分为冷启动和热启动，再结合前后台切换看生命周期变化。

```d2
direction: right

cold: 冷启动 {
  class: group

  A: 客户端拉起
  B: 校验包
  C: 注入基础库
  D: 启动逻辑层
  E: 启动渲染层
  F: 首屏渲染
}

hot: 热启动 {
  class: group

  G: 前后台切换
  H: 复用逻辑层
  I: 恢复页面状态
}

cold.A -> cold.B -> cold.C
cold.C -> cold.D
cold.C -> cold.E
cold.D -> cold.F
cold.E -> cold.F
hot.G -> hot.H -> hot.I
```

冷启动是“从零开始”的路径，逻辑层、渲染层和运行时环境都需要重新准备。热启动通常发生在小程序从后台切回前台时，客户端会尽量复用已有运行状态，但是否保留页面和渲染资源仍取决于内存、页面栈和客户端策略。

`onHide` / `onShow` 是前后台切换的钩子，它们和冷启动/热启动不是同一组概念。逻辑层被回收后再次进入，会重新走冷启动流程；如果逻辑层仍保留，通常只触发 `onShow`，不会再次触发 `onLaunch`。

小程序页面栈有层数上限，常见约束是最多保留 10 层页面。超过这个数时，需要用重定向、返回或页面拆分来控制栈深；至于页面和 WebView 资源是否被回收，还会受客户端实现和内存状态影响。

### 启动耗时拆分

启动耗时大致可以拆成几段看：

```text
资源加载
  -> JS 注入
  -> App.onLaunch 执行
  -> 首屏 Page.onLoad
  -> 首屏 setData 落地
  -> 首次渲染
```

平台性能指标可以用 `wx.getPerformance` 观察，业务关键阶段则需要自己打点；遇到复杂问题，再结合开发者工具 Trace 看完整链路。

```js
const performance = wx.getPerformance()
const observer = performance.createObserver((res) => {
  res.getEntries().forEach((e) => {
    console.log(e.name, e.entryType, e.duration)
  })
})
observer.observe({ entryTypes: ['render', 'script', 'navigation'] })
```

## 工程实践

工程实践不是另一套话题，而是把运行环境、双线程模型和 `setData` 成本转成日常项目里的取舍：项目怎么组织、包怎么拆、发布怎么管控、问题怎么监控。

```d2
direction: right

P1: 项目结构 {
  class: group

  A: app.js / app.json / app.wxss
  B: pages / components / utils
}

P2: 构建与发布 {
  class: group

  C: 开发者工具 / CI
  D: 主包 / 分包
  E: 审核 / 灰度 / 回滚
}

P3: 监控与诊断 {
  class: group

  F: 体验评分 audits
  G: 线上监控
  H: 开发者工具 Trace
}

P1 -> P2: 进入构建发布
P2 -> P3: 发布后监控
P3 -> P1: 反馈优化
```

### 项目结构

小程序的代码组织以 `app.js`、`app.json`、`app.wxss` 为入口。每个页面通常是一个文件夹，按需包含 `.wxml`、`.wxss`、`.js`、`.json` 文件；自定义组件也采用类似的文件组织方式。

业务目录按团队约定拆分即可，例如 `utils/` 放纯函数，`services/` 放跨页面服务，`images/` 放静态资源。核心原则是“按变更频率拆”：经常一起改的放一起，经常独立改的拆开。

自定义组件的拆分粒度会影响 `setData` 的更新范围。组件粒度越细，单次更新影响的组件树可能越小，但跨组件通信和状态同步也会变多。一个粗略的判断是：首屏关键路径按渲染和更新成本拆，非关键路径按业务聚合。

### 分包与预下载

小程序包大小有上限，主包体积过大时必须拆。即使没有超限，也可以为了首屏速度和业务隔离主动分包。常见判断维度有三个。

```d2
direction: down

size: 主包超限? {
  shape: diamond
  class: decision
}

first: 首屏依赖是否过多? {
  shape: diamond
  class: decision
}

isolated: 是否需要独立启动? {
  shape: diamond
  class: decision
}

defer: 拆普通分包
independent: 拆独立分包
keep: 保持主包

size -> defer: 是
size -> first: 否
first -> defer: 是
first -> isolated: 否
isolated -> independent: 是
isolated -> keep: 否
```

主包超限是最直接的理由；首屏不需要的页面、组件和静态资源，也适合下沉到分包。`app.json` 里通过 `subpackages` 字段声明分包：

```json
{
  "pages": ["pages/index/index"],
  "subpackages": [
    { "root": "packageA", "pages": ["pages/list/index"] },
    { "root": "packageB", "pages": ["pages/detail/index"] }
  ],
  "preloadRule": {
    "pages/index/index": { "network": "all", "packages": ["packageA"] }
  }
}
```

`preloadRule` 用来声明分包预下载规则：进入某个页面时，提前下载后续可能用到的分包。它可以减少用户进入分包页面时的等待时间，但预下载范围要控制，避免反过来增加首屏网络和资源压力。

独立分包是一种特殊的分包，它**不依赖主包就能独立运行**。活动页、临时入口页、和主流程耦合较低的页面适合用独立分包。代价是独立分包不能引用主包里的资源和代码，公共能力需要放到独立分包自身或公共分包里。

### 构建与发布

构建方面，微信开发者工具是默认入口；工程化项目通常会把构建、预览、上传放到 CI 里：

- 用 `miniprogram-ci` 在 CI 中做上传、预览、构建产物校验。
- 用 Vite / Webpack / Rspack 做自定义构建，把 TypeScript、SCSS、环境变量等编译成小程序可运行的代码。
- 使用 npm 依赖时，需要经过小程序的 npm 构建流程，生成可被小程序加载的依赖产物。

`project.config.json` 控制开发者工具和构建相关配置，`sitemap.json` 控制页面是否允许被微信索引。发布流程通常是上传代码、提交审核、发布版本；灰度可以通过“分阶段发布”逐步放量，回滚则回到上一个已发布版本，不影响正在开发或审核中的新版本。

### 跨端开发

跨端框架（Taro、uni-app、Remax 等）的设计目标都是“用一套代码写多端”。在小程序侧，它们的实现思路大致是：

- 编译时：把框架组件、模板和样式转换成小程序能识别的 WXML/WXSS/JS。
- 运行时：在框架组件树和小程序页面模型之间做适配，把状态变化、事件和生命周期转换成小程序的数据更新与页面更新。
- 差异适配：通过编译时转换和运行时封装，提供统一的 `request` / `storage` 等 API。

跨端框架的**优势是开发效率**，但在小程序侧，关键性能问题仍会落到包体积、组件映射、`setData` 频率和渲染层更新上。把基础原理搞清楚，跨端框架用起来更踏实。

### 体验评分

“体验评分”是微信开发者工具提供的质量检查能力，会从几个维度给出提示，适合在提测和发布前做一次集中排查：

- **性能**：`setData` 体积、启动耗时、长任务
- **体验**：布局抖动、点击区域、字号可读性
- **最佳实践**：基础库版本、资源体积、错误处理

它更适合当作发布前的辅助检查项，用来尽早发现明显问题；最终还是要结合真机体验、性能面板和线上监控一起判断。

### 监控与诊断

线上监控的常见组合：

```js fold
/** 初始化实时日志管理器。 */
const logger = wx.getRealtimeLogManager()

/** 全局错误兜底。 */
wx.onError((err) => {
  logger.error('onError', err)
})

App({
  onError(err) {
    logger.error('App.onError', err)
  },
})

/** 业务采样上报。 */
const performance = wx.getPerformance()
const observer = performance.createObserver((res) => {
  res.getEntries().forEach((e) => {
    if (e.duration > 100) {
      logger.warn('perf', e.name, e.duration)
    }
  })
})
observer.observe({ entryTypes: ['render', 'script'] })
```

设计原则：**异步、批量、采样、离线缓存**。上报本身不要阻塞主流程；网络请求尽量合并；采样要按用户、设备和场景控制；弱网下要支持本地暂存与补发。

调试方面，开发者工具的 Network、Storage、WXML、真机调试、Trace 是基础工具。线上排查通常还要结合业务日志、实时日志和受控的真机调试手段；`wx.setEnableDebug` 只适合临时排查，不应在正式线上环境长期开启。

## 踩坑与优化

### 启动与首屏

**常见瓶颈**

- `onLaunch` 内的同步阻塞（`wx.getStorageSync`、复杂计算）会推迟逻辑层初始化；把首屏依赖的数据都放在这里等待，也会拖慢首屏业务渲染。
- 首屏依赖的非首屏资源（图片、字体、二方包）会拖慢渲染层初始化。
- 首屏 `setData` 数据量过大会让“首屏可见”被推迟。
- 分包没有使用预下载会让用户进入分包页面时再次等一次冷启动。

**优化**

- 把 `onLaunch` 里的同步逻辑改成异步：能 `await` 就 `await`，能用 Promise 包装就用 Promise。
- 首屏只依赖首屏资源：非首屏图片用 `lazy-load`，非首屏组件动态引入。
- 用 `wx.getStorage` 替代 `wx.getStorageSync`；只在确实需要阻塞首屏的地方用同步 API。
- 给可能进入的分包配置 `preloadRule`，让用户点入口时包已经下载完。
- 真正不依赖主包的业务用独立分包，启动时不必等主包初始化。

### 双线程与 setData

**常见瓶颈**

- `setData` 里传循环引用、`Function`、`Date`（旧基础库下表现不稳）。
- 循环里逐项 `setData` 会让跨线程消息队列拥堵。
- 滚动/动画中持续 `setData` 会让渲染层没有时间做 patch。
- 大列表整张 `setData` 让 diff 范围爆炸。
- 把 `setData` 回调当成“绘制完成”会写出错误的下游逻辑。

**优化**

- 路径写法优于对象写法：只更新目标字段对应的子树。
- 合并下发优于逐项下发：循环里逐项 `setData` 改成一次 patch。
- 大列表分页：只 `setData` 当前可视区域附近的项，用 `recycle-view` 做节点复用。
- 高频更新优先用 WXS 处理渲染层内的简单计算，减少主动 `setData`。
- 需要帧调度时，按基础库能力选择 `wx.nextTick`、`requestAnimationFrame` 等可用工具，避免和渲染节奏抢资源。
- 给 `setData` 回调加采样输出，在性能面板里看实际耗时分布。

### 基础库与跨端

**常见瓶颈**

- 重要功能靠“试一下能不能调用”判断兼容性。
- 用 `@vant/weapp`、`tdesign-miniprogram` 时未确认最低基础库版本。
- 关键路径使用只在最新基础库才支持的语法糖。
- 跨端框架未配置自定义构建，留下大量死代码。
- `Worker` 未被用来处理纯计算。

**优化**

- 入口处用 `wx.getSystemInfoSync()` / `wx.getAppBaseInfo()` 拿到客户端和基础库信息，按需降级。
- 重要功能用 `wx.canIUse` 显式检查。
- 用 `Worker` 处理纯计算，把结果通过 `postMessage` 一次性回流。

### 监控与发布

**常见瓶颈**

- 主包超限未拆、预下载规则粒度过粗。
- 上报未做采样，监控成本失控。
- 错误只打 log 不上报，线上问题无法追溯。

**优化**

- 定期用 `audits` 自检，把扫描纳入提交流程。
- 监控按用户/设备/页面采样，重要页面全量。
- 错误监控覆盖 `wx.onError`、`App.onError`、`wx.onUnhandledRejection` 等入口；页面级错误可以在业务封装里统一捕获并上报。

### 内存与诊断

- `setInterval` / `setTimeout` 在 `onUnload` 里清理。
- 大图片、长列表、缓存按需加载、及时释放。
- 全局状态收口到 `App` 的 `globalData` 或专门的 store，避免重复大对象引用。

### 体验指标

- 首屏渲染时间：可参考 Web 的 FP/FCP 思路，用 `wx.getPerformance` 提供的渲染相关指标观察。
- 可交互时间：可参考 Web 的 TTI 思路，用首屏 `onReady` 和关键交互可用时间估算。
- 滑动帧率：按基础库能力选择帧回调或开发者工具 Trace 观察。
- 长任务数：用开发者工具 Trace、性能面板和必要的调度打点观察线程繁忙程度。

## 总结

- **运行环境**：Native + 逻辑层 + 渲染层 + 基础库四件套共同支撑小程序的运行。
- **双线程模型**：页面数据更新、用户事件和宿主能力调用会经过跨线程通信，序列化与调度是这条链路的固有代价。
- **小程序启动**：从用户点击到首屏可见分冷启动、热启动、前后台三套路径，`onLaunch` 里的同步逻辑和首屏依赖会影响启动体验。
- **setData 性能**：`setData` 的耗时由数据体积、调用频率和组件更新范围共同决定。
- **工程实践**：分包、构建、监控、调试把前面原理变成可执行的项目实践。

把链路看清楚，每一处取舍才有依据。
