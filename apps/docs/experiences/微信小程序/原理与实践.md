# 微信小程序原理与实践

小程序在用户视角看起来像一个轻量 App，在工程视角看起来像一个跑在客户端里的 WebView 容器。但它的运行模型既不是传统 Web，也不是 React Native 那一类原生组件树，而是自成一类：把 JS 逻辑和 UI 渲染拆到两条独立的线程里运行，通过客户端原生层通信。

## 运行环境

小程序运行环境由四部分组成：**Native、逻辑层、渲染层、基础库**。下面先把每一部分讲清楚。

```text
Native
  -> 注入基础库
  -> 创建逻辑层 JSCore / V8
  -> 创建渲染层 WebView / Native
  -> 桥接两条线程
  -> 暴露 wx.* API
  -> 装载用户代码
```

Native 是微信客户端提供宿主能力的那一层。逻辑层是跑用户 JS 的引擎，iOS 上是 JSCore，Android 上是 V8。渲染层是 WXML/WXSS/原生组件真正绘制的地方，承载在 WebView 上，少数原生组件（`map`、`video`、`canvas` 等）由客户端原生层直接渲染。基础库（`wx`）是微信自己实现的一套运行时，一部分以 JS 代码形式注入到逻辑层，一部分以原生代码形式驻留在客户端里。

这四部分都不归用户代码控制。开发者写下的 JS 只会跑在逻辑层；样式和模板经过编译后送进渲染层；任何越界操作（DOM 操作、动态执行代码）都会失败。

### 基础库与版本矩阵

小程序的可用能力，由**客户端版本、基础库版本、用户代码版本**三者共同决定。基础库由微信发布，可能内置在某个客户端版本里，也可能由用户端在打开小程序时按需下载；用户代码版本由开发者上传。每次运行时，客户端会按这张表去匹配：

```text
客户端版本
  -> 决定可用的最高基础库版本
  -> 决定可用的 wx.* 子集
基础库版本
  -> 决定 API 行为、组件能力、Exparser 行为
用户代码版本
  -> 决定本次运行使用的 JS、WXML、WXSS
```

同一个 `wx.request` 在不同基础库下行为可能有差别。`wx.canIUse` 就是用来在运行时检查当前环境是否支持某项能力。

```js
if (wx.canIUse('showModal.cancel.color')) {
  wx.showModal({
    title: '提示',
    content: '需要升级微信才能使用本功能',
    cancelColor: '#ff0000',
  })
}
```

### 为什么采用双线程模型

小程序最显眼的特征是逻辑层和渲染层分线程。常见动机有四点。

**安全隔离**。用户的 JS 跑在沙箱里，无法直接拿到 `document`、无法直接读 cookie，也无法直接操作真实 DOM。这一层隔离让攻击面天然收窄，恶意脚本只能通过 `wx.*` 触达能力。

**可控渲染**。所有 UI 都由客户端原生层调度，不依赖具体浏览器内核。同一份 WXML/WXSS 在 iOS 和 Android 上行为一致，规避了不同浏览器内核之间的兼容问题。

**抗主线程卡顿**。逻辑层和渲染层互不阻塞。逻辑层里出现长任务、抛异常、卡死，都不会让渲染层跟着卡死；反过来，渲染层重新计算布局时，逻辑层依然可以继续处理用户事件。

**能力收口**。所有 `wx.*` API 都走 Native Bridge，方便做权限校验、计费、合规审计。平台要新增一个能力，只需要在 Native Bridge 里加一个方法，所有小程序立刻可用。

### 与 Web 运行环境的关键差异

把小程序环境当 Web 用，是新手最常见的误解。差异摆出来：

- 没有 `window` / `document`，但有 `wx` 全局。
- JS 引擎是 JSCore（iOS）/ V8（Android），不是浏览器自带的。
- WXML 模板在构建阶段被编译，WXSS 经过样式隔离，原生组件由客户端直接渲染。
- 没有 Cookie，使用 `wx.setStorageSync` / `wx.getStorageSync` 这类 Storage API。
- 没有跨域、没有 `<iframe>`，所有外链要走 `web-view` 组件，并且走单独的域名配置。
- 渲染由原生层调度，不走浏览器主线程的 layout / paint / composite 流程。

这四部分怎么协同，关键看逻辑层和渲染层的分工。

## 双线程模型

逻辑层和渲染层分开之后，跨线程通信是小程序最核心的运行机制。所有数据流、所有事件、所有 UI 更新都沿着这条链路走。

```d2
direction: down

logic: 逻辑层 {
  class: group

  appjs: app.js
  pagejs: page.js
  component: 组件 js
  wxs: wxs 脚本
  worker: Worker
}

view: 渲染层 {
  class: group

  exparser: Exparser 组件框架
  wxml: WXML 编译产物
  wxs_runtime: wxs 运行时
  webview: WebView
  native_component: 原生组件
}

native: Native {
  class: group

  bridge: 桥接层
  wxapi: wx.* API 实现
  nativecom: 原生组件容器
}

# 启动阶段：Native 注入两条线程
native.bridge -> logic.appjs: 注入
native.bridge -> view.wxml: 加载
native.bridge -> view.exparser: 启动

# 运行时核心通信：逻辑层 ↔ 渲染层
logic.appjs -> view.exparser: setData {
  style.stroke-width: 2
}
view.exparser -> logic.appjs: 事件 {
  style.stroke-width: 2
}

# 能力调用：逻辑层 ↔ Native
logic.appjs -> native.wxapi: 调用 API {
  style.stroke-width: 2
}
native.wxapi -> logic.appjs: 回调

# 原生组件挂载到原生容器
view.native_component -> native.nativecom: 渲染
```

### 逻辑层

逻辑层跑用户的 JS：根入口 `app.js`、每个页面的 `page.js`、自定义组件的 `js`、用 `new Worker()` 创建的 Worker，以及 `wxs` 标签中通过 `<wxs module="...">` 注入的小脚本。

逻辑层只有数据，没有视图。`Page` / `Component` 的 `data` 就是它管理的状态；`setData` 是它能影响 UI 的唯一方式；事件回调、生命周期回调是它接收外部输入的入口。

`wxs` 是一种特殊的“逻辑层脚本”，但它运行在渲染层，访问不到 `Page` 的 `this.data`，只通过 `data-*` 属性和事件与逻辑层通信。它的存在让一些高频、简单的 UI 行为（滑动联动、格式化）不必走 `setData` 回流。

### 渲染层

渲染层负责把 WXML/WXSS 翻译成真实像素，由 Exparser 组件框架、模板编译产物、样式、原生组件容器组成。

Exparser 是小程序自研的组件框架，运行在渲染层。它不是 React/Vue 那一类 vdom diff 思路，而是按组件实例维护状态，按数据驱动 patch。每个自定义组件对应一个 Exparser 节点，组件之间的父子关系、slot、事件冒泡都由 Exparser 调度。

WXML 经过编译后会生成一份“虚拟节点树”，后续 `setData` 触发更新时，Exparser 会做差异对比再 patch 到真实组件树。理解 Exparser 有两个直接收益：

- 渲染层确实有 vdom，但 vdom 只在渲染层；逻辑层只有 `data`。
- `setData` 触发的更新流程是“数据快照传输 → 渲染层 vdom diff → Exparser patch → 原生层更新组件”，每一步都依赖 Native Bridge。

原生组件（`map`、`video`、`canvas` 等）不走 WebView 渲染。它们由客户端原生层直接绘制，渲染层在 WebView 里只保留一个占位节点。这种设计让原生组件性能更好，但反过来也带来一个限制：原生组件的层级最高，无法被普通 WXML 节点盖住。

### 通信链路

四条通信路径构成完整的运行模型。

```text
逻辑层 -> 渲染层: setData / 事件总线
渲染层 -> 逻辑层: 用户事件 / 生命周期 / 滚动回调
逻辑层 -> Native: wx.* API 调用
Native -> 逻辑层: 异步回调 (success / fail / complete)
```

`setData` 是逻辑层到渲染层的通信。它不是“把数据同步过去”，而是“把本次变更的数据传过去，让渲染层在 vdom 树上做 patch”。底层通道在不同客户端实现不同：iOS 走 `evaluateJavascript`，Android 早期走 JSBridge，新版本逐步迁移到 JSI。性能上 JSI 路径显著优于 JSBridge，因为 JSI 可以直接共享内存而无需 JSON 序列化。

事件是从渲染层到逻辑层的通信。`bindtap`、`bindinput`、`catchtouchmove`、自定义事件，本质都是渲染层把事件对象序列化后经由 Native Bridge 发回逻辑层。组件上声明的 `methods` 接收到的就是这些事件对象。

`wx.*` API 走的是另一条路：逻辑层调用 → Native 原生层执行 → 结果通过异步回调送回逻辑层。所有 IO（网络、文件、媒体、定位）都走这一类调用。

跨线程调用都涉及序列化、跨线程消息、调度开销。这一代价在 `setData` 上尤其显眼，下一节展开。

## 小程序启动

启动是“运行环境”和“双线程模型”这两条主线落到用户感知上的第一段。

```d2
direction: down

start: 用户点击入口
init: 客户端拉起小程序
pkg: 资源准备
inject: 注入基础库
logic_init: 逻辑层初始化
view_init: 渲染层初始化
page_load: 首屏 Page.onLoad
fetch: 首屏业务请求
setdata: 首屏 setData
patch: 渲染层 patch
ready: 首屏可见 {
  class: ok
}

start -> init -> pkg -> inject
inject -> logic_init
inject -> view_init
logic_init -> page_load
view_init -> page_load
page_load -> fetch -> setdata -> patch -> ready
```

### 资源准备

点击入口后，客户端会做几件事：

- 校验小程序包：检查本地缓存、版本、签名。
- 准备用户态：解析启动参数 `scene`、`path`、`query`，确定要打开哪个页面。
- 准备运行环境：检查基础库版本，准备 JSCore/V8 上下文和首屏 WebView。

这一段对用户来说是“按下后到看到白屏”的时间。资源如果已经下载到本地，开销主要在校验和解压；如果是首次打开，还要走下载。

### 逻辑层初始化

逻辑层初始化是注入式的。客户端把基础库的 JS 注入到 JSCore/V8 上下文里，然后执行用户的 `app.js`。`App({ onLaunch, onShow, onHide })` 在这里被调用。

`onLaunch` 是整个小程序的“启动钩子”，通常用来读取本地存储、发起首屏数据请求、登录态校验。**它阻塞渲染层开始首屏渲染**，只要 `onLaunch` 没结束，渲染层就算准备好也不会进入首屏。

```js
App({
  async onLaunch(options) {
    const sys = wx.getSystemInfoSync()
    this.globalData.system = sys
    const user = await login()
    this.globalData.user = user
  },
})
```

### 渲染层初始化

渲染层在逻辑层启动的同时开始初始化。首屏页面的 WebView 被创建，WXML 编译产物、WXSS、自定义组件模板被加载，原生组件占位节点被插入。然后 `Page({ onLoad, onShow, onReady })` 触发，组件实例被创建。

渲染层和逻辑层的初始化**是并行的**，但二者都准备好之后，首屏 `setData` 才会真正落到渲染层上。`onReady` 表示首屏已经渲染完成，是“首屏可见”的稳定信号。

### 冷启动 / 热启动 / 前后台

启动耗时要分冷启动、热启动和前后台切换三种情况看。

```d2
direction: right

cold: 冷启动 {
  class: fail

  A: 客户端拉起
  B: 校验包
  C: 注入基础库
  D: 启动逻辑层
  E: 启动渲染层
  F: 首屏渲染
}

hot: 热启动 {
  class: ok

  G: 前后台切换
  H: 复用逻辑层
  I: 必要时重建渲染层
}

cold.A -> cold.B -> cold.C -> cold.D
cold.D -> cold.E -> cold.F
hot.G -> hot.H -> hot.I
```

冷启动是“从零开始”的路径，所有线程、容器、运行时都要重新创建。热启动是“用户从后台切回”的路径，逻辑层通常被保留，渲染层如果页面数没有超过上限也会被保留。

`onHide` / `onShow` 是前后台切换的钩子，它们和冷启动/热启动不是同一组事件。逻辑层被杀掉再恢复时，会走一次完整的冷启动；逻辑层保留但渲染层重建时，会触发 `onShow` 但不触发 `onLaunch`。

微信官方建议小程序的渲染层保留页面上限是 10 层。超过这个数时，最旧的页面 WebView 会被回收；用户从被回收的页面回到首页时需要重新创建 WebView。

### 启动耗时拆分

启动耗时大致可以拆成下面几段：

```text
资源加载
  -> JS 注入
  -> App.onLaunch 执行
  -> 首屏 Page.onLoad
  -> 首屏 setData 落地
  -> 首帧绘制
```

每一段都可以用 `wx.getPerformance` 单独打点。

```js
const performance = wx.getPerformance()
const entry = performance.createObserver((res) => {
  res.getEntries().forEach((e) => {
    console.log(e.name, e.entryType, e.duration)
  })
})
entry.observe({ entryTypes: ['render', 'script', 'navigation'] })
```

## setData 性能

`setData` 是小程序性能话题的“主战场”。理解它，需要把 Native Bridge 在 `setData` 这一步展开：一个“看起来很快”的赋值，要经过逻辑层合并、序列化、跨线程消息、渲染层写入、Exparser diff、原生层 patch 全流程，每一步都在消耗时间。

```d2
direction: down

call: Page 调用 setData(data)
merge: 基础库合并 data 与旧值
serialize: JSON 序列化
bridge: 跨线程消息
write: 写入渲染层数据池
diff: Exparser vdom diff
patch: patch 真实组件树
native: 通知原生层更新
done: 完成 {
  class: ok
}

call -> merge -> serialize -> bridge -> write -> diff -> patch -> native -> done
```

`setData` 的语义是把“本次变更的数据”传给渲染层，渲染层按这份新数据和上一份旧数据做差异对比，得到 patch，最后更新到真实组件树。**`setData` 的回调函数在“数据已经到达渲染层”时触发**，不是“已经绘制到屏幕”，这两者的延迟可能不止一帧。

### 性能瓶颈分布

`setData` 的耗时分散在整条流水线上。

```d2
direction: right

logic: 逻辑层 {
  class: group

  A: 序列化
}

bridge_layer: 跨线程 {
  class: group

  B: 消息调度
  C: 消息体传输
}

view: 渲染层 {
  class: group

  D: 写入数据池
  E: vdom diff
  F: 原生层更新
}

logic.A -> bridge_layer.B -> bridge_layer.C -> view.D -> view.E -> view.F
```

**逻辑层序列化**：JSON 体积、对象深度、循环引用都会增加开销。`setData({ a: { b: { c: 1 } } })` 的代价比 `setData({ 'a.b.c': 1 })` 高，因为前者要序列化整条路径。

**跨线程消息**：体积 × 频率。具体数字会随客户端版本变化，但“频繁小 `setData` 比一次大 `setData` 更糟”是稳定的：每条消息都有调度开销，100 次 1KB 的 `setData` 比 1 次 100KB 的 `setData` 慢很多。

**渲染层 diff**：组件树深度、被影响的组件数量。`wx:for` 嵌套深、组件粒度过细都会放大 diff 成本。

**原生层更新**：实际绘制成本。触发布局、动画、图片解码都会在这里发生。

### 路径写法

`setData` 支持路径写法，只更新目标字段对应的子树，不动其他字段。

```js
this.setData({ 'user.name': 'Tom' })
this.setData({ 'list[2].title': 'New Title' })
```

这个写法背后的实现是：基础库在逻辑层把 `user.name` 这个路径取出，把 `user` 上一次的值拿出来，只把 `name` 字段替换掉，再合并回 `this.data`。最终跨线程消息里只包含“`user.name` 这一个字段变了”，体积小、diff 范围小。

如果用对象写法传整棵子树：

```js
this.setData({ user: { name: 'Tom', age: this.data.user.age } })
```

跨线程消息里就要带整个 `user` 对象，渲染层收到后要 diff 整个 `user` 子树。表面上看起来一样，实际上成本差距明显。

### 合并多次 setData

循环里逐项 `setData` 是最常见的反模式。

```js
list.forEach((item, index) => {
  this.setData({ [`list[${index}].done`]: true })
})
```

100 项就有 100 次跨线程消息。改成一次合并：

```js
const patch = {}
list.forEach((item, index) => {
  patch[`list[${index}].done`] = true
})
this.setData(patch)
```

一次 `setData` 落地，整张列表一次性 diff。

### 行为约束

官方对 `setData` 有几个明确的边界。

- 单次 `setData` 数据**建议不超过 1MB**。超过会被截断或直接报错。
- 一次设置过多的 `setData` 会被**节流**：基础库会把同一逻辑帧里的多次 `setData` 合并，下一帧再下发。节流粒度随客户端版本变化，业务代码不能依赖具体数值。
- `setData` 回调不是“绘制完成”。需要等“绘制到屏幕”的时机，用 `wx.nextTick` 或 `requestAnimationFrame` 这类渲染层调度器。
- `setData` **不能传 `Function`、不能传循环引用、不能传 `Date`（旧基础库下表现不稳）**。传值之前先 `JSON.parse(JSON.stringify(data))` 是一种简单粗暴但有效的“清洗”手段。

### 设计原则

`setData` 优化的核心不是某一处技巧，而是三条原则。

**能合并就合并**。同一帧内的多次状态变更合并成一次 `setData`。

**能不传就不传**。只传真正变化的字段，不传整张表、整棵树、整个 `this.data`。

**能不在主流程就不在主流程**。滚动、动画、手势这类高频更新，优先用 `wxs` 响应式（运行在渲染层），或用 `requestAnimationFrame` 把更新切到下一帧。

## 工程实践

工程实践是把前面所有原理落到日常项目里的部分。它不是另一套话题，而是“启动、setData、性能、监控”的工程落点。

```d2
direction: right

P1: 项目结构 {
  class: group

  A: app.js / app.json / app.wxss
  B: pages / components / utils
}

P2: 构建与发布 {
  class: group

  C: 开发者工具 / CI
  D: 主包 / 分包
  E: 审核 / 灰度 / 回滚
}

P3: 监控与诊断 {
  class: group

  F: 体验评分 audits
  G: 线上监控
  H: 实验室 Trace
}

P1.A -> P2.C
P1.B -> P2.D
P2.E -> P3.G
P3.F -> P3.G
P3.H -> P3.G
```

### 项目结构

小程序的代码组织以 `app.js / app.json / app.wxss` 为入口。每个页面是一个文件夹，里面包含 `.wxml` / `.wxss` / `.js` / `.json` 四个文件。自定义组件放在 `components/` 目录下，是一份独立的四件套。

按团队约定，`utils/` 放纯函数、`models/` 放数据请求和业务模型、`images/` 放静态资源、`services/` 放跨页面的服务层。原则是“按变更频率拆”：经常一起改的放一起，经常独立改的拆开。

自定义组件的拆分粒度直接关联 `setData` 性能。组件粒度越细，受影响的组件树越小，但跨组件通信和 `setData` 次数也会变多。一个粗略的判断是：首屏关键路径上的组件尽量细，非关键路径上的组件按业务聚合。

### 分包与预下载

小程序包大小有上限，主包体积过大时必须拆。是否分包、如何分包有三个判断维度。

```d2
direction: down

check: 主包超限? {
  shape: diamond
  class: decision
}

check2: 首屏只依赖核心? {
  shape: diamond
  class: decision
}

check3: 需要独立分包? {
  shape: diamond
  class: decision
}

defer: 拆普通分包
independent: 拆独立分包
keep: 保持主包

check -> check2: 否
check2 -> defer: 否
check2 -> check3: 是
check3 -> independent: 是
check3 -> keep: 否
check -> keep: 否
```

主包超限是最直接的理由。`app.json` 里通过 `subpackages` 字段声明分包：

```json
{
  "pages": ["pages/index/index"],
  "subpackages": [
    { "root": "packageA", "pages": ["pages/list/index"] },
    { "root": "packageB", "pages": ["pages/detail/index"] }
  ],
  "preloadRule": {
    "pages/index/index": { "network": "all", "packages": ["packageA"] }
  }
}
```

`preloadRule` 是“预下载规则”：进入某个页面时，提前下载指定的分包。它和“分包按需加载”配合，能显著减少用户进入分包页面的等待时间。

独立分包是一种特殊的分包，它**不依赖主包就能独立运行**。营销活动页、H5 替代品适合用独立分包。代价是独立分包不能引用主包的资源，启动时主包如果还没准备好，独立分包要先等。

### 构建与发布

构建方面，微信开发者工具是默认入口，但项目里更常见的做法是：

- 用 `miniprogram-ci` 在 CI 中做上传、预览、构建产物校验。
- 用 Vite / Webpack / Rspack 做自定义构建，把 npm 包、TypeScript、SCSS 等编译成小程序格式。
- 用 `miniprogram_npm` 让小程序原生支持 npm 依赖。

`project.config.json` 控制开发者工具行为，`sitemap.json` 控制是否允许微信搜索索引。小程序发布后，灰度通过“分阶段发布”实现：先给一定比例的用户，推全量通过审核后回滚也只影响已发布版本，不影响下一版。

### 跨端开发

跨端框架（Taro、uni-app、Remax、kbone、rax-pkg 等）的设计目标都是“用一套代码写多端”。在小程序侧，它们的实现思路大致是：

- 编译时：把 React / Vue 语法编译成 WXML/WXSS/JS。
- 运行时：让用户态以 `setData` 为唯一出口。
- 差异抹平：在编译时抹掉平台 API 差异，提供统一的 `request` / `storage` 包装。

跨端框架的**优势是开发效率**，但**在小程序侧所有优化最后都还是回到 `setData` 和渲染层 patch**。把基础原理搞清楚，跨端框架用起来更踏实。

### 体验评分

`audits` 面板（也叫“体验评分”）是开发者工具内置的体检工具。它会扫描当前项目，从性能、体验、最佳实践三个维度给出建议。

```text
性能: setData 体积、启动耗时、长任务数
体验: 布局抖动、可点击区域、字号对比
最佳实践: 基础库最低版本、依赖体积、错误处理
```

把 `audits` 接入提交流程，可以在每次发布前自动发现明显的性能问题。

### 监控与诊断

线上监控的常见组合：

```js
/** 初始化实时日志管理器。 */
const logger = wx.getRealtimeLogManager()
logger.setFilterMsg('realtime')

/** 全局错误兜底。 */
wx.onError((err) => {
  logger.error('onError', err)
})
App({
  onError(err) {
    logger.error('App.onError', err)
  },
})

/** 业务采样上报。 */
const performance = wx.getPerformance()
const observer = performance.createObserver((res) => {
  res.getEntries().forEach((e) => {
    if (e.duration > 100) {
      logger.warn('perf', e.name, e.duration)
    }
  })
})
observer.observe({ entryTypes: ['render', 'script'] })
```

设计原则：**异步、批量、采样、离线缓存**。上报本身要快（不阻塞主流程），要按队列合并（避免频繁 IO），要按用户/设备采样（避免数据爆炸），要支持离线（网络差时也能累积）。

调试方面，开发者工具的 Network、Storage、WXML、真机调试、Trace 是基础工具。线上问题还要靠真机 vConsole / `wx.setEnableDebug`（注意：线上环境不要开启 `setEnableDebug`，会暴露内部状态）。

## 踩坑与优化

### 启动与首屏

**常见瓶颈**

- `onLaunch` 内的同步阻塞（同步 `wx.getStorage`、同步登录、复杂计算）会推迟逻辑层初始化。
- 首屏依赖的非首屏资源（图片、字体、二方包）会拖慢渲染层初始化。
- 首屏 `setData` 数据量过大会让“首屏可见”被推迟。
- 分包没有使用预下载会让用户进入分包页面时再次等一次冷启动。

**优化**

- 把 `onLaunch` 里的同步逻辑改成异步：能 `await` 就 `await`，能用 Promise 包装就用 Promise。
- 首屏只依赖首屏资源：非首屏图片用 `lazy-load`，非首屏组件动态引入。
- 用 `wx.getStorage` 替代 `wx.getStorageSync`；只在确实需要阻塞首屏的地方用同步 API。
- 给可能进入的分包配置 `preloadRule`，让用户点入口时包已经下载完。
- 真正不依赖主包的业务用独立分包，启动时不必等主包初始化。

### 双线程与 setData

**常见瓶颈**

- `setData` 里传循环引用、`Function`、`Date`（旧基础库下表现不稳）。
- 循环里逐项 `setData` 会让跨线程消息队列拥堵。
- 滚动/动画中持续 `setData` 会让渲染层没有时间做 patch。
- 大列表整张 `setData` 让 diff 范围爆炸。
- 把 `setData` 回调当成“绘制完成”会写出错误的下游逻辑。

**优化**

- 路径写法优于对象写法：只更新目标字段对应的子树。
- 合并下发优于逐项下发：循环里逐项 `setData` 改成一次 patch。
- 大列表分页：只 `setData` 当前可视区域附近的项，用 `recycle-view` 做节点复用。
- 高频更新用 `wxs` 响应式或 `IntersectionObserver`，减少主动 `setData`。
- 用 `requestAnimationFrame` 把更新切到下一帧，避免和渲染节奏抢资源。
- 给 `setData` 回调加采样输出，在性能面板里看实际耗时分布。

### 基础库与跨端

**常见瓶颈**

- 重要功能靠“试一下能不能调用”判断兼容性。
- 用 `@vant/weapp`、`tdesign-miniprogram` 时未确认最低基础库版本。
- 关键路径使用只在最新基础库才支持的语法糖。
- 跨端框架未配置自定义构建，留下大量死代码。
- `Worker` 未被用来处理纯计算。

**优化**

- 入口处用 `wx.getSystemInfoSync()` / `wx.getAppBaseInfo()` 拿到客户端和基础库信息，按需降级。
- 重要功能用 `wx.canIUse` 显式检查。
- 用 `Worker` 处理纯计算，把结果通过 `postMessage` 一次性回流。

### 监控与发布

**常见瓶颈**

- 主包超限未拆、预下载规则粒度过粗。
- 上报未做采样，监控成本失控。
- 错误只打 log 不上报，线上问题无法追溯。

**优化**

- 定期用 `audits` 自检，把扫描纳入提交流程。
- 监控按用户/设备/页面采样，重要页面全量。
- 错误监控覆盖 `wx.onError`、`App.onError`、`Page.onError`、`wx.onUnhandledRejection` 四个入口。

### 内存与诊断

- `setInterval` / `setTimeout` 在 `onUnload` 里清理。
- 大图片、长列表、缓存按需加载、及时释放。
- 全局状态收口到 `App` 的 `globalData` 或专门的 store，避免重复大对象引用。

### 体验指标

- 首屏渲染时间：等价 Web 的 FP/FCP，用 `wx.getPerformance` 的 `render` 事件测量。
- 可交互时间：等价 Web 的 TTI，用首屏 `onReady` 时间估算。
- 滑动帧率：`requestAnimationFrame` 切帧统计。
- 长任务数：用 `setTimeout(fn, 0)` / `requestIdleCallback` 这类调度工具测量主线程繁忙程度。

## 总结

- **运行环境**：Native + 逻辑层 + 渲染层 + 基础库四件套共同支撑小程序的运行。
- **双线程模型**：所有数据流、事件和 UI 更新都走 Native Bridge，序列化与调度是这条链路的固有代价。
- **小程序启动**：从用户点击到首屏可见分冷启动、热启动、前后台三套路径，`onLaunch` 阻塞逻辑层初始化。
- **setData 性能**：Native Bridge 的耗时由体积、频率、diff 范围共同决定。
- **工程实践**：分包、构建、监控、调试把前面原理变成可执行的项目实践。

把链路看清楚，每一处取舍才有依据。
