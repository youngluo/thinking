# 重构的目标不是拆文件，而是缩小变化半径

在复杂业务中，重构往往不是因为某个函数已经无法阅读，而是因为一次小需求开始牵动越来越多的状态、组件和数据转换。

表单权限就是一个典型例子。它同时包含页面选择、PC 和移动端差异、页面入参、字段权限、操作权限、表达式配置和一致性校验。每个功能单独看都不算复杂，组合起来却会形成一张相互牵连的变化网络。

本文以 `packages/bpm/src/components/form-permission` 的提交历史为线索，观察它如何从功能集中、变化耦合的结构，逐步演进为按变化方向拆分职责的结构。

这里关注的不是某个提交是否完美，也不是简单比较重构前后的文件数量，而是回答一个更实际的问题。

> 重构的判断标准不是文件数量增加了多少，而是新增需求是否能够局部修改、局部验证，并且不会持续冲击核心组件。

## 从一次需求变更开始

表单权限页面至少要处理下面几类问题。

| 变化方向 | 典型问题 |
| --- | --- |
| 页面选择 | 当前应用有哪些页面，个性化页面是否可选 |
| 设备适配 | PC 页面和移动页面如何分别展示，PC 页面是否作为移动端 Web 视图 |
| 页面入参 | 页面有哪些入参，参数值如何映射到表达式 |
| 表单结构 | 页面 Schema 如何转换成实体字段和控件列表 |
| 字段权限 | 字段是否可见、可编辑、必填，状态表达式如何配置 |
| 操作权限 | 附件和重复表等操作如何配置 |
| 数据一致性 | PC 和移动端的权限设置是否需要联动和校验 |

这些问题的变化原因不同。页面树的接口调整，不应该天然影响字段权限表格；页面入参的加载条件，也不应该和权限状态的全选逻辑绑定在一起。

如果不同原因导致的变化最终都落到同一个组件和同一组状态上，修改成本就会随着功能增长不断叠加。重构要处理的正是这种变化耦合。

## 重构前，功能集中带来的变化耦合

`9fd136d37` 是一个合适的观察起点。这个提交将 `processTemplate` 和 `formPermission` 迁移到 `biz-bpm`，也带来了当时的初始实现。

当时的职责主要集中在三个文件中。

- `index.tsx` 负责组件状态、Schema 初始化、权限数据组装和保存结果。
- `authority.tsx` 同时负责权限表格展示、字段状态修改、全选逻辑和表达式配置。
- `analyze-page-schema.ts` 同时承担页面 Schema 解析、权限数据转换和保存数据生成。

从提交中的文件规模看，`analyze-page-schema.ts` 约 1800 行，`authority.tsx` 约 700 行，`index.tsx` 约 280 行。行数本身不能证明代码一定有问题，但可以帮助我们定位需要进一步观察的地方。

例如，早期的 `index.tsx` 会在同一个组件中完成控件列表初始化、权限数据合并、页签状态保存和全选操作。

```tsx fold title="packages/bpm/src/components/form-permission/index.tsx @ 9fd136d37"
// 根据页面 Schema 生成控件列表，再叠加已有权限数据
const getTableData = async (authDataList: any[]) => {
  if (!schemaInfoList?.length) {
    setTabInfo({});
    return;
  }

  const map: Record<string, any[]> = {};
  for (const item of schemaInfoList) {
    let list: any[] = [];
    if (item.schema) {
      const schema = JSON.parse(item.schema);
      list = await getDomTree(
        schema,
        permissionsCode,
        mode,
        applicationName,
        undefined,
        dealEntityField,
        showSubPage,
        method,
        appId,
      );
    }
    map[item.key] = list;
  }

  const authDataArray = authDataList?.length > 0 ? authDataList : authData;
  const authList = authDataArray.filter(
    (item: any) => item.content !== JSON.stringify({ uiModel: { status: 'READ_ONLY' } }),
  );

  const nextTabData = Object.fromEntries(
    Object.entries(map).map(([key, data]) => [key, handleAuthDetail(data, authList)]),
  );
  setTabInfo(nextTabData);
};

// 页签全选还要考虑其他页签的联动关系
const changeAll = (value: any, field: string, key: string) => {
  const currentList = tabInfo[key] || [];
  const otherList = Object.entries(tabInfo)
    .filter(([tabKey]) => tabKey !== key)
    .flatMap(([, data]) => data);

  const nextList = changeTableList(currentList, value, field, otherList, linkage);
  setTabInfo({ ...tabInfo, [key]: nextList });
};
```

这段代码的问题不在于每个操作都不合理，而在于多个层次被放进了同一个状态闭包。

- 页面 Schema 的解析规则变化，会影响权限表格初始化。
- 权限数据的转换规则变化，会影响组件状态。
- 字段联动规则变化，会影响全选和单行修改。
- 表格数据结构变化，会反过来影响保存数据的生成。

于是，代码的依赖关系更接近“一个中心组件连接所有变化”，而不是多个模块各自拥有明确的变化边界。

## 识别变化轴，而不是按页面区域拆组件

重构前，最容易采取的做法是按照页面区域拆分 JSX，例如把弹窗、表格和页签分别提取出来。这能改善文件可读性，却未必能降低修改成本。

更有价值的拆分方式是先识别变化轴，再决定状态和逻辑的归属。

| 变化轴 | 应该归属的职责 |
| --- | --- |
| 页面来源、页面树和设备差异 | 页面列表获取、筛选和树结构转换 |
| 页面 Schema 和实体字段 | Schema 获取、字段聚合和字段映射 |
| 页面入参 | 入参获取、已有值合并和参数映射 |
| 字段权限编辑 | 权限表格状态、单行修改和批量修改 |
| 联动与一致性 | PC/移动端数据比较和错误提示 |
| 保存转换 | 将编辑状态转换为接口所需的 `contentDtos` |

这里有一个可以迁移到其他项目的判断方法。

> 如果两个功能因为不同原因变化，却共享同一份状态和处理函数，它们通常应该被拆成不同的职责边界。

这个判断比“一个组件最好不要超过多少行”更有用。行数只能提示复杂度，变化原因才能帮助我们决定边界。

## 从集中式组件到职责分层

`137b33f8f` 的提交信息是“表单权限组件重写”。它不是一次简单的 JSX 提取，而是重新安排了页面数据、权限编辑和保存流程之间的关系。

下图只展示主要职责关系，不代表完整目录。左侧是重构前的集中式结构，右侧是重构后的职责分层。

```d2
direction: right

before: 重构前 {
  container: index.tsx
  authority: authority.tsx
  schema: analyze-page-schema.ts

  container -> authority: 状态和回调
  container -> schema: 初始化和保存转换
  authority -> schema: 表格数据和状态转换
}

after: 重构后 {
  container: index.tsx

  pageData: 页面数据 {
    list: usePageList
    schema: usePageSchema
    params: usePageParams
  }

  permission: 权限编辑 {
    operation: FormOperation
    table: FormTable
    source: useDataSource
    consistency: useDataConsistency
  }

  contract: 模块契约 {
    types: type.ts
    enums: enum.ts
    utils: utils.ts
    exports: exports.ts
  }

  container -> pageData: 页面输入和上下文
  container -> permission: Schema 和权限数据
  permission -> contract: 类型和转换规则
  pageData -> contract: 页面数据转换
}
```

### 页面数据单独管理

页面相关的变化被放进不同的 Hooks 中。

- `usePageList` 处理 PC/移动端页面树、个性化页面筛选、Web 视图和页面切换。
- `usePageSchema` 处理页面 Schema、实体字段名称和字段 ID 的聚合。
- `usePageParams` 处理页面入参读取、已有参数合并和参数映射。

这样做的价值是，页面列表变化不再要求权限表格理解接口细节。表格只接收已经整理好的 `schemaInfoList`、字段映射和权限数据。

### 权限编辑单独管理

`FormOperation` 负责字段权限编辑的整体流程，`FormTable` 负责表格呈现和行级交互，`useDataSource` 负责编辑状态，`useDataConsistency` 负责联动校验。

这几层仍然协作，但协作方式从“共享一组外层变量”变成了“通过参数和返回值传递数据”。例如字段变化会先进入数据源，再根据需要触发一致性比较，而不是由表格组件直接修改所有页签状态。

### 保存边界显式化

重构还保留了一个很重要的父子组件契约。父组件不需要知道权限表格内部如何组织页签和行数据，只需要通过 `FormOperationRef` 获取保存结果、联动状态并触发校验。

```tsx fold title="packages/bpm/src/components/form-permission/components/FormOperation/index.tsx"
useImperativeHandle(
  ref,
  () => ({
    getLinkage: () => linkage,
    getSaveData,
    onCheckAll,
  }),
  [getSaveData, onCheckAll, linkage],
);
```

容器组件在保存时只依赖这个契约。

```tsx fold title="packages/bpm/src/components/form-permission/index.tsx"
const authData = formOperationRef.current?.getSaveData();
const isFieldSame = formOperationRef.current?.getLinkage();

const params = {
  ...values,
  contentDtos: [...(authData || [])],
  isFieldSame,
};
```

这就是“状态也要拆分”的具体表现。拆分的不只是 `FormTable` 这段 JSX，还包括谁拥有状态、谁负责转换，以及父组件可以向子组件提出哪些请求。

## 后续提交，重构是否经得起继续变化

重构完成后，提交历史仍然会继续出现修复。它们不应该被简单理解为重构失败，而应该用来观察新的边界是否能承接变化。

| 提交 | 主要变化 | 主要落点 |
| --- | --- | --- |
| `389ff1fe6` | 调整个性化页面筛选判断 | `usePageList.ts` |
| `a16b8e9a6` | 修复实体级权限绑定个性化页面时的未授权后缀 | `usePageList.ts`、`utils.ts`、列表和容器适配 |
| `935654d00` | 没有必需参数时不再调用页面参数接口 | `utils.ts` 和文案处理 |
| `f77d0e342` | 移除移动端标识符的正则匹配 | `utils.ts` |
| `01b990ad1` | 适配页面入参实体参照 | `ParamsMapping/params-select.tsx` |

从这些提交可以看到三个变化。

第一，页面树和个性化页面规则主要在页面数据层调整。`389ff1fe6` 直接修改 `usePageList.ts`，没有把筛选条件扩散到权限表格。

第二，页面展示名称、内部标识和页面类型需要保持区分。`a16b8e9a6` 虽然涉及多个适配入口，但核心问题仍然是页面数据和展示数据之间的转换边界。

第三，接口请求应该由实际数据依赖触发。`935654d00` 对页面参数逻辑增加了必要条件，避免“打开页面”直接等价于“请求所有页面参数”。

这些修复也说明，重构并不会让后续需求自动消失。它真正改变的是问题的落点。后续需求可以更准确地进入页面数据、参数映射或表格交互对应的模块。

当然，边界也不是一次重构后就永久稳定。`a16b8e9a6` 同时修改了列表、工具函数和容器适配，说明展示规则和数据规则之间仍然存在协作关系。评价重构时应该关注这种依赖是否清晰、是否可控，而不是要求每次修改只触及一个文件。

## 如何评价一次重构

可以用下面的问题检查一次重构是否真的降低了变化半径。

- 新需求是否能定位到明确模块？
- 页面数据、权限数据和展示状态是否分开？
- 数据转换逻辑能否脱离 UI 单独验证？
- 父子组件之间是否有清晰的输入和输出？
- 修改一个设备端逻辑是否会影响另一个设备端？
- 后续 Bug 修复是否持续集中在同一个“万能组件”中？
- 一个模块的内部状态变化，是否必须通过多个组件才能完成保存？

如果新增页面参数只需要调整参数模块，新增页面筛选规则只需要调整页面数据模块，新增字段权限规则只需要调整权限编辑模块，那么重构就已经产生了实际价值。

文件数量、Hooks 数量和组件层级都只是结果。真正值得关注的是，一个变化需要穿过多少层代码，才能完成一次修改并被验证。

> 好的重构不是让代码看起来更复杂，而是让复杂性被放在正确的边界内。

## 总结

从 `form-permission` 的演进可以看到，重构通常由三步组成。

1. 找到变化耦合的中心，确认哪些职责共享了过多状态和转换逻辑。
2. 按变化原因重新划分边界，让页面数据、权限编辑和保存转换各自拥有明确入口。
3. 用后续需求验证边界，观察新问题能否落在正确模块，而不是继续回到核心组件。

因此，重构的目标不是把一个大文件拆成很多小文件，而是缩小变化半径，让系统在继续变化时保持可理解、可修改和可验证。
