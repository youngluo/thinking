# 服务端渲染与静态生成

讨论服务端渲染和静态生成时，核心问题是：首屏 HTML 在什么时候生成。

- CSR：浏览器拿到空壳 HTML，下载 JavaScript 后再渲染页面；
- SSR：请求到来时，服务端生成 HTML；
- SSG：构建阶段提前生成 HTML；
- ISR：先按静态页面返回，过期后再重新生成。

CSR 作为对照，主要把渲染工作留给浏览器；SSR、SSG、ISR 会先产出可展示的 HTML。Hydration 不决定 HTML 何时生成，只负责让这些 HTML 在浏览器里恢复交互。

## 四种渲染方式

CSR（Client-Side Rendering）适合登录后的复杂应用，比如后台、编辑器、控制台。服务端返回的 HTML 通常很薄，页面内容依赖客户端 JavaScript 拉数据后渲染。它部署简单，但首屏、SEO 和弱网体验通常不如预渲染页面。

SSR（Server-Side Rendering）是在每次请求到来时生成 HTML，适合既需要优化首屏或 SEO，又依赖请求时数据的页面。它能根据 Cookie、Header、地区、权限等请求上下文返回完整 HTML；代价是需要服务端运行时，还要处理缓存、峰值流量和服务端错误。

SSG（Static Site Generation）是在构建阶段生成 HTML。它适合内容稳定、路由可枚举、更新频率可控的页面，比如文档、博客、官网、营销页。优点是部署简单、CDN 友好、运行时压力低；代价是数据更新不天然实时。

ISR（Incremental Static Regeneration）介于 SSG 和 SSR 之间。页面先按静态页面返回，超过设定时间后再重新生成。它适合内容会变但不要求每次请求都实时的页面，比如商品详情、榜单、活动页。

## Hydration

Hydration 是浏览器接管静态 HTML 的过程。SSR、SSG、ISR 先把 HTML 发给浏览器，此时页面能展示内容，但按钮、表单等组件还没有绑定事件。

客户端 JavaScript 加载后，框架会根据同一份组件树重新计算 UI，复用已有 DOM，并接回事件、状态和路由能力。如果服务端 HTML 和客户端首次计算结果不一致，就会出现 hydration mismatch。

## 怎么选择

| 方式 | HTML 生成时机                  | 数据新鲜度     | 服务器压力 | 典型场景                 |
| ---- | ------------------------------ | -------------- | ---------- | ------------------------ |
| CSR  | 浏览器运行时                   | 取决于接口     | 低         | 后台、编辑器、控制台     |
| SSR  | 每次请求时                     | 高             | 高         | 首屏、SEO、动态数据      |
| SSG  | 构建阶段                       | 取决于构建频率 | 低         | 文档、博客、官网、营销页 |
| ISR  | 构建时生成首版，过期后重新生成 | 中             | 中         | 商品详情、榜单、活动页   |

一个简单判断：

- 不需要 SEO，也不关心首屏 HTML：优先 CSR；
- 内容稳定、能提前生成：优先 SSG；
- 需要首屏优化或 SEO，且内容依赖当前请求：优先 SSR；
- 内容大部分稳定，但允许一定延迟更新：考虑 ISR。

实际项目里通常会混用。文档页可以 SSG，商品详情可以 ISR，搜索结果页可以 SSR，登录后的管理后台可以 CSR。

## React / Next.js 怎么用

React 本身提供服务端渲染 API，例如 `renderToPipeableStream`、`renderToReadableStream`、`renderToString`、`renderToStaticMarkup`、`prerender`。它们负责把组件渲染成 HTML；至于路由、数据加载、缓存、代码分割和部署，真实项目通常交给框架处理。

React 生态里最常见的选择是 Next.js。

### 服务端组件

React 里的服务端组件通常指 RSC（React Server Components）。它解决的是组件在哪里执行：Server Component 在服务端运行，通常可以访问数据库、文件系统或内部服务，并把结果序列化给客户端。Client Component 才会进入浏览器，负责状态、事件和浏览器 API。

所以 RSC 不等于 SSR。SSR 讨论 HTML 在什么时候生成，RSC 讨论组件代码在哪一侧运行。在 Next.js App Router 里，两者经常一起出现，但它们解决的是两个不同问题。

### 渲染配置

App Router 中，`layout` 和 `page` 默认是 Server Components，组件逻辑会在服务端执行。前面说过，Server Components 不等于 SSR；页面是否请求时生成，还要看缓存、请求上下文和动态路由配置。

Next.js 不是手动选择一个固定渲染模式，而是根据页面是否读取请求上下文、数据请求是否可缓存、动态路由是否能在构建时枚举，推导出对应的渲染和缓存行为。

### 配置 SSR

依赖请求上下文的页面会进入请求时渲染。常见入口是 `cookies()`、`headers()` 这类 API：

```tsx
import { cookies } from 'next/headers'

export default async function Page() {
  const cookieStore = await cookies()
  const token = cookieStore.get('token')?.value
  const profile = await getProfile(token)

  return <main>{profile.name}</main>
}
```

如果页面没有读取请求 API，但业务上要求等真实请求到来后再渲染，可以使用 `connection()`：

```tsx
import { connection } from 'next/server'

export default async function Page() {
  await connection()

  const data = await getRequestScopedData()

  return <main>{data.title}</main>
}
```

如果只是某次请求不能复用缓存，可以在 `fetch` 上关闭缓存：

```tsx
await fetch('https://api.example.com/profile', {
  cache: 'no-store',
})
```

### 配置 SSG

静态页面不读取请求上下文。普通静态路由保持可缓存即可；动态路由需要用 `generateStaticParams` 枚举构建时要生成的路径：

```tsx
export async function generateStaticParams() {
  const posts = await getPosts()

  return posts.map((post) => ({
    slug: post.slug,
  }))
}

export default async function Page(props: { params: Promise<{ slug: string }> }) {
  const { slug } = await props.params
  const post = await getPost(slug)

  return <article>{post.title}</article>
}
```

不希望访问未预生成路径时，可以关闭动态参数兜底：

```tsx
export const dynamicParams = false
```

### 配置 ISR

页面可以静态返回，但需要定期更新时，可以配置 `revalidate`：

```tsx
export const revalidate = 60
```

这表示页面最多缓存 60 秒，过期后重新生成。它不是纯 SSR，也不是纯 SSG，更接近 ISR。

### 静态导出

如果整个站点都能静态化，可以在 `next.config.ts` 中导出静态产物：

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  output: 'export',
}

export default nextConfig
```

这个模式要求所有页面都满足静态约束，不能依赖请求时 Cookie、Header、动态重写和服务端运行时能力。

## Vue / Nuxt 怎么用

Vue 核心提供的是 SSR API。服务端用 `createSSRApp` 创建应用，再用 `vue/server-renderer` 的 `renderToString` 渲染出 HTML；浏览器加载客户端 bundle 后，再完成 Hydration。

```ts
import { createSSRApp } from 'vue'
import { renderToString } from 'vue/server-renderer'

const app = createSSRApp(App)
const html = await renderToString(app)
```

这只是底层渲染能力。真实项目里的路由、数据加载、缓存和部署，通常还是交给 Nuxt 或 VitePress。

### 服务端页面和组件

Vue 核心没有 RSC 这样的内置模型。Nuxt 提供的是框架层能力，需要分成页面和组件两种情况看。

页面放在 `app/pages` 下时，可以用 `.server.vue` 写成 server-only page。这类页面只在服务端渲染，代码不会进入客户端 bundle，适合不需要浏览器交互的整页内容。

组件放在 `components` 下时，也可以用 `.server.vue` 写成 Server Components / Islands，把 Markdown 渲染、代码高亮、重计算等不需要进浏览器的部分留在服务端。这和 React RSC 不是同一套机制。按当前 Nuxt 文档，组件级 Islands 仍标为 experimental，需要通过 `experimental.componentIslands` 开启。

### 渲染配置

Nuxt 默认开启服务端渲染：

```ts
export default defineNuxtConfig({
  ssr: true,
})
```

如果设置为 `false`，整个应用会变成客户端渲染：

```ts
export default defineNuxtConfig({
  ssr: false,
})
```

注意，`ssr: false` 不是 SSG。它只是关闭服务端输出内容，页面主要等客户端 JavaScript 渲染。

Nuxt 更常见的混合渲染配置是 `routeRules`：

```ts
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },
    '/blog/**': { prerender: true },
    '/products/**': { swr: 3600 },
    '/admin/**': { ssr: false },
  },
})
```

这些配置分别对应：

- `prerender: true`：构建时生成静态页面，更接近 SSG；
- `swr: 3600`：请求时生成并缓存，过期后后台重新生成；
- `isr: true | number`：在支持的平台上使用增量静态生成；
- `ssr: false`：这个路由只做客户端渲染。

### VitePress

VitePress 更偏内容型 SSG。Markdown 在构建阶段转成静态页面，部署后交给 CDN 分发。文档、博客、组件库说明这类站点通常不需要每次请求都重新渲染，用 SSG 更简单。

## 总结

SSR、SSG、ISR 的区别不是页面能不能交互，而是首屏 HTML 在什么时候生成、能不能缓存，以及数据要新鲜到什么程度。服务端组件是另一条维度，它讨论的是组件代码在哪一侧运行。

React 和 Vue 都提供底层服务端渲染能力，但实际项目更常通过 Next.js、Nuxt、VitePress 这类框架落地。选型时重点看页面是否需要请求上下文、数据更新频率、缓存策略和部署成本。
