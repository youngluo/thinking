# 低代码平台实现方案

这套平台分三段：设计器产配置，出码引擎把配置编译成真实前端工程，runtime core 解释构建期定不下的部分。它要同时满足四类诉求：业务配置即可上线、开发者能接手代码、一份页面覆盖两端、平台升级能覆盖存量应用。三段关系可以压成一个等式：

> 低代码应用 = 元数据契约 + 编译骨架 + 运行时解释

多数低代码平台把配置交给通用渲染器解释执行，这里没有：构建期能确定的编译成代码，运行期才知道的留给 runtime core。这条分界线决定改一个标题的成本，也决定一次修复能覆盖多少应用。

## 能力总览

七块能力各自可替换：

| 能力 | 主要职责 |
| --- | --- |
| 元数据契约 | 页面结构、控件描述、表达式、事件动作与运行时边界，三段唯一的接口 |
| 建模与规则 | 实体、字段、索引、参照、字典与扩展方案，及流程、生成、扣减三类规则 |
| 设计器 | 把意图写成配置，管理应用与组件资产，不生成渲染代码 |
| 出码引擎 | 把配置编译成可构建可修改的工程：骨架、依赖、路由与流程函数 |
| runtime core | 解释构建期定不下的部分：组件代理、状态、表达式、事件、数据与权限 |
| 组件资产 | 控件包、描述清单与远程加载，加控件不动设计器也不动内核 |
| 文案与交付 | 文案收集与按需拉取，构建号刷新缓存，后端触发的发布与双向装载 |

## 运行形态

三个维度相互独立，任意组合共用同一套内核：

| 维度 | 选项 | 含义 |
| --- | --- | --- |
| 终端 | PC 与移动 | 页面配置按终端各存一份，一次发布并行产两份工程 |
| 接入 | 独立访问、门户装载、审批内嵌 | 产物是远程模块，宿主按地址拉入口 |
| 交付 | 全量发布、只重出前端、批量升级、跨环境导入导出 | 从改标题到推控件包各有对应构建类型 |

## 设计思路

四条思路各回答一个问题：

| 设计思路 | 实现机制 | 实际价值 |
| --- | --- | --- |
| 构建期能定的就编译 | 骨架、依赖、路由与流程写成源码，属性与事件留成数据 | 产物可接手可进宿主，行为修复靠升内核覆盖存量 |
| 配置只有一种形状 | 页面用扁平 id 表，一份描述同时驱动面板、初始值与包裹 | 版本比对、局部改动与跨端转换落在同一份数据上 |
| 三段只靠契约耦合 | 元数据以目录输入，产物与内核之间是注册表加注入 SDK | 出码幂等可快照测，三段能独立发版 |
| 永远留人工出口 | 手写页只播种不覆盖，动作实现注册在产物而非内核 | 页面能绕开生成逻辑，单应用能改自己的动作行为 |

判据只有一条：**构建期能不能确定**。两条极端路都不成立，纯解释执行时宿主在构建期拿不到页面与依赖清单，纯代码生成时行为修复被绑死在重新发布上，而属性与表达式的取值依赖运行期上下文（当前行、选中集合、登录人）。

## 架构总览

设计态产出元数据，出码引擎编译成工程，内核解释数据并把页面交给宿主，组件资产与交付机制横切其外：

```d2 fold
direction: down
title: |md
  # 低代码平台
| {near: top-center}

design: 设计态 {
  modeling: 建模与规则
  designer: 页面设计器
}

meta: 元数据 {
  schema: 页面结构与控件描述
  resource: 实体 参照 字典 列表方案 规则
}

codegen: 出码引擎 {
  parse: 解析，元数据变事实
  generate: 生成，事实变文件
}

app: 生成工程 {
  skeleton: 页面骨架与配置数据
  preset: 平台自带页与流程
}

kernel: runtime core {
  proxy: 组件代理与状态订阅
  action: 表达式 事件 数据 权限
}

side: 资产与交付 {
  supply: 组件库与控件描述
  delivery: 门户 文案 构建号
}

design.designer -> meta.schema: 保存草稿
design.modeling -> meta.resource
meta -> codegen.parse: 元数据目录
codegen.parse -> codegen.generate
codegen.generate -> app
app -> kernel: 骨架引用组件代理并读取配置
side.supply -> design.designer: 远程拉描述
side.supply -> codegen.generate: 解析包名
app -> side.delivery: 远程入口装载
side.delivery -> kernel: 取词与版本校验
```

## 元数据契约

三段独立发版，中间只有数据。五层契约里前两层定义能配出什么，后三层定义怎么对上。

### 页面结构契约

页面配置在库里是一列 JSON，结构是扁平 id 表而非嵌套树：

```ts fold
{
  childById: {
    a1: { id: 'a1', type: 'Panel', children: ['a2'] },
    a2: { id: 'a2', type: 'FormField', index: 0, columns: 6, dataSource: {} },
  },
}
// 页面级：类型、入参、出参、变量、外框、终端
```

摊平的收益有三：改动只表现为某几个键变化，通用 diff 库就能做版本比对、草稿判脏与提交差量；改单个节点不必重建整棵树；跨端转换只重写栅格字段。

一个页面记录只属于一个终端，同一逻辑页面在两端是两份配置，共享的是实体、参照、字典、权限与流程；把两份认成同一页面的是一对分组标识，列表方案与校验都按它关联。页面类型枚举有十四类，但新建页面只开放列表、详情、全表编辑与其它，门户、报表、审批、子页面、辅助信息页当前被注释关闭；子页面在注释里写明不可独立访问、只能被嵌入，页面因此是嵌套结构而非一张表单。

### 控件描述契约

一份描述喂四个消费者：面板按它渲染，新建实例按它取初始值，runtime core 按它决定包裹，出码按它解析包名。

```ts fold
defineControl({
  type: 'BizUserPicker',            // 三端共用的唯一标识
  name: '人员选择', group: 'application',  // 面板展示与分组
  uiModelSchema: [],                // 可绑数据形态与状态集合
  dataTypes: [{ type: 'STRING' }],  // 能承接哪些字段类型
  isFormItem: true,                 // 运行时是否套表单项
  settings: [{ key: 'attributes', name: '属性', setting: [{ group: '选择设置', items: [
    { key: 'multiple', label: '多选', type: 'switch', defaultValue: false, classification: 'settings' },
    { key: 'range', label: '范围', type: 'radioButton', props: { options: [],
      visible: { dynamic: true, getValue: (d) => d.multiple } } },  // 显隐是函数
  ] }]}],
});
```

配置项要点有四：键与点分路径 `classification` 决定值落在组件属性哪，预置值给面板、默认值给运行时，`props` 原样交给编辑控件，显隐可以是一个按当前配置算的函数，它随控件包发版而不随应用配置变化。容器类控件另有 `containerBox` 声明可拖入区域，`rules` 挂设计期校验。

三条经验：描述必须是面板、初始值与行为的唯一来源，拆成三套就会出现「面板能改、运行时无效」；描述应由工厂函数包一层补默认值与派生字段，允许裸对象导出就会两种写法并存；字段类型在控件源码、登记清单与设计器读取处用了三个名字，默认控件也不看描述里的标记而读实体字段配置。这类不一致不报错，只让配置静默失效。

### 表达式契约

表达式的值有两个形态存在同一对象里：给人看的（可读文本、算子、结果类型）回填面板，给机器跑的（表达式、参数、结果类型）给出码。出码只搬后者并在生成期预编译，运行态只求值。可引用变量被枚举成两侧对齐的前缀（页面入参、页面变量、当前行、勾选集合、全部行、登录人、组件属性），设计器据此生成候选树，内核据此取值，这条枚举是两侧唯一的语义接缝，错位时配置能存、面板能显示、运行时静默取不到值。落库时表达式还会被抽出换成占位标记，另存一张路径侧表，主体配置因此保持可读可 diff。

### 事件与动作契约

固定四段：事件触发，动作序列按条件取首个成立分支，单个动作走前置、本体、后置，本体分四类（内置、控件、流程、扩展）。取首个分支而不是全部执行，配置里就能表达 if 与 else if；扩展动作指向一个包的运行时入口动态加载，留给三方。

内置与控件类动作大多没有独立实现，而是映射到预置流程：出码引擎内置十余个流程模板（保存、提交、撤回、删除、导入导出、打印等）无条件生成到工程里，运行期按「预置前缀加动作名」找到流程，与自绘流程走同一条调用路径。流程分前后端：前端编译成函数在浏览器执行，后端不出码、运行期拼接口地址发请求；节点模板文件名与动作类型一一对应，加一种节点就是加一个模板片段。

### 运行时边界契约

出码工程与 runtime core 在不同构建里产出，之间没有依赖注入容器也不靠 context：内核把管理器实例按应用、页面、组件三级签名注册到全局对象上二十个左右命名空间，一个五十多方法的 SDK 作为属性注入页面与每个组件，类型声明由出码落盘。不用 context 是因为流程函数、宿主脚本与内嵌子页都不在组件树里，必须能拿到同一份状态。

## 建模与规则面

实体侧可建模：字段与字段组、可复用字段集、数据库索引（一等产物）、两套枚举字典、参照、DTO、业务事件、扩展方案与自定义类型。字段一旦发布，类型、多选、审计、可搜索、脱敏等一批属性不可再改，只有小数位数与长度允许单向放宽；实体的版型门控它能否参与单据生成与内嵌流程。参照不是字段属性而是独立对象，有自己的分组、终端维度与发布状态，配置时绑定一个已发布页面，所以「选客户」是可复用、可版本化的资产。

规则有三种，容易混为一谈：

| 形态 | 表达什么 | 存与跑 |
| --- | --- | --- |
| 流程 | 命令式步骤 | 节点图，前端编译成函数，后端留在服务端 |
| 生成规则 | 单据 A 生成 B 的字段映射 | 图加逐行映射，服务端执行 |
| 扣减规则 | 生成 A 时按算法增减 B 的数量 | 条件、规则、算法三段声明 |

生成与扣减共用一个图组件与后端模块，流程是另一套编辑器，它的节点清单就是平台可调用能力的清单。另有三条边界：筛选方案同表不同源，设计器配系统级、用户存自定义；外部服务经接口文档导入成连接器，客户端只存方法全名而调用在服务端；跨应用复用靠依赖清单并锁版本，出码时把对端元数据目录整棵递归进来。

## 设计器

设计器是门户里的独立微应用，难点不是交互，而是如何不重发自己就容纳新控件。答案是控件描述不写死在设计器里：启动时从两端组件库的远程模块拉描述与本体，业务包按终端注册，三方件按应用版本动态加载，所以加控件不动设计器；流程图形编辑器同样来自别的应用，设计器也反向暴露发布面板等模块供复用。

编辑器由四个部件组成：控件注册表按终端缓存并推导初始值，画布按终端与类型找组件再套拖拽与选中外壳，大纲树，属性面板按配置项类型分发到编辑控件（这是设计器最厚重的一块）。配置类系统必撞的几件事都有机制：编辑只写草稿、发布才落正式并按两者差异判脏；进入设计器抢锁；实体被别处改动通过长连接广播刷新；设计期校验覆盖九类规则加三类绑定规则并做两类环检测；变更日志按产物记录，页面、外框、流程可各自回滚；跨端跨页漂移由后端检测、长连接推回三级严重度。

## 出码引擎

出码是持续集成里的一次命令行调用：克隆产物仓库、拷模板、解析元数据、并行生成、依赖软链到共享仓、构建回仓。

引擎不逐类调接口，而是把每类元数据映射成一个目录按应用读取并递归依赖应用。这让出码成为纯函数，同样的输入产出同样的工程，于是能拿生成目录做逐文件快照测试，改模板时 diff 只出现在预期文件里。解析与生成之间有一条纪律：**数据加工只准发生在解析阶段，生成器不得再改数据**。解析先预扫描算出真正依赖哪些实体、字段、参照与字典再按需加载，再由一组访问器遍历页面配置，得出引入哪些包、生成哪些配置数据、组件依赖与事件绑定；生成阶段只写文本，可并行可重跑可比对，唯一顺序例外是依赖清单与多语言要先生成。

约二十个生成器并行落盘路由、入口、宿主资产、元数据、流程、外框、构建参数与手写页。页面生成器最关键：每页产出入口、视图、布局与配置数据，而视图的 JSX 只有组件代理标签的嵌套。

```tsx fold
<WidgetProxy key="a1" id="a1" type="Panel" runtimeContext={ctx}>
  <WidgetProxy key="a2" id="a2" type="FormField" runtimeContext={ctx} />
</WidgetProxy>
```

组件是谁、有哪些属性、绑了哪些事件，全在同目录的配置数据里以压缩形式内联，运行时才解析。**这就是分界线的物理位置**：骨架是代码，行为是数据。流程则被编译成可直接调用的函数，控制流交给语言运行时，省掉自建解释器，调试与打包优化都能覆盖。

一批管理页（字典、参数、编号规则、导入导出模板、打印、生成与扣减规则）不参与生成：它们被标为预置页从待生成清单剔除，文件由工程模板整目录拷贝带入，哪些进哪个终端由一份硬编码白名单决定，两端数量并不对称，也不进路由表而靠页面名命中懒加载。收益是平台能力随模板升级而不惊动业务配置，代价是这份白名单两处各存一份。

控件从哪个包引入由一组有序规则决定：特殊控件白名单、节点的远程包标记、工程内本地组件、业务组件登记路径、按终端换前缀的业务包、组件库兜底。终端差异在配置层就已分开，出码按终端字段过滤页面并行产两份工程；移动页由 PC 页一次性转换生成副本并重新生成标识，之后两端各自演进。依赖版本号一律取自共享依赖仓，否则每个工程各自锁版本，统一升级就是纸面能力。

页面还能标成手写页：跳过配置解析，只在目标文件缺失时播种模板（绝不覆盖已有内容），视图换成懒加载手写页的外壳，其引入的依赖合并进依赖清单。这个口子也是排障的最后手段：页面能绕开生成逻辑，又仍在同一套路由与运行时里。

## runtime core

页面从被访问到可见走五步：门户装载远程入口、进页面容器、交应用壳、由产物入口把资产交给内核、渲染并初始化。初始化分两段：同步段只建上下文与注册资产，保证首帧可渲染；异步段并发拉权限、组件资产、流程、默认值、多语言与流程权限，全部就绪才进入渲染前事件，其间有一个最多等若干秒的任务闸门。异步段在流程权限解析完成后会清掉非值类状态信号，否则表达式会读到合并前的配置，凡把两份来源合并进一份配置的系统都需要这一步。预置页命中内置名单后跳过入参、占位、权限与标题栏逻辑。

九个管理器（资产、设置、状态、组件状态、表单四态、事件、数据源、默认值、权限）都是普通类实例，按签名注册在全局命名空间里彼此直接引用；设置读取分两个接口，求值版服务渲染，原始版服务调试与依赖收集。

几百字段的表单页不能被一次回填整页渲染，做法是两侧收口。写侧：状态库是原子风格存储，每页一个实例，键名带类型与行标识共十余类，核心写函数只写有差异的键，按当前渲染形态取值已相同的直接跳过，需要强制刷新时给一个时间戳原子打值唤醒订阅者，批量写入统一收口。读侧：出码阶段就算好每个组件依赖哪些数据源与字段，运行期把这张表展开成具体行标识集合，全部行、勾选行这类引用要摊成当前所有行，子页入参还要重定向回父页数据源，于是命中粒度是组件乘行而不是页面。另两点：派生属性按帧缓存，永久不可见组件走无头分支只参与数据流。

组件代理是骨架里唯一标签，一条链做完全部差异：按类型解析组件，按状态信号分流到四种模式（标准、纯展示、只绑值、哑组件），求值派生属性与动作，给每个节点套独立错误边界、懒加载与记忆化，再按控件描述决定是否包表单项、重复节点容器或栅格项。独立错误边界是必需项，单个控件抛错不能整页白屏，且要打出它的引入路径。控件接入契约很薄：一组固定属性（节点标识、类型、运行时上下文、值、组件签名、SDK）加两个可选静态量，契约越薄接入成本越低。

调度在平台、实现在产物：内核只做分支选择、前置后置、事件总线、等待组件处理完的异步调用与错误收敛，内置动作（开关页、批量设值、数据流、事件抛出、打印、参照携带、表单转换、附件上下载）在每个出码工程里作为资产注册。于是调度逻辑升内核即全量生效，而某个应用想改某个动作的行为，改自己的源码就行。

数据源抽象成七类实例存在页面签名下，子页入参映射指回父页数据源；列表查询带筛选方案加条件值，写入区分普通与流程通道，提交前算差量并生成变更日志，审计字段的变更历史由内置动作懒挂载日志组件查询；接口层从 GraphQL 迁向 REST，由开关控制。权限两个来源都在启动期解析完合并进组件设置：资源权限给可操作、只读、禁用、隐藏四种效果，流程表单权限按控件与字段路径给状态、必填与初始值，且值本身可以是表达式。合并后走同一条四态通道，渲染层不知道来源，因此不存在两套逻辑互相覆盖；行级数据权限留在后端，前端做行级过滤必然泄露。双端只剩极薄交互壳，因为包与控件集的分端已在出码期完成；运维侧自带错误信息、调试面板、耗时埋点与自动保存。

## 组件资产供给

控件要能被拖出来并被渲染，需要实现与描述、登记清单、以及被出码与构建识别：

```json fold
{ "controls": [{
    "name": "人员选择", "type": "BizUserPicker", "terminalType": "PC", "category": "builtin",
    "designModule": { "name": "UserPickerDesign" }, "schemaModule": { "name": "UserPickerSchema" },
    "runtimeModule": { "name": "UserPicker" }
}] }
```

三个入口可以各自独立文件，也可以合并成一个由组件按「是否设计态」分流两套渲染；清单是数组且由构建工具校验 schema，写错在构建期就失败而不是设计器里静默少控件；组件导出时还要把描述与静态量挂回组件。控件声明因此分散在清单、描述与静态量三处，失败表现不同：清单漏了面板里没有它，描述漏了属性区是空的，静态量漏了能渲染但设计器读不到配置。

## 文案与版本

文案是配出来的，所以多语言贯穿三段。设计器里每个文本属性存成带默认值的键值对象；出码时把页面标题、列表列、按钮、属性与流程里的文案收集成静态与元数据两类写入工程，并生成一份描述文件记下后端归属；构建工具再把工程与控件包文案分别拷进产物目录。运行期不打包文案，而是按公共包、应用页面包、参照页面包三类请求接口，结果按租户缓存，宿主靠注入到远程入口里的映射表决定用哪个后端归属取词。取不到键就回落到同时存的默认值，这正是每个文本都要带默认值的原因，出码侧只上报源语言。

版本号决定交付能否真正生效。构建工具生成时间戳构建号、加提交与分支拼成的标签与平台版本，写回应用清单并产出版本文件，远程入口文件名与模块唯一名都带标签。运行期在初始化第一步比对两份版本：一份从静态服务取版本文件且禁缓存，一份从已加载入口里读，不一致就记监控日志、刷新入口并中断本次渲染重取。构建工具同时拒绝依赖版本落在平台版本范围之外的包，把同一代平台变成构建期约束。

## 发布与装载

发布面板驱动分步状态机，对应运行形态里的几种交付：全量发布走完整出码与构建，另一种构建只重出前端代码，这是改一个标题的成本上限；批量升级按前后端、终端、整批或部分、是否只推某个控件组合，对应控件包修复后存量应用重出码；跨环境搬运走元数据导出与导入。

装载是双向的：门户按地址拉取产物页的远程入口，审批客户端启动时预加载 runtime core，出码工程则把审批运行态包识别为唯一的远程模块以便挂流程按钮。三个方向合起来才满足页面要嵌进已有系统，单向设计会把应用孤立成独立站点。

## 关键取舍与代价

| 决策 | 换来 | 付出 | 何时后悔 |
| --- | --- | --- | --- |
| 骨架编译、行为解释 | 可接手、可装载、可统一升级 | 改标题也要出码构建 | 配置变更高频而构建慢时，用户以为没生效 |
| 元数据目录输入 | 幂等、可离线、可快照测 | 一份隐式目录契约 | 结构演进快又缺校验时静默出错码 |
| 注册表加注入 SDK | 组件树外可访问、跨产物定位 | 二十个左右可变全局 | 同页多实例变多后排查变难 |
| 权限合并进组件设置 | 渲染层单一事实源 | 需要作废中间态 | 权限来源增多时合并顺序成为故障点 |
| 页面按终端各存 | 两端各自排版与本端控件集 | 改一端不同步 | 两端长期偏离，用户报移动端少了字段 |
| 同一事实多处拷贝 | 各仓解耦 | 描述与自带页清单各自漂移 | 控件增多或多产品线并行时静默失效 |

三条改进：控件描述改为单一来源并据此生成面板配置、初始值与类型声明；全局注册表收敛成带生命周期校验的单一 registry；表达式的变量枚举与求值器合成共享包。

## 重建顺序与验收判据

| 顺序 | 模块 | 验收判据 | 会先撞到的问题 |
| --- | --- | --- | --- |
| 一 | 元数据契约 | 手写配置能渲染成可用表单页 | 用嵌套树，三套配置各写一遍 |
| 二 | 代理渲染与状态 | 两组件互相赋值不触发整页渲染 | 拿浅比较当性能方案 |
| 三 | 事件调度与动作注册 | 一个按钮完成校验、取值、请求与关页 | 发明分支语法，动作没有注册口 |
| 四 | 出码引擎 | 同一份元数据两次出码零差异 | 生成阶段改数据，依赖版本散落 |
| 五 | 设计器 | 配出的页面能正常出码并正确渲染 | 编辑控件类型与描述对不上 |
| 六 | 双端与权限 | 同一页面两份终端配置行为一致 | 在运行态做双端，两套权限两套渲染分支 |

贯穿一条：每阶段都要能被人工绕过，第四步之后必须有源码出口。

## 写作口径与边界

机制来自对一套真实运行平台的核查，覆盖设计器、出码引擎、runtime core 与一个已发布产物；公司名、包名、接口与路径已隐去，规模数字量级化，示例代码按真实结构重写。三处限制：部分依赖库不在本地，相关判断只到调用点；后端未接触，部署与检测类结论只到请求点；未实跑构建，骨架生成这条路径在样例产物里没有实例。
