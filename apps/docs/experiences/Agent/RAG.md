# RAG

很多人第一次接触 RAG 时，会把它理解成“大模型加一个知识库”。这个说法不算错，但太粗了。真到项目里，你会发现问题没这么简单。

大模型本身已经很强，为什么还需要 RAG？原因通常不是模型不会说，而是它说的时候缺少你真正关心的那份上下文。

比如这些场景：

- 公司内部有一堆产品文档、流程文档、接口说明、会议纪要，但模型训练时根本没见过；
- 公共知识会过时，模型知道的是训练截止前的世界，不是你现在系统里的真实状态；
- 用户问的问题往往很具体，答案藏在一大堆文档的某几个段落里，不是靠模型“泛化一下”就能稳定答对；
- 即使模型有长上下文，也不代表你可以每次把所有资料都塞进去，成本、延迟和噪声都受不了。

所以 RAG 要解决的，本质不是“让模型更聪明”，而是“在生成答案之前，先把和问题相关的信息找出来，再交给模型回答”。

这篇文章按下面这个顺序展开：

- 先说清楚 RAG 是什么，以及它到底在解决什么问题；
- 再拆成两个主流程：离线阶段怎么准备知识，在线阶段怎么回答问题；
- 最后落到工程实践，讲 chunk、召回、重排、缓存、评测这些真正决定效果的部分。

## RAG 是什么

RAG 全称是 Retrieval-Augmented Generation，中文通常叫“检索增强生成”。

如果只看名字，它包含两件事：

- Retrieval：先检索；
- Generation：再生成。

这两个词放在一起，核心意思就是：不要只靠模型参数里的记忆回答问题，而是先从外部知识源里找到相关内容，再把这些内容作为上下文交给模型，让它基于检索结果作答。

所以 RAG 不是单一模型能力，而是一套系统能力。它至少包括下面几层：

- 知识从哪里来；
- 知识怎么切分和索引；
- 用户提问后怎么召回相关内容；
- 多段候选内容里哪些最值得放进上下文；
- 最终怎么组织提示词，让模型引用这些内容回答。

如果把它说得再直白一点：

RAG 不是让模型“凭空知道更多”，而是让模型“回答前先查资料”。

## 为什么需要 RAG

理解 RAG 时，最好不要从“它是什么组件”开始，而要从“纯大模型回答为什么会出问题”开始。

### 1. 模型知识不是实时的

模型参数里的知识来自训练数据，而训练是有截止时间的。你今天上传的新文档、刚改过的产品规则、刚发布的接口字段，模型并不会自动知道。

这意味着只靠模型参数回答“最新制度是什么”“当前产品怎么收费”“我们内部这套系统如何接入”时，答案天然不可靠。

RAG 的价值在这里很直接：把最新资料接进来，让回答基于最新文档，而不是基于模型训练时的旧记忆。

### 2. 私有知识不在模型参数里

很多业务问题不是公共知识问题，而是私域知识问题。

例如：

- 公司制度；
- 内部 API 文档；
- 客服知识库；
- 法务模板；
- 客户项目资料。

这些内容模型通常没见过，或者即使见过，也不可能以你当前版本、当前组织结构、当前业务规则的形式存在。

所以项目里真正有价值的问答系统，往往都不是“考模型知不知道”，而是“让模型能不能稳定用好你的私有数据”。

### 3. 纯模型回答容易幻觉

当模型缺少足够上下文时，它经常不会老老实实说“不知道”，而是会根据已有模式补出一个“看起来像答案”的答案。

这就是很多人提到的幻觉。

RAG 不能彻底消灭幻觉，但它能显著降低“无依据乱答”的概率。因为模型不再只能依赖参数记忆，还可以依赖你明确提供的检索证据。

### 4. 不是所有问题都值得塞全量上下文

有人会说，现在模型上下文很长，为什么不直接把整份知识库塞进去？

问题在于：

- 文档一多，token 成本会明显上升；
- 上下文越长，噪声越大，模型注意力越容易被无关信息稀释；
- 延迟会变高；
- 不同问题只需要知识库里的很小一部分，全量塞入的性价比很低。

RAG 的意义就在于先做筛选。真正昂贵的是生成，所以先用检索把候选范围缩小，再把高相关内容交给模型。

## RAG 的基本思路

可以把 RAG 看成一个两阶段系统：

1. 离线阶段：把知识整理成“可检索”的形式
2. 在线阶段：用户来提问时，实时检索相关知识，再生成答案

这里最容易被低估的是中间那几步。RAG 效果差，很多时候不是模型不行，而是：

- 文档切得不对；
- 检索没召回到真正相关内容；
- 候选很多但排序不好；
- 上下文拼接方式太粗。

所以工程上常说，RAG 是“检索系统 + 提示词系统 + 生成系统”的组合，不是“接个向量库”就结束。

## 离线流程：先把知识变成可检索资产

### 1. 文档接入与解析

RAG 的原料通常不是干净的纯文本，而是各种异构数据：

- PDF；
- Word；
- Markdown；
- 网页；
- 数据库记录；
- 工单和 FAQ。

第一步要做的是把这些原始资料解析成结构化或半结构化文本。这里的难点不在“读出来”，而在“不要读坏”。

常见问题包括：

- PDF 双栏布局被解析乱序；
- 表格被摊平成不可理解的文本；
- 标题层级丢失；
- 代码块、列表、引用区被破坏。

如果文档解析阶段就把语义结构搞乱，后面检索质量通常也会明显下降。

### 2. 文本清洗

解析完后，一般还要做清洗：

- 去掉重复页眉页脚；
- 去掉无意义空白和乱码；
- 规范标题层级；
- 合并被错误切断的段落；
- 标注文档来源、时间、业务域、权限信息。

清洗的目标不是“越干净越好”，而是“尽量保住语义边界，删掉噪声”。

### 3. 切块

切块是 RAG 里最关键的一步之一。

因为模型不会直接检索整份文档，而是检索文档块。如果块切得太大，会带来很多无关噪声；切得太小，又容易把完整语义切碎，导致召回到的内容不够回答问题。

常见切块方式有几种：

- 固定长度切块：按字符数或 token 数切；
- 滑动窗口切块：相邻块保留一部分重叠；
- 结构化切块：按标题、章节、段落、表格、代码块等结构切；
- 语义切块：根据语义边界动态切分。

工程上最常见的是“结构优先 + 长度兜底”：

- 如果文档本身有清晰结构，尽量按结构切；
- 单块过长时再按长度二次切分；
- 为了避免语义断裂，再加少量 overlap。

切块没有通用最优值，通常要结合：

- 文档类型；
- 用户问题粒度；
- 模型上下文窗口；
- 重排模型成本。

### 4. 元数据抽取

一个成熟的 RAG 系统不会只存文本，还会给每个 chunk 绑定元数据，例如：

- 文档标题；
- 来源链接；
- 更新时间；
- 文档类型；
- 所属业务线；
- 权限标签；
- 章节路径。

元数据有两个重要价值：

- 检索时可以做过滤，比如只搜某个产品线、某个时间范围、某类文档；
- 生成答案时可以提供引用来源，增强可解释性。

### 5. 向量化

接下来要把文本块转成向量表示，也就是 embedding。

向量化的目标，是让“语义相近的文本在向量空间里距离更近”。这样用户提问时，就能通过相似度搜索找出相关 chunk。

这里要注意两点：

- embedding 模型决定的是“如何理解文本语义”；
- 向量库决定的是“如何高效检索这些向量”。

这两者经常被混在一起，但其实是不同层。

### 6. 构建索引

向量生成完后，要写入索引系统。常见不只有向量索引，还可能包含：

- 稀疏索引，比如 BM25 一类关键词检索；
- 混合索引，同时支持向量召回和关键词召回；
- 分区或多租户索引，用于权限和业务隔离。

很多项目最后会发现，光有向量检索不够。因为不少问题带有很强的关键词特征，例如：

- 错误码；
- 表名；
- API 路径；
- 产品型号；
- 人名、地名、术语缩写。

这类问题往往混合检索比纯向量检索更稳。

### 1. 查询理解

用户输入的问题，不一定适合直接拿去检索。

例如：

- 问题太短：“退款怎么走？”；
- 指代不清：“这个接口为什么失败？”；
- 依赖上下文：“那第二种情况呢？”。

所以在线阶段经常会先做查询理解或查询改写，例如：

- 补足上下文；
- 改写为更适合检索的表达；
- 提取关键词；
- 判断所属领域；
- 判断是否需要多跳检索。

这一层做得好，召回质量会明显提升。

### 2. 召回

召回的目标不是“一步到位找出最优答案”，而是“先从大知识库里快速挑出一批相关候选”。

常见召回方式包括：

- 向量召回：适合语义相似匹配；
- 关键词召回：适合精确术语匹配；
- 混合召回：把两类结果合并；
- 多路召回：不同索引、不同 query、不同数据域并行召回。

很多工程问题都出在这里。用户觉得“RAG 没答对”，本质上常常是正确文档压根没被召回出来。

所以召回阶段更像 recall-first 的策略：先尽量别漏，再让后续排序和生成收敛。

### 3. 重排

召回出来的候选通常有几十条甚至更多，但真正能回答问题的可能只有前几条。

这时就需要重排。

重排模型做的事情，是更精细地判断“候选内容和当前问题到底有多相关”，然后把最值得进入上下文的内容排到前面。

为什么不能只靠向量相似度直接选前几条？

因为向量召回擅长“快速大范围找相似内容”，但不一定擅长“细粒度区分哪一段最回答当前问题”。重排常常是把 RAG 从“能用”拉到“好用”的关键一步。

### 4. 上下文组装

重排后，不是简单把 topK 全拼进去就结束了。

还需要处理几个现实问题：

- 有些 chunk 高度重复；
- 有些 chunk 来自同一文档相邻段落，应该合并；
- 有些 chunk 虽然相关，但和当前回答目标不一致；
- token 预算有限，不能无限塞。

所以常见做法包括：

- 去重；
- 相邻块合并；
- 按来源或主题分组；
- 控制总 token 预算；
- 给每段上下文加标题、来源、编号。

这一层看起来像小事，但会直接影响模型读上下文的效率。

### 5. 生成答案

上下文准备好后，才进入生成阶段。

这时提示词一般会明确约束模型：

- 优先依据提供的上下文回答；
- 如果上下文不足，就明确说明不知道；
- 尽量给出引用来源；
- 不要编造文档里没有的信息。

这一层的目标，不是把模型“驯得更会说”，而是让它遵守“基于证据回答”的规则。

### 6. 返回答案与引用

一个成熟的 RAG 系统，通常不会只返回一段自然语言答案，还会返回：

- 引用段落；
- 来源文档；
- 跳转链接；
- 置信提示。

因为对用户来说，能追溯答案依据，往往和答案本身一样重要。

## RAG 不只是向量检索

很多入门材料会让人误以为：

`RAG = Embedding + Vector DB + LLM`

这个式子只能算最小可运行版本，不足以解释工程现实。

一个真实可用的 RAG 系统，通常至少还要考虑：

- 数据接入和清洗；
- 切块策略；
- 混合召回；
- 重排；
- 权限控制；
- 缓存；
- 引用和可追溯；
- 评测和持续迭代。

如果只做了“文本切块 + 向量库 topK + 扔给模型”，系统往往很快会撞上天花板。

## 工程实践：真正影响效果的关键点

下面这些点，比“换一个更大的模型”更常决定 RAG 最终体验。

### 1. Chunk 策略通常比想象中更重要

如果 chunk 切得不好，后面所有步骤都在补救前面的错误。

常见失误：

- 切得太大，导致无关内容过多；
- 切得太碎，导致单块无法独立回答；
- 完全不看文档结构，只按长度硬切；
- overlap 太小，关键信息被截断。

实践建议：

- 先按文档结构切，再按长度兜底；
- FAQ、制度文档、接口文档、代码文档使用不同切块策略；
- 评估的不是“切了多少块”，而是“是否更容易召回回答所需的最小充分信息”。

### 2. 召回要兼顾语义和关键词

语义检索很强，但并不总是最稳。

尤其在这些场景里，关键词检索很重要：

- 精确错误码；
- SQL 字段；
- 接口名；
- 版本号；
- 专有名词。

所以很多项目最后会采用混合检索：

- 一路走向量召回；
- 一路走 BM25 或倒排索引；
- 最后合并候选，再统一重排。

### 3. 重排是提升答案质量的高性价比手段

如果说召回解决的是“别漏”，那重排解决的是“别把不该进上下文的内容塞进去”。

很多时候你会发现：

- top20 里已经有正确答案；
- 但 top3 里没有。

这说明系统不是“没找到”，而是“没排好”。这类问题通常加重排比换主模型更划算。

### 4. 查询改写能显著改善检索

用户天然不会按知识库的表达方式提问。

文档里写的是“访问令牌过期后执行刷新流程”，用户问的可能是“token 失效后怎么办”。  
文档里写的是“订单逆向流程”，用户问的可能是“退款怎么走”。

所以查询改写常见做法有：

- 同义词展开；
- 缩写还原；
- 多 query 并发检索；
- 结合对话历史补齐指代。

### 5. 权限控制不能后补

企业知识库场景里，RAG 不只是检索问题，还有权限问题。

如果离线阶段和索引阶段没有设计好权限标签，在线阶段就可能把不该看的文档召回出来。这个问题不是回答质量问题，而是数据安全问题。

所以工程上通常会在 chunk 或文档级别绑定：

- 用户组；
- 部门；
- 项目空间；
- 数据密级。

检索时先过滤，再排序，而不是先全量召回再临时屏蔽。

### 6. 缓存决定成本和延迟

RAG 系统通常比普通问答链路更长，所以更需要缓存。

可以缓存的层次包括：

- 文档解析结果；
- embedding 结果；
- 检索结果；
- 重排结果；
- 最终回答。

但缓存也不是越多越好。知识一旦更新，缓存失效策略就必须跟上，否则系统会出现“文档已经更新，但回答还是旧的”。

### 7. 引用和可追溯很重要

很多用户并不满足于“系统给了一个像样答案”，他们更想知道：

- 这句话是从哪来的；
- 是哪篇文档；
- 是哪个版本；
- 有没有原文依据。

所以高质量 RAG 往往会把引用做成一等公民，而不是可有可无的附加信息。

## 常见优化方向

RAG 上线后，优化通常围绕三类目标展开：召回率、答案质量、系统成本。

### 1. 提升召回率

典型手段：

- 调整 chunk 粒度和 overlap；
- 引入混合检索；
- 查询改写；
- 多路召回；
- 基于元数据过滤缩小搜索空间。

### 2. 提升答案质量

典型手段：

- 增加重排；
- 优化上下文拼接顺序；
- 对相邻 chunk 做合并；
- 增加回答模板和引用约束；
- 对特定场景做路由，例如 FAQ、流程问答、代码问答走不同链路。

### 3. 降低成本和延迟

典型手段：

- 缩短召回链路；
- 缓存中间结果；
- 控制上下文 token；
- 对简单问题先走 FAQ 或规则匹配；
- 把昂贵模型留给高价值步骤。

## 如何评估一个 RAG 系统

RAG 最容易掉进的坑是“看起来答得还行，但不知道到底哪里有问题”。

所以它需要拆开评估，而不是只看最终回答。

### 1. 先评估检索

典型问题：

- 正确 chunk 有没有被召回；
- 正确 chunk 排在第几；
- 不同 query 改写方式下召回差异如何。

如果正确材料根本没进候选，后面的生成基本无从谈起。

### 2. 再评估生成

典型问题：

- 有没有依据上下文回答；
- 有没有编造上下文中不存在的信息；
- 有没有遗漏关键约束；
- 答案是否可读、完整。

### 3. 建立失败案例集

高质量 RAG 不是一次调出来的，而是靠失败案例持续打磨出来的。

最值得沉淀的案例通常包括：

- 召回不到；
- 排序错误；
- 上下文过长导致关键证据被淹没；
- 文档版本冲突；
- 多跳问题只命中一半材料。

有了这些案例，后面优化 chunk、召回、重排时才有明确靶子。

## RAG 适合什么，不适合什么

适合：

- 基于企业私有知识的问答；
- 文档助手；
- 客服知识库；
- 内部制度与流程问答；
- 代码库和接口文档检索问答。

不太适合：

- 根本没有稳定知识源，答案主要依赖开放式推理；
- 问题需要复杂长链条规划，而不是先查资料再作答；
- 数据变动频繁但又无法及时更新索引；
- 对答案正确性要求极高，但检索证据本身并不完整。

要注意，RAG 也不是所有知识问题的终点。

有些场景更适合：

- 微调：当你要改变模型输出风格、格式、行为模式，而不是补充事实知识时；
- 工作流或 Agent：当问题不只是“找资料并回答”，而是需要多步操作、调用工具、执行任务时。

## 最后的理解

如果只用一句话概括，我会这样理解 RAG：

RAG 的本质，是把“知识查找”和“语言生成”拆开，让模型在回答前先拿到足够相关的外部证据。

它解决的不是模型会不会说，而是模型回答时有没有根据。

从工程上看，RAG 真正的难点也不在“接上模型”，而在于整个知识链路是否可靠：

- 文档有没有被正确解析；
- chunk 切得是否合适；
- 检索能不能召回正确证据；
- 排序能不能把真正有用的内容放到前面；
- 生成时能不能尽量依据证据回答。

所以一个好的 RAG 系统，最终拼的不是某个单点技巧，而是整条链路的协同质量。
