# Vue 渲染机制

Vue 的一次更新，整体可以理解成一条链路：

`响应式数据变化 -> 调度更新 -> 执行组件 render effect -> 生成新 vnode -> patch -> 更新真实 DOM`

- `响应式数据变化`：触发依赖这份数据的副作用；
- `调度更新`：把组件更新任务放进队列，同一轮事件循环里尽量合并；
- `render effect`：重新执行组件渲染函数，得到新的 vnode 树；
- `patch`：比较新旧 vnode，把必要的变化提交到真实 DOM。

## 一次更新的主线

Vue 组件第一次挂载时，模板会被编译成 render function。运行时执行 render function，得到一棵 vnode 树，再把 vnode 挂载成真实 DOM。这个过程会作为一个响应式副作用执行，所以 render 过程中读取到的响应式数据会被记录成依赖。

当这些依赖后续发生变化时，Vue 不会立刻同步重跑所有逻辑，而是把对应组件的更新任务交给调度器。调度器负责去重、排序和异步刷新，真正刷新时再重新执行组件的 render effect，生成新的 vnode，并进入 patch。

```d2
direction: right

A: 响应式数据变化
B: trigger 依赖
C: 组件更新任务入队
D: 已在队列中? {
  shape: diamond
  class: decision
}
E: 跳过去重
F: 等待队列刷新
G: 执行 render effect
H: 生成新 vnode
I: patch 新旧 vnode
J: 更新真实 DOM {
  class: ok
}

A -> B -> C -> D
D -> E: 是
E -> F
D -> F: 否
F -> G -> H -> I -> J
```

这条链路里有两个边界要分清：

- 响应式系统只负责知道“谁依赖了谁”，不直接操作 DOM；
- renderer 只负责把 vnode 同步到宿主环境，不关心数据为什么变化。

中间的调度器把两者连接起来。它决定什么时候刷新、同一组件重复触发时如何去重，以及用户写的 `nextTick` 应该等到哪个时机再执行。

## 响应式触发更新

Vue 3 的响应式系统以 `Proxy` 和 effect 为基础。组件挂载时，Vue 会为组件创建一个渲染副作用。这个副作用执行组件的 render function，render 过程中读取到的响应式属性，会通过 `track` 被记录下来。

可以把这个过程理解成：组件在渲染时顺手登记了自己用过哪些数据。

```ts
const state = reactive({ count: 0 })

effect(() => {
  // 读取 count 时建立依赖
  render(state.count)
})

// 修改 count 时触发依赖
state.count++
```

真实组件里不是直接调用上面这个 `effect`，但思路接近：组件 render effect 会收集依赖，依赖变化时，`trigger` 找到这些 effect，再通过 scheduler 安排组件更新。

这一层最关键的是“精确触发”。如果某个组件渲染时没有读到 `state.count`，那么 `state.count` 变化就不应该让它更新。Vue 的更新粒度不是从根节点无条件重跑，而是从响应式依赖能触达的组件更新任务开始。

## 调度更新

响应式数据可能在同一个同步流程里被修改多次。如果每次修改都立刻重新渲染，页面会做很多重复工作。所以 Vue 会把组件更新放进 job queue，等当前同步代码执行完后，再统一刷新。这个异步刷新通过注册 microtask（`Promise.then`）实现。同步代码执行完后，微任务队列自然触发，Vue 在回调中执行所有排队的组件更新。

一个典型例子是：

```ts
count.value++
count.value++
count.value++
```

这三次修改会触发依赖三次，但同一个组件的更新任务只需要进入队列一次。最终刷新时，组件只用最新状态渲染一次。

调度阶段主要做三件事：

- 去重：同一个组件更新任务在同一轮刷新里只执行一次；
- 排序：父组件通常先于子组件更新，避免子组件在过期父状态下重复执行；
- 延后：把 DOM 更新推迟到当前调用栈结束后批量处理。

`nextTick` 等的就是这一批更新刷新完成后的时机。它不是让数据“下一次才变化”，数据在赋值时已经变了。它等的是 Vue 把由这次数据变化引发的 DOM patch 做完。

```d2
direction: down

A: 同步代码修改响应式数据
B: 多次 trigger
C: 收集组件更新 job
D: 队列刷新中? {
  shape: diamond
  class: decision
}
E: 复用本轮刷新
F: 创建微任务刷新队列
G: 执行组件更新
H: 执行 nextTick 回调 {
  class: ok
}

A -> B -> C -> D
D -> E: 是
D -> F: 否
E -> G
F -> G
G -> H
```

## Render 阶段

Vue 的 render 阶段，核心是执行 render function，得到新的 vnode 树。

如果使用模板，模板会先被编译成 render function。这个过程可以发生在构建阶段，也可以在带编译器的运行时版本中即时发生。生产项目里更常见的是构建阶段编译，因为这样 runtime 可以直接执行生成好的渲染函数。

一个模板：

```vue
<template>
  <button :class="{ active }">{{ count }}</button>
</template>
```

会被编译成大致类似这样的 render 逻辑：

```ts
function render(ctx) {
  return createVNode('button', { class: { active: ctx.active } }, ctx.count)
}
```

这里的重点不是代码长什么样，而是职责边界：render function 只描述“这一刻 UI 应该是什么结构”。它返回的是 vnode，不是真实 DOM。

vnode 是一份普通 JavaScript 对象，描述节点类型、属性、子节点、key、patch flag 等信息。renderer 后续会拿这份描述和上一轮 vnode 对比，再决定真实 DOM 怎么变。

## Patch 阶段

Patch 阶段负责把 vnode 同步到真实 DOM。第一次挂载时，没有旧 vnode，renderer 会根据 vnode 创建 DOM，这叫 mount。更新时，Vue 同时拿到旧 vnode 和新 vnode，比较两者并应用必要变化，即 patch。

```d2
direction: down

A: 新 vnode
B: 有旧 vnode? {
  shape: diamond
  class: decision
}
C: mount
D: 创建真实 DOM
E: patch
F: type 相同? {
  shape: diamond
  class: decision
}
G: 卸载旧节点并挂载新节点
H: 复用节点并更新 props
I: patch children
J: DOM 更新完成 {
  class: ok
}

A -> B
B -> C: 否
C -> D -> J
B -> E: 是
E -> F
F -> G: 否
G -> J
F -> H: 是
H -> I -> J
```

单个节点的判断比较直接：如果新旧 vnode 的 `type` 不同，通常就不能复用旧节点，需要卸载旧节点再挂载新节点。如果 `type` 相同，就可以复用已有 DOM，再更新属性、事件和子节点。

列表更新会更复杂。Vue 会根据 `key` 判断同一层里的节点能否复用，再处理插入、删除和移动。`key` 的意义不是“让列表更快”这么简单，而是帮助 renderer 判断：这个新 vnode 和哪个旧 vnode 表示同一个真实节点。

组件也是 vnode。patch 到组件 vnode 时，Vue 会判断组件是否需要更新。如果需要，就重新执行这个组件的 render effect，得到组件子树的新 vnode，再继续向下 patch。也就是说，组件更新和 DOM 更新之间隔着一层 vnode 子树计算。

patch 完成后，Vue 会更新组件上关联的模板 ref 和 `vnode.ref` 的回调，作为 render effect 收尾的一步。

## 编译器优化

Vue 渲染机制不是纯运行时的虚拟 DOM，它同时掌握模板编译器和 runtime，所以编译器可以提前分析模板，把运行时需要的提示写进生成代码里。

常见优化有三类。

第一类是静态提升。模板中完全不依赖响应式数据的节点，可以在编译阶段被提到 render function 外面，或者在初次创建后复用。这样组件重新渲染时，不必反复创建这些静态 vnode。

第二类是 `patch flag`。如果编译器能判断某个节点只会变化 `class`、`style`、文本内容或某几个 props，就会在 vnode 上标记对应的更新类型。patch 时，runtime 可以直接走更窄的更新路径，而不是把所有 props 都完整比较一遍。

第三类是 block tree，一个 block 对应模板根节点或 `v-if`/`v-for` 等结构化指令的边界，会收集内部有动态绑定的后代节点。组件重新渲染时，Vue 可以优先遍历这些动态节点，而不是把整棵模板树从头到尾都 diff 一遍。

```d2
direction: right

Compiler: 模板编译器 {
  class: group
  A: 分析模板结构
  B: 提升静态节点
  C: 标记 patch flag
  D: 收集 dynamic children
}

Runtime: 运行时 patch {
  class: group
  E: 复用静态 vnode
  F: 按 flag 更新动态字段
  G: 优先遍历动态节点
  H: 更少 DOM 操作 {
    class: ok
  }
}

Compiler.A -> Compiler.B -> Runtime.E
Compiler.A -> Compiler.C -> Runtime.F
Compiler.A -> Compiler.D -> Runtime.G
Runtime.E -> Runtime.H
Runtime.F -> Runtime.H
Runtime.G -> Runtime.H
```

这也是 Vue 推荐模板的原因之一。模板语法更受约束，编译器更容易静态分析；render function 更灵活，但很多结构信息只能留到运行时再判断。

## 和 React 的几个关键差别

React 和 Vue 都可以使用虚拟 DOM，但两者的更新入口和优化重心不同。

React 的更新会被调度到 Root，再从 Root 进入 Fiber workLoop。实际计算过程中，React 通过优先级、bailout、memo 等机制减少不必要的子树展开。Vue 的入口更依赖响应式追踪：组件 render 过程中读了哪些响应式数据，后续这些数据变化时才会触发对应组件的更新任务。

调度模型也不一样。React 的并发渲染强调不同优先级任务之间的中断、恢复和让出执行权。Vue 的默认更新调度更偏向批处理：同一轮同步代码里多次状态变化会被合并到一个异步刷新队列里，再统一执行组件更新。

优化重心也不同。React 主要在运行时依靠 Fiber、lane、bailout 等机制控制工作量；Vue 则把模板编译器也纳入渲染优化，让 runtime 在 patch 时知道哪些节点是静态的、哪些字段是动态的、哪些后代需要重点遍历。

所以不能简单说谁“更细”或“更快”。更准确的说法是：React 把更多问题放在运行时调度和 Fiber 结构里解决；Vue 则用响应式依赖定位更新来源，再用编译器提示减少 patch 阶段的无效工作。

## 总结

Vue 渲染机制的主线：响应式系统负责触发，调度器负责合并，render effect 负责生成 vnode，patch 负责把必要变化落到真实 DOM。

理解这条链路后，很多现象会更清楚：为什么连续修改状态通常只渲染一次，为什么 `nextTick` 能拿到更新后的 DOM，为什么列表需要稳定的 `key`，以及为什么模板写法会影响运行时性能。Vue 不是绕开 DOM 更新成本，而是把它拆开处理：先通过响应式系统减少无关组件更新，再通过调度器减少重复更新，最后通过编译器提示和 patch 算法减少真实 DOM 操作。
