# 微前端：架构决策与运行原理

微前端不是把一个前端仓库拆成多个目录，也不是同时运行多个框架。它要解决的是：当业务和团队扩张后，如何把一个前端系统拆成若干边界清晰、可以独立交付的应用，同时保持一致的用户体验。

一套微前端方案首先要回答两个问题：

- 为什么要拆，拆分带来的收益能否覆盖额外成本；
- 拆分后的应用如何加载、运行、隔离和通信。

本文讨论与具体框架无关的架构决策和运行原理。

## 为什么需要微前端

### 单体前端何时会成为瓶颈

单体前端并不等于设计落后。对大多数中小型系统来说，一个仓库、一套构建流程和一次整体发布通常更简单，也更可靠。代码量大或使用时间长，同样不足以成为引入微前端的理由。

真正的问题是业务边界、团队边界和交付边界开始相互冲突：

| 现象                                     | 背后的约束                   |
| ---------------------------------------- | ---------------------------- |
| 多个团队频繁修改同一入口、路由和依赖     | 所有团队共享同一个变更边界   |
| 一个局部需求也要等待整站回归和统一发布   | 所有模块共享同一个交付周期   |
| 升级框架或构建工具时必须一次改完整个系统 | 技术依赖缺少可独立演进的边界 |
| 某个模块加载或运行失败会阻塞整个页面     | 故障边界与应用边界重合       |
| 仓库权限、代码评审和责任归属越来越模糊   | 代码结构没有反映业务所有权   |

如果这些问题只是偶尔发生，优先通过模块化、按领域分包、Monorepo 增量构建和优化发布流程解决。只有当多个团队确实需要按照不同节奏长期交付，单体的协调成本才可能高于微前端的治理成本。

### 微前端的本质：围绕业务边界独立交付

微前端把一个前端系统按业务能力拆成多个应用。每个应用拥有明确的负责人，可以独立开发、构建、测试和发布；主应用负责把它们组合成一个连续的产品体验。

这里的关键单位是**可独立交付的业务应用**，而不是任意组件。订单、客户管理、财务中心通常可以形成边界；按钮、弹窗或一张表格通常不应该单独成为微应用。

```d2
direction: down

platform: 微前端系统 {
  class: group

  shell: 主应用 {
    class: subgroup
    router: 路由与应用编排
    session: 登录态与权限策略
    layout: 全局布局与导航
    observability: 监控与错误兜底
  }

  apps: 业务应用 {
    class: subgroup
    customer: 客户管理
    order: 订单中心
    finance: 财务中心
  }

  delivery: 独立交付 {
    class: subgroup
    build: 独立构建
    deploy: 独立发布
    rollback: 独立回滚
  }
}

platform.shell -> platform.apps: 提供平台能力
platform.apps -> platform.delivery: 生成各自产物
platform.delivery -> platform.shell: 发布应用入口
```

拆分后仍然需要共享登录态、导航、设计语言和监控能力。微前端不是消除依赖，而是把依赖从隐式代码耦合改成显式平台契约。

### 适用场景、引入成本与决策边界

微前端更适合下面这些场景：

- 系统包含多个相对独立的业务域，并且由不同团队长期负责；
- 各业务域的发布频率、技术演进节奏或稳定性要求明显不同；
- 旧系统无法一次重写，需要按路由逐步替换；
- 平台需要接入不同组织维护的应用，并为它们提供统一入口。

以下情况通常不适合：

- 团队规模小，所有模块始终一起规划和发布；
- 页面之间共享大量细粒度状态，业务边界尚未形成；
- 当前问题主要来自代码质量、构建速度或职责混乱；
- 团队还没有独立 CI、监控、灰度和回滚能力。

引入前至少要确认四件事：

1. 能否按业务能力划出稳定边界；
2. 每个边界是否有明确的长期负责人；
3. 是否真的需要独立发布，而不只是独立开发；
4. 是否愿意承担应用编排、契约兼容、运行隔离和可观测性的建设成本。

如果第四项没有投入计划，拆分只会把单体内部的问题变成分布式前端问题。

## 主流方案如何选择

微前端是一种架构方式，不等于某个框架。iframe、运行时应用编排和 Module Federation 解决的问题不同，也可以组合使用。

| 方案                 | 组合粒度   | 隔离能力                     | 独立部署 | 主要代价                           |
| -------------------- | ---------- | ---------------------------- | -------- | ---------------------------------- |
| iframe               | 页面或区域 | 最强                         | 支持     | 路由、通信、弹层和体验整合成本高   |
| single-spa / qiankun | 路由级应用 | 依赖框架提供的沙箱和样式策略 | 支持     | 所有应用仍共享同一个页面环境       |
| Module Federation    | 模块或应用 | 默认不提供运行隔离           | 支持     | 构建体系、共享依赖和版本协商更复杂 |

### iframe：浏览器原生隔离

iframe 为子应用创建独立的浏览上下文、`Window` 和 `Document`。子应用的全局变量、样式和路由天然不会直接进入主页面；跨域时，同源策略还会限制双方读取彼此的 DOM 和 JavaScript 对象。

这种边界适合下面几类系统：

- 难以改造的遗留应用；
- 需要接入第三方页面的开放平台；
- 对运行隔离要求高于交互一致性的后台模块；
- 无法信任或无法约束其全局副作用的应用。

代价也很明确：主子页面需要通过 `postMessage` 等机制通信，浏览器历史、页面高度、焦点、快捷键、全局弹层和无障碍语义都要额外协调。每个 iframe 还拥有独立的文档和运行环境，重复加载依赖的概率更高。

iframe 提供的是边界，不自动提供良好的集成体验。同源 iframe 仍然可以主动访问 `parent`，因此还需要权限约束；微前端框架中的 JavaScript 沙箱则主要防止意外污染，不能替代 iframe 或浏览器安全机制。

### single-spa 与 qiankun：运行时应用编排

[single-spa](https://single-spa.js.org/docs/building-applications/) 把子应用抽象成带生命周期的模块。主应用根据当前 URL 判断哪些应用应该激活，再调用它们的 `bootstrap`、`mount` 和 `unmount`。它主要解决路由级应用编排，不规定仓库、构建、部署和样式隔离方案。

[qiankun](https://github.com/umijs/qiankun) 基于 single-spa，进一步提供 HTML Entry、JavaScript 沙箱、样式隔离和资源预加载等能力。子应用可以保留接近普通 SPA 的构建产物，主应用从 HTML 入口解析脚本和样式，再把应用挂载到指定容器。

这类方案适合以路由为主要边界、需要渐进改造现有 SPA 的系统。它能降低接入成本，但主应用和所有子应用仍运行在同一个页面中，共享 DOM、浏览器 API 和主线程。沙箱只能约束框架能够拦截的访问，不能形成安全边界。

### Module Federation：远程模块加载与依赖共享

[Module Federation](https://webpack.js.org/concepts/module-federation/) 允许多个独立构建在运行时暴露和消费模块。工程中通常把提供模块的一方称为 remote，把消费模块的一方称为 host；从 webpack 的协议看，二者都可以是既提供又消费模块的容器。remote 通常先发布一个 `remoteEntry.js`，其中的容器暴露 `init` 和 `get` 接口。host 先初始化本地共享作用域，再调用远程容器的 `init` 让其了解可用的共享模块，最后通过 `get` 获取指定模块。

```d2
direction: right

A: Host 加载 remoteEntry
B: Host 初始化共享作用域
C: Host 调用 container.init
D: Host 调用 container.get
E: 执行模块工厂
F: Host 使用模块

A -> B -> C -> D -> E -> F
```

它解决的是**独立构建之间如何在运行时加载代码和共享依赖**，并不自动提供路由编排、应用生命周期、JavaScript 沙箱或样式隔离。把远程模块作为完整应用加载时，双方仍然需要约定挂载、卸载和错误处理接口。

Module Federation 更适合同一技术体系下的模块复用，或者需要细粒度动态组合的系统。它也可以和 single-spa 配合：single-spa 决定何时激活应用，Module Federation 负责加载应用模块和协商共享依赖。

### 如何对比并组合不同方案

选型时先判断需要哪一种边界：

- 需要浏览器级运行隔离，优先考虑 iframe；
- 需要按路由组合多个完整 SPA，优先考虑 single-spa、qiankun 或同类编排方案；
- 需要跨独立构建动态加载模块，考虑 Module Federation；
- 同时需要应用编排和远程模块加载，可以组合运行时编排与 Module Federation。

不要只比较“是否支持 React/Vue”。更重要的是现有应用能改造到什么程度、是否允许共享运行环境、部署入口如何切换，以及团队能否处理跨版本契约。

## 应用如何加载和运行

### 主应用如何根据路由匹配子应用

为便于说明，可以把一个路由级微应用抽象成四项注册信息。下面是本文使用的通用模型，不对应某个框架的原生 API：

```ts fold title="src/micro-app-contract.ts"
type MicroAppRegistration = {
  name: string
  entry: string
  container: string
  activeWhen: (location: Location) => boolean
}
```

- `name` 标识应用，也用于日志、缓存和沙箱命名；
- `entry` 指向应用入口；
- `container` 指定渲染位置；
- `activeWhen` 根据 URL 判断应用是否应该激活。

浏览器触发 `popstate` 或 `hashchange` 时，编排器可以重新计算活动应用。`history.pushState` 和 `history.replaceState` 本身不会触发 `popstate`，因此运行时通常还要包装这两个方法，在 URL 被代码修改后主动调度一次应用切换。

概念上的切换流程如下。具体框架可能并行加载资源或调整卸载顺序，但状态转换基本一致：

```d2
direction: down

A: URL 发生变化
B: 计算新的活动应用集合
C: 卸载不再匹配的应用
D: 目标应用已加载 {
  shape: diamond
  class: decision
}
E: 加载并执行入口资源
F: 目标应用已初始化 {
  shape: diamond
  class: decision
}
G: 执行 bootstrap
H: 执行 mount
I: 应用进入运行状态

A -> B -> C -> D
D -> F: 是
D -> E: 否
E -> F
F -> H: 是
F -> G: 否
G -> H -> I
```

主应用只负责决定应用是否活动。子应用挂载后，其内部路由仍应由自己处理，避免主应用知道每个业务页面的细节。

### HTML Entry、JS Entry 与 Remote Entry 如何加载资源

三种入口代表不同的加载协议：

| 入口         | 加载过程                                    | 子应用需要暴露的内容     | 主要特点                       |
| ------------ | ------------------------------------------- | ------------------------ | ------------------------------ |
| HTML Entry   | 获取 HTML，解析并加载其中的脚本和样式       | 生命周期函数             | 接近普通 SPA 产物，接入方便    |
| JS Entry     | 通过 ESM、SystemJS 或脚本地址加载模块       | 生命周期函数             | 协议直接，入口和样式需自行管理 |
| Remote Entry | 加载远程容器，再调用 `init`、`get` 获取模块 | 远程模块及双方约定的接口 | 支持独立构建和共享依赖         |

HTML Entry 的重点不是把完整 HTML 嵌入页面，而是把 HTML 当作资源清单。加载器先获取入口文件，以入口 URL 为基准解析相对路径，再加载样式和脚本，最后从脚本执行结果中取得生命周期。

JS Entry 直接把子应用当作浏览器模块加载。入口形态与模块寻址方式相互独立：它既可以通过原生动态 `import()` 或 SystemJS 加载，也可以配合 import map，把稳定的模块名映射到不同版本 URL。切换映射即可发布或回滚，不必重新构建主应用。

Remote Entry 先建立一个远程容器。host 初始化本地共享作用域后，把它传给远程容器的 `init`，再调用 `get` 获取模块工厂；执行工厂才得到真正的模块导出。这个协议负责取代码，不负责决定模块如何渲染。

无论使用哪种入口，跨域加载都要同时处理 CORS、CSP 和资源地址。运行时代码最终拥有当前页面授予的权限，因此入口来源必须可信。

### bootstrap、mount、update、unmount 如何协作

生命周期把“加载代码”和“产生页面副作用”分开。下面是一份通用契约：

```ts fold title="src/micro-app.ts"
type PlatformAPI = {
  navigate: (path: string) => void
  reportError: (error: unknown) => void
}

type LifecycleProps = {
  container: HTMLElement
  platform: PlatformAPI
}

type MicroAppModule = {
  bootstrap: (props: LifecycleProps) => Promise<void>
  mount: (props: LifecycleProps) => Promise<void>
  update?: (props: LifecycleProps) => Promise<void>
  unmount: (props: LifecycleProps) => Promise<void>
}
```

各阶段的职责应保持稳定：

- `bootstrap`：执行一次性初始化，不渲染依赖当前容器的页面；
- `mount`：创建框架根节点、渲染页面并注册本次运行需要的副作用；
- `update`：在不重新挂载时接收新的外部参数，在 single-spa 等主流编排器中属于可选生命周期；
- `unmount`：销毁页面并清理本次挂载产生的资源。

以 single-spa 应用为例，`bootstrap`、`mount` 和 `unmount` 是必需生命周期，且都要返回 Promise；`bootstrap` 通常只在首次挂载前执行一次，`mount` 和 `unmount` 可以重复发生。应用被显式 unload 后，后续才会重新进入加载和初始化过程。

不要在模块顶层修改 DOM、注册监听或启动定时器：加载完成不代表应用已激活，且无法归属到某次 `mount` 的副作用，在 `unmount` 时也难以准确恢复。

### 静态资源路径、预加载与缓存如何处理

子应用独立部署后，页面地址、入口地址和静态资源地址往往不在同一个域名。例如主页面位于 `/portal/orders`，子应用入口可能位于 CDN 的 `/orders/20260722/index.html`。如果构建产物把分包写成 `/assets/chunk.js`，浏览器会错误地请求主站根路径。

常见处理方式有三种：

- 构建时为每个应用配置稳定的资源前缀；
- 运行时根据入口 URL 或 `document.currentScript.src` 推导 public path；
- 由主应用在加载前向子应用注入资源基地址。

发布时应把入口和内容资源分开管理：

- 带内容哈希的 JS、CSS 和图片使用长期缓存并保持不可变；
- manifest、import map 或 HTML 入口使用短缓存，并支持原子切换版本；
- 回滚时切换入口指针，不覆盖已经发布的旧文件。

预加载只适合高概率即将访问的应用。可以在浏览器空闲、网络状况允许且核心页面加载完成后获取资源，但不要提前执行会产生副作用的业务代码。盲目预加载所有子应用，只会把首屏之后的带宽竞争提前发生。

## JavaScript 与样式如何隔离

### 全局变量和副作用为什么会相互污染

除 iframe 外，主应用和子应用通常共享同一个 `Window`、`Document` 和 JavaScript 主线程。任何应用都可能修改公共环境：

| 污染类型   | 例子                           | 可能结果                   |
| ---------- | ------------------------------ | -------------------------- |
| 全局变量   | 写入 `window.app`              | 后加载的应用覆盖同名属性   |
| 原型修改   | 修改 `Array.prototype`         | 所有应用的运行行为变化     |
| 全局监听   | 监听 `window.resize`           | 卸载后逻辑继续执行         |
| 定时任务   | `setInterval`                  | 应用离开后仍然占用资源     |
| 动态资源   | 向 `<head>` 插入脚本和样式     | 资源无法随应用卸载         |
| 构建运行时 | 使用相同 JSONP 或 chunk 全局名 | 不同构建的模块注册发生冲突 |

隔离需要分别处理两类问题：沙箱约束全局对象的读写，副作用管理负责事件、定时器、DOM 和订阅的创建与销毁。只做其中一项并不完整。

### 快照沙箱与 Proxy 沙箱如何工作

快照沙箱直接操作真实 `window`。激活应用时保存全局属性，停用时比较前后差异，记录应用改过的值并把环境恢复到快照；再次激活时重新应用这些改动。

它的优势是可以兼容不支持 `Proxy` 的旧环境，限制也很明显：

- 激活和停用都要遍历大量全局属性；
- 应用实际修改的仍是真实 `window`；
- 两个应用同时运行时，无法为它们提供各自独立的全局状态；
- DOM、原型链和异步副作用不会因为恢复属性而自动消失。

Proxy 沙箱为每个应用创建一个代理对象。读取属性时先从应用自己的对象查找，找不到再读取真实全局；写入时优先落到应用自己的对象，从而让多个应用看到不同的“全局变量”。执行子应用脚本时，加载器需要让代码中的 `window`、`self` 和 `globalThis` 尽可能指向这个代理。

这种方式支持更细的读写拦截，也更适合多个应用同时挂载，但仍有边界：部分不可配置属性必须读取真实对象，原生方法可能需要重新绑定真实 `window`，间接 `eval`、原型修改和主动获取原始全局对象都可能绕过代理。

因此 JavaScript 沙箱的目标是**减少应用之间的意外污染，并帮助恢复运行环境**，而不是执行不可信代码。安全隔离应使用 iframe、CSP、同源策略和独立权限边界。

### scoped CSS、选择器改写与 Shadow DOM 有何差异

样式隔离既要防止子应用样式泄漏，也要防止主应用规则误伤子应用。常见方案如下：

| 方案           | 原理                          | 优点                       | 边界                                             |
| -------------- | ----------------------------- | -------------------------- | ------------------------------------------------ |
| CSS Modules    | 构建时生成局部类名            | 自动处理大部分组件类名冲突 | 无法约束全局选择器和动态样式                     |
| BEM 等命名约定 | 人工为选择器增加稳定前缀      | 不依赖构建工具             | 依赖团队持续遵守约定                             |
| 选择器前缀     | 把规则改写到应用容器下        | 可以在普通 DOM 中运行      | `html`、`body`、`@keyframes`、弹层等需要额外处理 |
| Shadow DOM     | 把 DOM 和样式放入 Shadow Root | 浏览器原生提供样式边界     | 主题继承、全局弹层和组件库兼容需要适配           |
| iframe         | 使用独立 Document             | 隔离最完整                 | 集成和通信成本最高                               |

所谓 scoped CSS 通常是给应用容器添加唯一属性，再把 `.button` 改写成类似 `[data-micro-app='order'] .button` 的选择器。它能减少普通规则冲突，但运行时插入的样式也必须经过同样处理；挂到 `document.body` 的弹窗不在容器内，同样不会命中前缀规则。

[Shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM) 会建立真正的样式边界：页面选择器默认不能选中 Shadow Tree 内部节点，内部样式也不会直接作用到外部。它仍然不是完全封闭的视觉环境，继承属性和 CSS 自定义属性可以通过宿主传入，弹层容器、字体和主题 token 也需要显式设计。

没有一种方案可以无成本兼容所有历史应用。新应用优先通过 CSS Modules、低特异性选择器和统一 token 避免污染；只有确实存在冲突时，再增加运行时前缀或 Shadow DOM。

### 卸载应用时如何清理全局副作用

一个应用从页面上消失，不代表它已经停止运行。`unmount` 至少要清理：

- 框架根节点和应用创建的额外 DOM；
- `window`、`document` 和媒体查询上的事件监听；
- `setTimeout`、`setInterval`、`requestAnimationFrame`；
- Observer、消息通道、WebSocket 和事件总线订阅；
- 尚未完成的请求和异步任务；
- 动态插入的 `<style>`、`<link>` 和 `<script>`。

可以把每次挂载产生的释放函数统一收集：

```ts fold title="src/micro-app.ts"
let disposers: Array<() => void> = []

function handleResize() {
  renderResponsiveLayout()
}

export async function mount() {
  window.addEventListener('resize', handleResize)
  const timer = window.setInterval(refreshData, 30_000)
  const unsubscribe = platform.events.subscribe('session:changed', refreshSession)

  disposers = [() => window.removeEventListener('resize', handleResize), () => window.clearInterval(timer), unsubscribe]
}

export async function unmount() {
  disposers
    .splice(0)
    .reverse()
    .forEach((dispose) => dispose())
  destroyApplicationRoot()
}
```

编排框架可以通过包装浏览器 API 帮助记录副作用，但子应用仍应主动清理。框架很难可靠拦截闭包中的异步任务、第三方库内部资源以及逃逸到真实全局对象的操作。

## 应用如何通信和共享依赖

### Props、事件与共享状态分别适合什么场景

通信方式应根据数据语义选择，而不是统一塞进一个全局 store：

| 方式           | 适合的数据                     | 耦合特点                     |
| -------------- | ------------------------------ | ---------------------------- |
| URL            | 当前页面、筛选条件、可分享状态 | 标准化，可刷新和回退         |
| 生命周期 Props | 容器、平台 API、启动参数       | 主应用到子应用的显式依赖     |
| 领域事件       | 登录态变化、订单已提交等事实   | 发布方不依赖具体订阅方       |
| 后端 API       | 持久业务数据                   | 以后端模型作为事实来源       |
| 共享内存状态   | 少量全局瞬时状态               | 实时，但最容易形成运行时耦合 |

可导航的状态优先放在 URL 中，持久业务状态由后端负责。事件适合表达“已经发生的事实”，不适合模拟跨应用函数调用。共享内存只保留当前用户、语言、主题等确实属于整个平台的数据，业务表单和页面交互状态应留在各自应用内。

如果两个应用需要持续同步大量 UI 状态，通常说明它们拆得过细。合并边界往往比增加复杂的状态同步协议更可靠。

### 如何用通信契约控制跨应用耦合

事件名只是契约的一部分。一个可维护的通信契约还要定义：

- 事件或方法的负责人；
- 请求参数、返回值和错误语义；
- 字段的兼容策略和废弃周期；
- 重复投递、乱序和订阅时机如何处理；
- 调用失败是否影响当前应用。

可以用 TypeScript 为平台事件建立集中映射：

```ts fold title="src/platform-events.ts"
type PlatformEventMap = {
  'session:changed': {
    userId: string | null
  }
  'order:submitted': {
    orderId: string
    occurredAt: string
  }
}

type PlatformEvents = {
  emit<K extends keyof PlatformEventMap>(name: K, payload: PlatformEventMap[K]): void
  subscribe<K extends keyof PlatformEventMap>(name: K, listener: (payload: PlatformEventMap[K]) => void): () => void
}
```

类型只能约束同时使用这份定义的代码，不能自动保证独立部署版本兼容。重要契约还应在 CI 中做 schema 或契约测试，并遵守“先扩展生产方、再迁移消费方、最后删除旧字段”的演进顺序。

### 主应用应提供哪些平台能力

主应用适合提供跨业务域且需要统一治理的能力，例如：

```ts fold title="src/platform-api.ts"
type PlatformAPI = {
  version: '1'
  navigate: (path: string) => void
  getCurrentUser: () => Promise<{ id: string; permissions: string[] } | null>
  hasPermission: (permission: string) => boolean
  events: PlatformEvents
  openGlobalDialog: (name: string, payload: unknown) => Promise<unknown>
  reportError: (error: unknown, context?: Record<string, string>) => void
}
```

平台 API 应暴露稳定能力，而不是主应用内部的路由实例、状态仓库或组件树。函数接口比共享可变对象更容易增加兼容层，也便于记录调用、处理错误和替换实现。

平台能力同样要版本化。主应用可以在注册子应用时声明自己支持的 API 版本，子应用入口也可以声明最低版本；版本不兼容时应阻止挂载并展示可诊断的降级页面，而不是运行到一半才报错。

### shared、singleton 与依赖版本冲突如何处理

Module Federation 的共享作用域允许 host 和 remote 提供同名依赖，由两端的共享配置和版本约束协商最终使用哪一份。

常见配置含义如下：

- `shared`：把依赖加入共享协商，而不是无条件打进每个消费模块；
- `singleton`：期望当前共享作用域只使用一个实例，适合无法安全共存多份实例的框架运行时；
- `requiredVersion`：声明消费方可接受的版本范围；
- `eager`：让共享模块进入同步加载路径，会增加初始资源，不应作为默认选项。

最终使用哪个实现取决于容器初始化顺序、依赖是否已经被消费、版本约束和回退配置，不能把共享作用域理解成简单的“先注册者覆盖后来者”。

共享越多，版本协调面越大。可以遵循以下原则：

1. 优先共享体积大、版本稳定且多实例可能出错的依赖；
2. 小型工具库允许重复打包，以换取独立升级；
3. 设计系统共享稳定的组件和 token，不共享业务组件；
4. 在发布前验证 host 与 remote 的版本组合；
5. 为远程入口加载失败、模块不存在和版本不兼容提供降级。

`singleton` 不能消除不兼容版本，只是把冲突集中到运行时协商。若多个应用必须同步升级大量依赖，它们实际上仍共享一个发布边界。

## 常见误区

- **拆分过细**：拆分粒度越细，入口、依赖、通信和发布单元越多。若几个模块总是一起修改、一起测试、一起发布，它们就不具备独立边界。优先从路由和业务域拆分，不要把组件化问题交给微前端解决。
- **全局状态制造隐式耦合**：让所有应用读写同一个 store 看似方便，却要求所有版本同时理解相同的状态结构和 action 语义。任何字段调整都可能影响整站。全局只保留真正的平台状态，跨业务数据通过 URL、事件或后端接口传递。
- **共享依赖阻碍独立升级**：把所有依赖都设置为 singleton 能减少重复资源，也会把应用升级重新绑定在一起。共享前要比较节省的体积和新增的版本协调成本，小依赖重复加载通常比全平台锁定版本更可控。
- **只拆代码，不拆团队与交付流程**：如果所有应用仍由同一批人维护、必须通过同一条流水线整体发布，微前端只增加了运行时复杂度。应用边界应该与责任、权限、监控和发布边界一致；否则更适合继续使用模块化单体。

## 总结：先确定边界，再选择实现

微前端首先是架构决策，其次才是框架选型。iframe 提供浏览器级边界，single-spa 和 qiankun 负责路由级应用编排，Module Federation 负责独立构建之间的远程模块加载；它们解决的问题不同，可以按实际边界组合。

做出决策时，顺序应该是：

1. 确认系统是否真的需要独立交付；
2. 按业务能力划出稳定的应用边界；
3. 根据隔离强度和组合粒度选择运行方案；
4. 用生命周期、平台 API 和通信契约约束应用协作。

如果系统不需要独立交付，模块化单体通常更简单。如果已经具备稳定的业务边界和长期自治团队，下一步才是把这些原则落实到具体框架中。
