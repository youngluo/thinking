# 门户微前端实现方案

这套门户把多个独立部署的前端应用装进同一个浏览器标签。应用构建为 Module Federation 容器，门户根据 URL 选择加载器，拉取远程入口并渲染页面。

## 架构设计一览

| 层面 | 方案 | 边界 |
| --- | --- | --- |
| 产物 | 应用输出远程入口和模块导出 | 容器不负责应用生命周期 |
| 编排 | 门户按 URL 寻址并选择加载器 | 没有统一注册表和激活规则 |
| 依赖 | 公共依赖走 externals，业务组件运行时解析 | 当前未启用 Module Federation `shared` 协商 |
| 隔离 | CSS Modules、主题和命名约定 | 应用仍共用 `window`，没有 JS 沙箱 |
| 通信 | props、事件总线和插槽 | 依赖协作约定 |
| 交付 | 固定入口、构建号副本和版本文件 | 刷新时才重新获取入口 |

```d2 fold
title: |md
  **门户微前端运行结构**
| {near: top-center}

build: 编译阶段 {
  entry: 远程入口
  vendor: 公共依赖
}

static: 静态目录 {
  remote: remoteEntry.js
  version: 版本文件
  assets: vendor 与页面资源
}

  route: URL 路由分流

}

  origin: 静态域
  apps: 应用配置
}

build.vendor -> static.assets
config -> portal.route
static.remote -> portal.loader: 按应用名取入口
portal.route -> portal.loader
portal.loader -> portal.render
```

子应用主要分为两条远程加载路径。普通子应用通常暴露 `Entry`，普通加载器按页签中的 `module` 取导出；如果该模块是 `Entry`，页面再由子应用内部路由决定。低代码子应用通过 `RemoteLoader` 加载，同样以 `Entry` 作为容器入口，再把页面名和承载上下文传入。第三方页面不属于子应用，不参与容器加载，单独使用 iframe。

## 一个链接如何加载成页面

主应用先根据 URL 匹配页签，再按类型渲染门户页面、第三方 iframe 或远程子应用。远程子应用统一进入 `RemoteModuleLoader`，再分流至普通加载器 `ModuleFederationLoader` 或低代码加载器 `UdcAppLoader`。后者解析 `currentRoute`，调用 `@seeyon/global` 导出的 `RemoteLoader` 组件。

| {near: top-center}

普通子应用从页签读取 `url` 和 `module`，入口如 `https://static.example.com/app-a/remoteEntry.js`；低代码子应用由 `RemoteLoader` 按应用名生成入口路径，再补上运行时静态域，固定获取 `Entry`，并把页面名和查询参数作为页面属性传入。两者都遵循 Module Federation 容器协议。`RemoteLoader` 是低代码链路中的 React 组件，不是这套协议本身。

下面是方案级伪代码，省略加载状态和错误边界，只保留组件分流、低代码路由传递和容器取模块。

```tsx fold
// RemoteModuleLoader 按应用类型选择实际加载组件
function renderRemoteTab(tabData) {
  const Loader = getIsUdcApp(tabData.appId) ? UdcAppLoader : ModuleFederationLoader;
  return <Loader {...tabData} />;
}

// UdcAppLoader 从当前路由解析页面名和查询参数，再交给共享 RemoteLoader
function renderUdcPage({ appId, currentRoute, properties }) {
  const { pageName, inParams } = resolveCurrentRoute(currentRoute);
  return (
    <RemoteLoader
      appName={appId}
      pageName={pageName}
      pageProps={{ inParams, ...properties }}
    />
  );
}

// 两种加载器各自加载 remoteEntry，执行后在 window 上注册容器
// 普通子应用：ModuleFederationLoader -> useDynamicScript -> remoteEntryLoader(url)
// 低代码子应用：RemoteLoader -> useLoadRemoteEntry -> getUrlByAppName(appName)

// 加载器内部按 Module Federation 协议获取暴露模块
async function loadExposedModule(appId, moduleName) {
  await __webpack_init_sharing__('default');
  const container = window[appId];
  try {
    await container.init(__webpack_share_scopes__.default);
  } catch (error) {
    // 容器初始化异常由加载器记录，随后继续尝试获取模块
    console.warn(error);
  }

  // 普通子应用使用页签的 module；低代码子应用使用 Entry
  const factory = await container.get(`./${moduleName}`);
  return factory();
}
```

## 依赖关系

公共依赖和业务组件走两条不同的链路。公共依赖在构建时 external 到全局变量，业务组件的导入在构建时改写为运行时解析。

```d2 fold
title: |md
  **依赖加载路径**
| {near: top-center}

app: 应用代码
external: externals
global: window 全局实例
businessImport: 业务组件导入
rewrite: 构建时改写
resolver: 运行时解析器
host: 宿主版本路由
platform: 平台版本路由
load: 动态加载

app -> external
external -> global: 框架、组件库、能力库
businessImport -> rewrite
rewrite -> resolver
resolver -> host
resolver -> platform
host -> load
platform -> load
load -> global: 注册组件实例
```

运行时解析器根据包名和调用上下文选择宿主或平台版本，再动态加载对应资源。它解决的是资源寻址，不等同于完整的依赖版本协商；缺少路由或资源时仍可能加载失败。

## 隔离与协作

### 样式隔离

符合约定的样式文件启用 CSS Modules，生产类名使用构建哈希。主题、图标和组件风格由固定的 link 标签管理，应用可以复用门户主题。未启用 CSS Modules 的样式仍是全局选择器，层级和命名需要应用自行约束。

### 脚本隔离

应用共用 `window`、框架实例和公共依赖，没有代理、快照或完整 JS 沙箱。容器、分片数组和入口启动器的全局名由应用名派生，应用名重复或自行写入全局时仍可能互相影响。

第三方页面通过 iframe 加载。门户不执行其脚本，也不共享框架和页面上下文；当前 iframe 没有统一的 `sandbox` 或通信协议。

### 生命周期

普通远程模块没有统一的挂载和卸载协议，门户通过 props 传递承载方式、页面参数和回调。低代码加载器额外提供页面就绪、渲染、卸载和销毁等回调。契约分散在加载器和页面之间，遗漏调用不会自动报错。

### 跨应用通信

- props 传递页面参数、承载信息和回调；
- 事件总线负责同窗口订阅和跨窗口 `postMessage`；
- 插槽按约定名称向宿主界面注入内容；
- 门户和应用各自维护状态，通过事件、全局句柄和会话存储传递少量共享信息。

## 交付与故障边界

部分生产构建路径会生成固定入口、带构建号的入口副本和版本文件。加载器首次加载入口时预取版本信息，页面主动刷新时才比较版本并重新获取入口；长期停留的页面不会自动切换到新产物。

一次加载是否成功，主要取决于以下条件：

| 环节 | 要求 | 失败表现 |
| --- | --- | --- |
| 路由 | 能解析出应用名和页面名 | 回到门户页面或抛出路径错误 |
| 静态资源 | 入口文件可访问 | 显示加载失败 |
| 容器注册 | 入口成功执行并注册容器 | 获取模块失败 |
| 模块导出 | 容器存在目标导出项 | 页面渲染失败 |
| 公共依赖 | 全局框架和资源已就位 | 入口或页面运行时报错 |

普通 Loader 提供基础的加载态和失败文本，低代码路径有页面级错误边界。入口文本来自静态域，加载后直接求值，因此构建产物、静态目录和模板替换链必须可信。当前源码未见远程入口签名或加载来源白名单。

## 与完整微前端方案的差异

| 能力 | 当前方案 | 边界 |
| --- | --- | --- |
| 应用编排 | URL 寻址和加载器分流 | 没有统一注册与激活模型 |
| 生命周期 | props 回调 | 没有统一协议和自动校验 |
| JS 隔离 | 共用 `window` | 全局副作用需要自行清理 |
| 样式隔离 | CSS Modules 与主题约定 | 全局选择器仍可能冲突 |
| 依赖管理 | externals 与运行时解析 | 不提供完整版本协商 |
| 通信 | props、事件和插槽 | 命名与数据结构依赖约定 |

这套方案把主要复杂度放在构建脚手架、加载器和协作约定上。它适合已有应用沿用现有构建方式接入门户，但隔离、生命周期和依赖协商能力需要应用共同遵守约定。

本文只描述 PC 门户的主加载链路，具体应用名、业务属性和后端实现均已抽象化。
