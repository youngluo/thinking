# 门户微前端实现方案

一套企业门户的前端，十个可独立部署的应用、上百个业务控件包，加上配置产出的出盘子应用与客户自写页面，要在同一个浏览器标签里表现成一个产品。每个应用构建成一个模块联邦容器，门户按地址加载容器，编排由自研加载器承担，依赖共用走 externals 与运行期解析两条路。

对照[《微前端：架构决策与运行原理》](./架构决策与运行原理.md)的四件事项，这套方案的答案都指向同一个前提，所有应用跑在同一份运行时里。加载走模块联邦容器，通信走 props 与事件总线，隔离靠构建期哈希类名与命名前缀，版本协调靠交付纪律。

## 架构设计一览

| 层面 | 设计 | 承担方 |
| --- | --- | --- |
| 产物 | 每个应用构建成模块联邦容器，只当产物格式用，不启用生命周期语义 | 构建脚手架 |
| 编排 | 自研加载器，URL 路径段即应用名，没有注册表与激活规则 | 平台能力库 |
| 依赖 | 公共依赖 external 到 window 全局，业务控件的导入改写成运行期解析 | 构建脚手架与门户 |
| 隔离 | 构建期 CSS Modules 哈希类名，全站共用一份主题标签，运行时不做沙箱 | 构建脚手架 |
| 通信 | props 下发回调与承载形态，跨应用广播走事件总线，状态不共享 | 门户主应用 |
| 交付 | 稳定入口地址加构建号旁路副本，双路比对决定是否刷新 | 构建脚手架与静态目录 |

## 产物与依赖关系

主链自上而下三段，编译时决定应用被装配成什么容器，静态产物决定文件落在哪个目录，运行时决定谁的入口被谁取走。配置来源挂在旁边，不参与寻址。

```d2
direction: down

build: 编译时 {
  class: group
  grid-columns: 3
  grid-gap: 28
  cli: 构建脚手架 { width: 220 }
}

site: 静态产物 {
  class: group
  grid-columns: 3
  grid-gap: 28
  entry: 每个应用一份远程入口 { width: 220 }
  pkg: 公共依赖包 { width: 220 }
}

conf: 配置来源 {
  class: group
  grid-rows: 4
  grid-gap: 20
  origin: 静态域与租户前缀 { width: 220 }
  appcfg: 后端下发的应用配置 { width: 220 }
  namelist: 内置应用名单 { width: 220 }
  libver: 组件库版本表 { width: 220 }
}

run: 运行时 {
  class: group
  grid-columns: 3
  grid-gap: 28
  portal: 门户主应用 { width: 220 }
  biz: 业务子应用 { width: 220 }
  gen: 出盘子应用 { width: 220 }
}

build -> site: 产出入口与公共包
site -> run: 按 URL 取入口，共用依赖
conf -> run: 提供静态域、宿主与版本
```

子应用按产物形态只有两类，业务子应用与低代码搭建应用，后者由搭建配置产出、经出盘发布，下文称出盘子应用。两类走同一条加载链路，差别只在取哪个模块名，业务子应用逐页导出，出盘子应用全站共用一个入口模块，页面名带进产物内部再分派。门户因此不区分手写页面与配置页面，新增一类页面不用改门户。外部页不产容器，走不到这套寻址。

运行层的第二条关系是组件供应。模块联邦不限制谁向谁取，任何应用都能导出组件，门户自己也导出组件库；实践中供应方是某个业务子应用，出盘子应用在运行期向它取业务控件，下文把这个供应方称作宿主，各应用配置里的宿主名指的就是它。谁兼任宿主写在它自己的构建覆写脚本里，供应哪些组件出自编译时生成的引用清单。

寻址不经过配置，取谁的入口由 URL 里的应用名决定，应用名同时是静态目录名与容器注册到 window 的名字。配置来源提供寻址之外的四样东西，各由不同代码读取：

- 静态域与租户前缀，后端改写页面时注入，决定这些目录能否被访问；
- 后端下发的应用配置，给出应用挂在哪个宿主下、用哪个构建版本与主题，门户启动时预热一次；
- 内置应用名单，写死在加载器里，名单外一律按出盘子应用处理；
- 组件库版本表，把包名解析到版本目录，服务运行期解析控件包那条路。

四样收不成一个来源，新增应用因此要改加载器代码，解析逻辑也存在三份实现。

## 一个链接如何加载成页面

五步，门户路由分流、路径切分、模块判定、取入口执行、按协议取模块，前三步决定命中哪个应用的哪个模块，全在浏览器完成。

### 门户路由先分流

门户路由表把地址分两拨。页签承载、打印、按打开者打印、预览、应用首页五类前缀指向远程页组件，命中才进入子应用加载；后台管理、门户配置、各类设计器预览、登录前门户等前缀指向门户自己的页面。

### 从路径切出应用名与页面名

解析函数接受两种输入，完整门户路径与剥掉基础路径后的相对路径，前者按基础路径段数跳过再切，应用首页前缀多占一段、单独按固定段数切。规则是首段为页签承载段时取下一段当应用名，否则首段即应用名；页面名优先取应用名之后那一段，取不到则取剩余路径首段。移动端在调用前替换掉租户前缀与门户段，同一份代码处理两种地址。

应用名同时是静态目录名、window 全局名与文案资源归属键。地址带移动端后缀时端别按后缀判定，返回前剥掉后缀，两端共用一套应用名。门户在这个函数外又包一层，用路由常量表再判一次，命中门户路由就把类别改成非出盘子应用，路由常量表与内置名单是两份清单。切不出应用名只返回空结果，加载器随后统一判一次，应用名与页面名缺一个就发页签错误事件并抛错，文案是「此页面不存在」加当前路径。

### 名单决定取哪个模块

内置名单实测三十五条，列的是业务子应用与门户自身那几个应用。名单内取与页面名同名的模块，名单外按出盘子应用处理，取全站共用的入口模块：

```ts fold
// 一个应用的对外导出面（示意）
plugin._options.exposes = {
  './Entry': entryShell,             // 全站出盘子应用共用的入口模块
  './PortalEntry': portalEntryPage,  // 应用逐个手写的业务页面
  ...componentExposes,               // 由引用清单批量生成，键形如 './范围/包名'
};
```

判定是一次数组取反。消费方只拿到一个模块名字符串，看不出对方内部是一组页面还是一个组件仓库。

### 取入口并执行

地址由静态域前缀、应用名与固定入口文件名拼出，文件名不带内容哈希，每次拿到的都是静态目录当前内容。拉取用 cors 模式并带凭据，成功后先补装缺失的全局依赖再执行入口：

```ts fold
// 把入口变成可执行容器（示意）
const url = `${staticOrigin}/${appName}/remoteEntry.js`; // 固定文件名，不带内容哈希
const text = await fetchText(url);
installMissingGlobals(text);   // 按入口里的标记补齐缺失的全局依赖
eval(text);                    // 容器与 i18n 映射表在这一步注册到 window
```

两条顺序约束，全局依赖先于入口执行，否则入口引用的框架实例还不存在；i18n 映射表拼在入口头部，文案资源加载排在执行入口之后。缓存策略按类别分，业务子应用每次挂载以 reload 重取入口文本，出盘子应用按内存里的版本号决定是否重取。请求失败构造的错误码带序号与地址，没有消费方。

### 按协议取模块并渲染

容器就是 `window[appName]`，协议规定三步：

```ts fold
await initSharing();                    // 第一步，初始化本应用的共享作用域
await container.init(shareScope);       // 第二步，容器接管这份共享作用域
const Module = (await container.get(`./${moduleName}`))(); // 第三步，按名取模块

render(lazy(() => Module));             // 包成懒加载组件交给渲染
```

容器接管失败只打一条警告，取值继续。模块包成懒加载组件，外面是页面级错误边界；挂页签由外层完成，默认按应用名聚合，同一应用共用一个页签。

## 依赖共享

两套机制并行，公共依赖构建期 external 到 window 上的 UMD 全局，业务控件包的导入改写成运行期解析。模块联邦的 `shared` 只配运行内核一项且不作 eager 加载，`singleton` 与版本约束都不参与。

### 公共依赖走 externals

脚手架的公共依赖表把框架、状态库、路由、日期、工具库与组件库配成 externals，映射到 window 全局名，组件库额外注册一组别名，新旧名字指向同一份实例。这些实现打成一份 UMD vendor 包，由构建插件以 script 标签注入，文件放在门户静态根下，子应用模板统一从门户加载，本地单独启动时用路径开关指向本地。

组件库也由门户供给，门户里有一份组件库源码的 fork 以导出模块形式提供，这份 fork 与组件库仓库已经分叉，两边各有对方没有的组件。

externals 让首屏依赖只有一份，存量应用不改构建即可接入。应用拿到的版本是否符合声明不在校验范围内，两个版本同时存在时靠清空 webpack 分片缓存补救，清掉后再请求分片仍可能报错。

### 业务控件运行时解析

出盘工程里业务控件包的裸包名导入，编译时被解析器插件改写成运行期解析调用，参数带宿主身份与平台版本，能力库查一张三级解析器表决定地址，未命中落到平台版本兜底，结果是真正的 ES 动态导入：

```ts fold
// 裸包名导入被改写成运行时解析（示意）
externalType: 'promise',
request: `Lib.dynamicImport(
  '${packageName}',
  { host: { name: hostName }, caller: { name, copVersion, type: 'UDC_APP' } },
  subPackage,
  module
)`,
```

修一个控件即可覆盖全部存量应用，出盘子应用的依赖版本由宿主决定，自身不做验证。

组件版本清单实测三十余条里 3.x 与 5.x 并存，主次版本线十余条。清单有两套生成实现，一套写各包真实版本，一套统一写平台版本，设计器读到的语义随构建链路切换而变，读取失败回落一个兜底版本号。宿主导出的组件清单与出盘工程的引用清单由同一段容错代码先后写出，中间失败时导出项已生效、版本清单缺失，设计器拿到空清单继续运行。

## 隔离

隔离发生在构建期与约定层，运行时不介入，样式靠哈希类名与一份共用主题，脚本靠同域与命名前缀，生命周期靠一份随 props 下发的契约。

### 样式作用域在构建期

所有样式文件走同一条 loader 链，CSS Modules 按文件名自动生效，只有以 module 结尾的文件参与改名，生产类名是八位哈希，移动端多一个端别前缀，开发环境保留路径与原名。跨应用样式冲突靠这层哈希类名挡住。

不带 module 的文件按全局处理，选择器原样进产物。脚手架加了一个自定义 loader 检查 `:global` 有没有父级选择器，建议父级用应用名或页面名，命中只在构建输出打一行红字，不中断构建。后处理链没有加作用域前缀的插件，压缩配置关掉了 z-index 归一与标识符合并，跨应用层级由各自写的数值决定。

### 主题只有一份

主题、图标、组件风格三份样式由脚手架生成的入口代码在启动时创建 link 插入 head，各带固定 id。主题与图标放在门户静态根下，组件风格按各应用自己的静态目录取；地址来自租户配置的主题键，取不到落默认主题，主题文件加载失败再向 body 追加一个指向默认主题的 link。

换肤改的就是主题 link 的 href，运行时按主题 id 从当前用户的主题资源表查出地址写回，组件风格另有 id 单独切换。这个函数只改写已有标签，标签不存在时打印一条脚手架版本过低的错误。出盘子应用不产主题标签，样式天然与宿主同源；登录页是例外，它不外部化依赖，脚手架把门户主题地址直接写进它的模板。

控件级换肤另有一条路，样式设计器的 hook 取回主题 CSS 文本，正则解析出变量表，渲染一个内联 style 标签并把 `:root` 改写成控件容器的类名，变量只在该容器内生效。这是全站唯一一处把样式收进作用域的地方。

### 运行时不做沙箱

所有应用共用同一份框架实例与同一套全局命名空间，没有代理 window，没有快照回滚，同域与命名前缀负责避免覆盖。版本配套因此是硬前提，第二个版本的内核或组件库进场时只能靠清空分片缓存补救。

外部页面是唯一例外，走 iframe。属性带 URL 时直接返回 iframe，不执行代码、不注入门户上下文、不共享框架，也不参与页签联动。这条路上没有 sandbox 属性与通信协议，参数靠查询串下发。

### 生命周期契约

生命周期不是一组挂载卸载函数，而是一份随 props 下发的回调加一组承载形态：

| 契约 | 内容 | 由谁决定 |
| --- | --- | --- |
| 承载形态 | 单页签、多页签、嵌入、弹窗、抽屉、子页、外框、按 HTML 加载 | 门户注入，页面据此调整行为 |
| 页面回调 | 就绪、渲染完成、卸载、销毁、关闭、刷新、改标题 | 承载方实现，页面调用 |
| 页面入参 | 业务标识、占位区内容、页签信息、打开者上下文 | 上游页面或菜单配置 |
| 失败出口 | 错误页的重试与关闭按钮是否出现 | 承载形态加是否顶层窗口 |

契约没有集中声明，页面漏调回调与承载方不触发它表现一致。失败出口有直接用户后果，重试按钮只在多页签形态且处于顶层窗口时出现，页面在栏目、弹窗或 iframe 里时加载失败没有出口。

## 跨应用协作

分界是随页面生灭的走参数，跨页面常驻的走全局。下发的是应用身份、页面参数、承载形态、页面上下文标识与三个版本句柄；共用的是组件库、能力库、请求实例、文案实例与一条借来的历史对象。

- 事件总线是唯一有意的跨应用广播机制，同页走订阅表，跨窗口走 `postMessage` 到当前窗口、打开者与父窗口，目标来源写死为通配，事件名是裸字符串；
- 插槽机制按名字注册与包装，名字限定大写字母加下划线，用于在不建立引用关系的前提下向宿主界面加内容；
- 状态完全不共享，门户用自己的 store 管页签，各应用自建 store，跨应用信息只走 props、事件、全局句柄与会话存储。

多页签意味着同一窗口里有多个路由实例，一次回退被所有实例响应。能力库为此提供只允许门户注册的路由生命周期钩子，劫持历史监听，回退由哪个页签处理由门户裁决。页签标题与面包屑靠事件加会话存储传递，判断是否处于面包屑态的办法是数文档里面包屑元素的个数。

## 交付与版本

构建号定位到一次具体构建，出盘子应用缺了它直接构建失败。产物侧两个地址加一个比对文件：

```text fold
/<应用名>/remoteEntry.js              稳定地址，指向静态目录当前内容
/<应用名>/remoteEntry.<构建号>.js     带构建号的旁路副本
/<应用名>/版本文件                    包描述文件的拷贝，只用于比对构建号
```

校验走双路，加载入口时并行预取版本文件，比对不一致就刷新入口并中断渲染，错误文案写明缓存过期。刷新权下放给页面，加载器把取最新版本、取当前版本、刷新入口三个句柄随 props 交出，页面不调用就一直用旧版本，而长期停留同一页签正是门户的典型姿势。

构建成功的推送由消息通道下发，移动端收到后清缓存并提示刷新，门户端把消息转给订阅者，不发强刷标记。Service Worker 只缓存文案与页面结构两类资源，离线包不带它。

发布粒度是一个仓库一个应用。改公共依赖只需重发门户，公共包与组件库导出都在门户产物里，应用侧 external 掉的依赖不含代码副本，记录的版本号也不参与校验。改宿主导出的组件要重发宿主，并重新出盘引用它的应用。回滚由静态目录指回旧产物完成，这是推断，代码里没有对应的前端实现。

## 故障与可信边界

每个远程页包一层页面级错误边界，单页失败不会白掉整个界面。加载态是空片段，失败提示是一行纯文本，没有重试与超时。可观测集中在性能一侧，启动五段漏斗、资源速度与缓存命中、页面级绘制指标、请求层版本哨兵都在跑。

一次加载能否成功取决于下面九项，前六项不满足就打不开页面，后三项是静默或延后失败，页面照样渲染但结果不对。

| 环节 | 要求 | 不满足时 |
| --- | --- | --- |
| 入口路由 | 前缀命中远程页那五类，且能切出应用名与页面名 | 落到门户自己的路由或 404，缺名直接抛错 |
| 静态目录 | 应用名对应的目录里要有那份入口 | 请求非 2xx 或取文本失败，落到一行失败提示 |
| 三处同名 | 静态目录名、window 全局名、包名必须一致 | 取不到容器，报错发生在取模块那一步 |
| 导出命中 | 内置应用的页面名必须在导出表里 | 取模块被拒绝，页面失败 |
| 名单方向 | 两类子应用的判定不能反 | 两条加载路径各自有一句明确的重定向提示 |
| 端的匹配 | 门户不加载移动包 | 直接渲染一段红字并终止 |
| 公共依赖 | 全局框架实例与共享作用域要先就位 | 容器接管失败只打一条警告，缺失延后炸在渲染期 |
| 宿主归属 | 配置里的宿主名要与实际供应方一致 | 缺省回退成应用名，不报错，但文案与权限请求打到错误归属上 |
| 页签容量 | 页签数未达上限 | 策略为提醒时新页签不入列，用户只看到点了没反应 |

故障上报有三条通道，都通不到服务端。能力库里唯一的日志工具指向一个开发环境域名，门户与业务应用都没有引用；链路追踪模块只剩一个基类；入口拉取失败的错误码没有消费方。加载失败在用户侧是一行文本，在服务侧不留痕迹。

| 执行远端代码的位置 | 输入来源 | 受控程度 |
| --- | --- | --- |
| 入口文本拉取后直接求值 | 静态域前缀加应用名 | 应用名取自 URL，判定靠内置名单取反 |
| 按注册表版本拼资源地址 | 版本由已加载的入口自报 | 可被远程包伪造 |
| 生产 HTML 由后端替换占位符 | 模板被轮询改写后下发 | 替换逻辑不在前端仓库 |

缓解措施集中在请求层，接口签名开关、跨站请求令牌、文本清洗与重定向协议白名单。缺失的是完整性那一层，没有内容安全策略、没有产物签名、没有可加载来源白名单。风险重点不在任意地址注入，这些代码全部来自自家静态目录与网关，而在构建产物与模板替换链是否被污染。

## 两条待接线的问题

- 导出面与版本清单由同一段容错代码先后写出，中间失败会让导出项生效而版本清单缺失，应当一次生成、缺失即让构建失败；
- 故障上报三条通道都通不到服务端，把日志工具的正式接口接回来，再给加载失败补一条埋点，通道本来都在。

## 与完整微前端架构的差异

一套完整的微前端框架通常在运行时提供八项语义，本方案里 JS 沙箱一项完全缺席，其余七项的替代物落在构建期、约定层与交付纪律上：

| 能力 | 完整方案的语义 | 本方案 | 替代物的边界 |
| --- | --- | --- | --- |
| 应用注册与激活 | 注册表声明应用与激活规则，框架按规则决定挂载谁 | URL 路径段直接当应用名，内置名单只用来区分两类子应用 | 新增应用要改加载器代码，名单写死在前端产物里 |
| 生命周期协议 | 框架规定挂载卸载函数并在切换时调用 | 一组随 props 下发的回调，承载方实现、页面自愿调用 | 漏调与不触发表现一致，卸载不彻底不会报错 |
| JS 沙箱 | 代理 window、快照回滚、独立执行上下文 | 没有沙箱，同一份 window 与框架实例，靠命名前缀避让 | 版本必须配套，冲突只能清空分片缓存补救 |
| 样式隔离 | Shadow DOM 或运行时给选择器加作用域 | 构建期 CSS Modules 哈希类名，主题与组件库样式全局共享 | 全局选择器与 z-index 不受管，检查只打警告 |
| 依赖协商 | `shared` 声明版本约束，运行时协商出单一实例 | externals 直指 window 全局，`shared` 只留运行内核一项 | 不做版本校验，失配延后到渲染期 |
| 通信契约 | 框架提供的通道带类型与命名空间 | props、事件总线、全局句柄、会话存储四种并存 | 事件名是裸字符串，跨窗口目标来源写死通配 |
| 版本与回滚 | manifest 加内容哈希，回滚改指向 | 稳定文件名加构建号旁路副本，双路比对 | 每次挂载重取入口，回滚依赖静态目录侧操作 |
| 第三方页面 | 带 sandbox 的 iframe 加通信协议 | 裸 iframe，参数走查询串 | 外壳能力不跨越这条边界 |

差异不是能力缺失的累积，而是同一个前提的推论，所有应用跑在同一份运行时里。这个前提换来存量应用零改造接入，业务仓库不引入框架运行时，产物只是一份带导出面的普通 webpack 产物，门户升级不要求所有应用同步发版。要把那套语义接回来，代价是每个应用先接受被代理的 window 与被框架接管的挂载点，正好是零改造的反面。

现实里的补救因此都落在纪律与约定上，版本配套靠一仓一应用的发布粒度与构建号比对，样式冲突靠哈希类名与父级选择器约定，依赖失配靠清空缓存兜底。应用数量与版本线可控时够用，规模继续增长时先失效的是版本配套那一条。

## 写作口径与边界

文中的机制来自对一套真实运行的门户前端的核查，覆盖 PC 与移动两个门户主应用、承担宿主角色的业务应用、一个出盘子应用的发布产物、构建脚手架、平台能力库、组件库与若干业务控件仓。公司名、产品名、包名、接口地址与文件路径都已隐去，规模数字做了量级化处理，示例代码是按真实结构重写的示意而非原文。

三处限制需要读者知道。依赖未安装且若干共享库不在本地，涉及它们内部行为的判断只到调用点；后端服务、网关配置与模板替换逻辑都不在前端仓库，加载地址的最终形态只到拼接点；没有实跑任何构建与发布命令，构建流程的结论来自脚手架源码与一个真实出盘产物的文件形态。
