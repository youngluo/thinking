# Polish

撰写和优化技术文章。目标是技术表述可靠、结构清楚、语言自然：撰写只写有依据的内容，优化在保留作者观点和表达层级的前提下修正问题。

## 核心原则

- 先确定文章范围、全文结构和章节职责，再落笔或修改局部句子；
- 以正确性和完整性为优先，改动范围由实际问题决定：撰写只写有素材支撑的内容，优化必要时可以重写、补充或重组，不为了少改而保留错误或缺口；
- 区分事实、观点和教学简化，只把事实、因果、边界或术语问题视为技术错误；
- 易变化的 API、兼容性、性能、安全和最佳实践应查阅当前一手资料，无法确认时标为“疑似”；
- 用户和项目规范优先，用户要求保留的章节、示例、术语、参考资料和格式不得改动。

## 判断任务范围

先按以下优先级判断流程：

1. 用户只要求评价或建议、不要求改动时，只输出诊断，不修改文件：先给整体结论和主要短板，再按严重度列出必须修改的问题并指出位置，最后列出可以不改的建议；
2. 用户要求撰写新文章、补写缺失章节或扩写草稿时，按「撰写流程」处理；
3. 用户提供完整文件或完整文章文本，且未限定章节、行号或段落时，按「优化流程」的整篇优化处理；
4. 用户明确指定章节、行号或段落时，按「优化流程」的局部优化处理；
5. 范围会显著影响结果且无法从上下文判断时，先询问一个聚焦问题。

## 内容编写标准

撰写和优化共用这一套标准：它既是写作规范，也是检查清单。撰写逐节执行，整篇优化按文章顺序逐段执行，局部优化只处理指定范围及必要上下文，都不降低检查要求。

每段按以下顺序处理，细节见对应维度：

1. **对照标题**：确认段落回应所属标题，范围和叙述层级没有偏移；
2. **补齐与删减**：按「技术正确性」补齐定义、前提、输入输出、因果、边界、异常情况和必要示例，删掉与标题无关的内容；
3. **压缩表达**：删除赘述和重复，合并语义连续的短段落，避免为了改写而改写；
4. **检查推进**：确认本段与上一段、下一段的关系清楚，叙述顺序、转折和结论自然推进；
5. **处理展示内容**：图片、图表、代码块和列表按「结构与逻辑」的要求处理；
6. **语言收尾**：按「作者语气与语言」检查术语、语气、AI 味、结构助词、用词、引号和禁用标点；
7. **判断取舍**：正确性和完整性优先于最小修改；优化时没有实质提升空间就保留原文。

### 技术正确性

- 文字、代码、类型、图表、清单和示例保持一致；
- 术语、因果关系、适用前提和版本边界准确；
- 关键定义、前提、步骤、边界和异常情况没有缺失；
- 讲一类问题（缺陷、风险、故障、性能塌陷）时，先让读者看见它发生一次：谁做了什么、在哪个时刻触发、后果落在谁身上，再讲成因和对策；只有定义、分类和对策，读者判断不了它的分量；
- 讲一个可以开启的机制时，按「怎么开、在哪里做、多久生效、怎么退回」自查一遍，只写作用和代价不算讲完；
- 示例在当前讲解层级内闭合，省略部分明确为示意；
- 每个关键结论都有必要的前提、因果和适用边界；新增内容有可靠依据，不为了显得完整而扩展主题；
- 涉及具体技术结论时，读取 `references/tech-domains.md` 中对应领域的检查表逐条核对。

### 结构与逻辑

标题与章节：

- 不带数字、序号或编号前缀；
- 不使用行内代码包裹术语、代码标识符或 API，反引号和 <code> 标签都算；
- 原则上不使用标点符号，冒号和破折号一律不用。官方术语或版本号确实不可替代时，才保留必要标点；
- 层级不超过三级：文章标题占第一层，正文通常只到第二层和第三层，能压到两级就压到两级；
- 三级标题只在并列的子主题之间使用：章节开头的定义、根因、分类这类总起内容不设标题，直接放在二级标题下；某个三级标题与同级标题不同类时（通常是总起），删掉它，内容归入二级标题；
- 二级标题下先有一段正文交代本章的范围或主线，再进入三级标题，不从二级标题直接跳到三级标题；主线用内容本身说清（对象、职责、判断），不写成「这一章说明……」式的预告；
- 同级标题处于相同抽象层级，父子标题不重复表达同一含义；
- 章节标题只给对象或职责，不写成完整句子：去掉限定语、举例、条件和「的」字结构，能删的字删掉，通常不超过十个字；文章标题可以是一个完整问题，二级和三级标题不行；
- 每节要有独立问题要回答，删掉它文章的结论仍然成立时合并或删除；
- 叙事顺序和节奏合理：必要背景与定义先于概念使用，整体说明先于局部细节，规则先于例外，需要后文论证的最终结论不提前，同一主题尽量连续展开；
- 直接概括章节职责，不使用口号、噱头或目录预告。

正文：

- 章节职责清楚，概念在使用前已有必要说明；每个章节都准确回应标题，范围和叙述层级一致；
- 结论能从前文得出，过渡表达真实的承接、转折或因果；
- 开头两段内交代三件事：对象与覆盖范围、读者会遇到的处境或问题、以及读下去的理由（一处认知落差，或一个具体到可验证的问题）；只有定性加章节清单的开头不合格；
- 三件事是职责不是句式：不规定顺序、句长和每项各占一句，也不要求每篇都是同一个开头形状；写完自查一次，换掉主题之后这段开头还能原样用在别的文章上，就是模板，重写；
- 判断和落差先于例子出现，不靠两个以上例子去引出它；例子从属、一句以内，彼此同层并指向同一个判断；落差必须是文章自己论证、正文能展开的判断，不替读者立没人持有的靶子，也不靠情绪和夸张；
- 定义和细节留给正文，开头给到能定位、能引起兴趣的程度即可；方法句回答怎么做，不能顶掉回答讲哪些的范围句，也不写成全文摘要或目录预告；
- 结尾只在能够收束核心判断、取舍或适用边界时写总结，不为形式完整而新增；
- 图片、图表、代码块和列表与前后的自然段作为一个连续叙述单元：前文说明展示目的，不重复表内已有的限定；代码示例或图示前还要点明它与正文论点的关系，需要举例时自然引出；讨论组件职责或运行边界时明确示例角色。背景说明与具体示例提示承担不同作用时可以分段，同属一个概述时合并表达；后文按需承接关键信息或后续推导，不用空泛引导语重复内容；示例代码里出现的每一项都要在正文交代为什么在，交代不了的从示例里删掉；列表只在并列关系、步骤或对照比自然段更清楚时使用，非末项以中文分号结尾，末项以中文句号结尾；
- 编号列表只在顺序本身影响操作或理解时使用；编号不提供额外信息，或内容只是并列职责、要素和说明时，使用无序列表。步骤列表描述实际的流程动作和阶段变化；对整个流程的归纳及流程结束后的效果放在列表外。相邻步骤看似重复时，先确认是否属于不同阶段，只合并重复说明，保留各阶段独有的动作、因果和状态变化；
- 紧接详细列举的概括句只收束整体结论，不复述条目，也不引入前文未说明的新分类；
- 表格是本类事实的家：速查表放在细节段落之前，表里放事实与边界，正文只写表格放不下的推理；同一行两列说同一件事时合并成一列；示例代码已经列出的项，不再另做逐项说明表；把段落改写成表格时，单元格按列名重写成短句（如「要守住什么 / 放行的后果」），照抄原句只是把段落搬进格子，省不下篇幅；
- 不在句内用「见「某节」」这类指向把读者支开：同一篇文章里章节与机制的对应关系集中写在图或结构说明处，其余位置把话在句内说清；
- 同一细节只在最合适的位置完整说明，不跨段、跨节重复结论；
- 图表主链路正确，并与正文和代码对应；图表或开头承诺的顺序与正文的组织方式一致，不一致时改承诺，不让读者按图找不到章节；
- 移动或合并章节之后回头复查三件事：图和开头承诺的顺序是否仍与正文一致，按章序书写的并列清单要不要重排，跨章指代（「前面」「上一章」）是否因距离变远而失去所指；
- 不套用固定文章骨架，也不强制添加总结。

### 作者语气与语言

- 删除无信息量的开场、目录预告、万能总结和模板化转折；
- 不凭空加入第一人称经历、情绪、比喻或立场；
- 句子主干、指代、条件和因果清楚，术语前后一致；回指要自带所指，上文没有编号就不用序号回指，对象的类别名不省略（写「响应头」不写「这个头」），需要读者回头数或回头猜时把该项写全；写条件、约束类事实时写全三步：动作或用法、谁在强制或校验、效果，只列条件读者看不出关联；约束和限制再补一句它防的失败是什么，只有限制没有理由，读者会当成背规定，也会怀疑这条限制是否多余；
- 用词要准确表达技术关系和结论强度，避免关系表述不准或语气过强。「只有」仅用于确实排他的判断。不为缩短句子省略必要的连接成分，如「除了……外，还可以……」；
- 同一动作在不同前提下结论相反时，分别命名两种做法（如「比对白名单后回显」和「原样抄回」），不要用一个动词加限定语承载，读者会读成自相矛盾；
- 自然段不过度零散，也不堆叠多个独立观点，每段保持一个完整小观点；
- 根据句子与后文的关系选择冒号或句号：只有当前句引出独立成块的展示内容（等式、表格、图示、代码块、列表）时才用冒号；句子内部的解释和行内列举不用冒号，改用句号、逗号或「即」「包括」；不因下一段恰好是展示内容而机械改为冒号；同一段里最多保留一处引出展示内容的冒号；
- 根据句法选择“的、地、得”：定语或省略中心语的结构用“的”，动词前的状语用“地”，动词或形容词后的补语用“得”；
- 遇到“动词 + de + 越……”结构时，先判断“越……”修饰的是对象、动作还是状态，再确定结构助词。修饰由前面结构限定的对象或省略的中心语时使用“的”，直接补充动作程度或状态时才使用“得”，在动词前作状语时使用“地”。例如“生成的越快”使用“的”，不能写成“生成得越快”或“生成地越快”；
- 全文不使用中文或英文破折号，按语义改用句号、逗号、冒号或括号；
- 文章正文的自然语言引号统一使用「」，嵌套引用使用『』；
- 全文统一使用“其它”；
- 行内代码只包标识符、API 和取值，示例主机名、示例 URL 这类说明性内容用普通文本；
- 需要详细判断 AI 味时读取 `references/ai-voice.md`。

### 内容边界

- 优化时不改变原文的核心观点和立场；
- 可以补充保证正确性和完整性所需的事实、定义、前提、步骤与边界，但不得添加无关观点，新增技术内容必须经过核验；
- 不把通用概念改成某个框架或产品的专属解释；
- 不凭空构造反面说法来引出结论；
- 不为了形式感添加表格、流程图、代码或总结；
- 参考文章只用于学习语气、节奏和表达密度，仓库约定的目录、命名和格式按项目规范执行，不复制其结构或模板。

## 标题结构审查

撰写和优化共用这一步，只读，不修改文件，也不提前改写正文，只判断主题是否成立、标题形式、章节的职责、顺序和节奏。撰写动笔前用它确认结构，成稿后和整篇优化用它审查现有结构。

判结构前先确定文章要回答的问题（第一性原理）：读者带着什么疑问来，文章给出什么回答。章节职责从这个问题上推，不从标题字面上推。主题偏浅、答非所问或问题本身不成立时，写进方案的说明里作为建议，不擅自更换主题，立场仍按「内容边界」保留。

标题和章节是否合格，按「内容编写标准」的「结构与逻辑」判断；逐个三级标题与同级标题对照，标出不并列的那一个（通常是章节总起），只有一个三级标题的章节也按这条处理。

标题确认统一使用 Markdown 表格，列名固定为「旧标题」「新标题」「调整原因」。撰写和优化都列出完整大纲，包含文章标题，并在前两列分别标明原层级和新层级，按新大纲的顺序排列。保留项前两列相同；新建文章或新增章节的旧标题写「（新增）」；删除章节的新标题写「（删除）」；合并或拆分时在对应单元格列出涉及的全部标题。只列改动项会让作者看不到全貌，也无从判断哪些节被漏看。

第三列逐项说明改名、移动、合并、拆分、删除或新增的原因，保留项留空；撰写时在第三列说明各章节要回答的问题。方案写在回复里，不写进文章。

```markdown
## 标题结构建议

| 旧标题 | 新标题 | 调整原因 |
| --- | --- | --- |
| 文章标题 | 文章标题 | |
| 二级 标题甲 | 二级 标题甲 | |
| 二级 旧标题乙 | 二级 新标题乙 | 更准确地概括章节职责 |
| 三级 标题丙 | （删除） | 属于二级标题的总起内容 |
| 三级 标题丁 | 三级 标题丁一<br>三级 标题丁二 | 原章节包含两个并列子主题 |
| （新增） | 二级 标题戊 | 补齐缺失的章节职责 |
```

只要需要调整结构，就必须先经用户确认，改标题、增删或合并章节、调整章节顺序和内容归属都算。此时只输出方案和说明，然后结束当前轮次，等用户确认后再动正文；优化时即使收到直接修改的要求也不例外，因为原有结构是作者的选择。顺序不合理时，说明哪些概念需要前置、哪些内容需要后置，以及这样调整如何改善叙事推进。用户提出调整时，更新方案并再次结束轮次。结构不需要调整时，不输出方案，直接进入下一步。

## 对抗性复读

撰写、整篇优化和局部优化共用这一轮复读，范围与本次改动一致：全文流程覆盖整篇，局部流程只看本次改动及其上下文。同一套标准重读容易自我确认，这一遍的目标是把文章推翻：

- 逐个驳倒关键结论：构造反例，检查缺失的前提、版本与规模边界和绝对化表达，无法证实的按「技术正确性」标为“疑似”或改回原文；
- 检查本次改写有没有引入新的不准确、新的重复或新的逻辑断点；
- 读者反馈看不懂时，先补场景和动作主体（谁在什么情况下做什么、对谁生效），不要用拆段、列表或表格代替内容补全：排版只让已有的推理更好扫读；
- 对照改动前的原文逐字比较，确认没有改丢信息；删除的内容逐条核对，删掉之后核心结论仍然成立、读者仍能读懂，删不是为了让文章变短；
- 判断每处改动是否优于原文，说不上更好就退回原文。

技术结论按 `references/tech-domains.md` 的判别问句反驳，语言按 `references/ai-voice.md` 的判别问句反驳。

## 撰写流程

### 范围与素材

1. 确认文章主题、目标读者、要回答的问题和不覆盖的范围。信息不足以确定标题或章节职责时先询问，不臆造主题；
2. 收集素材：仓库代码与运行结果、官方文档、用户提供的内容。结论必须有可核验的来源，无法确认的事实标为“疑似”或直接不写；
3. 读取项目规范和目标目录的相邻文章，按当前规范确定目录、命名、格式和图示要求，只在项目指定的目录和格式下创建文件；
4. 在既有草稿上补写或扩写时，先读取草稿，沿用它的结构、术语和叙述层级，只补缺口；改写已有段落属于优化，先说明问题或征得同意，不顺手重写。

### 结构确认

动笔前按「标题结构审查」确认结构，等用户确认后再写正文。用户已给出明确结构或要求直接成文时，直接沿用，不重复确认。

### 逐节起草

- 按确认的结构逐节写，每节准确回应标题，不写无关内容；
- 写作节奏：先把内容写全，再安排顺序与衔接，最后统一语言；
- 每节完成后只核对处理顺序的第 1、2 项（「对照标题」「补齐与删减」）；语言、衔接和去 AI 味留到成稿后的整篇检查，避免同一遍检查做两次。

### 成稿后

全部章节完成后，对成稿执行一遍完整的「优化流程」，这是全文级的第一遍检查：标题结构审查确认结构无需调整后，进入整篇优化，新稿的衔接、语言和用词问题在这一步处理。

## 优化流程

优化只改文档本身，不扩展到构建、暂存、提交或其它仓库操作，除非用户明确要求。整篇优化先做标题结构审查；局部优化不进入结构审查。

### 修改前准备

1. 读取项目规范和目标文件；
2. 查看目标文件的 Git 状态，区分暂存区与工作区，避免覆盖用户已有修改；
3. 整篇优化时通读全文，用一句话写下文章要回答的问题和读者的疑问，作为结构方案和逐节判断的基准，并记下现有篇幅（段落数与大致字数）作为对照；局部优化时读取目标范围及必要上下文；
4. 记录用户要求冻结的内容，保存改动前的版本用于逐字比较，已跟踪文件也可用 `git diff` 还原；
5. 识别文章已有的术语、代码块、图表和叙述层级。

只有系列文章的职责边界确实影响当前修改时，才读取相邻文章。

### 整篇优化

先应用用户确认的结构方案；方案还没确认时，输出方案并结束本轮，不改正文；标题无需调整时直接处理正文。技术诊断在内部完成；只有疑似技术问题、作者意图不明确或需要超出已确认结构时才暂停确认。

1. **取舍与精简**：以文章要回答的问题为基准逐节判断，删掉它文章的结论是否仍然成立；只是相关的内容压缩成一句、移出到更合适的文章或删除。篇幅以现有长度为上限，除非补齐必要的前提、边界或示例；需要增删或合并章节时，按「标题结构审查」输出方案等确认，不在这一步顺手改结构；
2. **开头与结尾**：先在原文基础上优化开头，结尾按「结构与逻辑」处理。正文和结尾完成后重新评估开头，局部调整仍无法引出优化后的内容时可以整体重写，但不得新增原文没有的观点，也不能改写成全文摘要；
3. **逐节处理**：先明确标题承诺回答的问题、覆盖范围和叙述层级，再按文章顺序逐节执行「内容编写标准」。修改当前段落时同时检查所属标题、上一段和下一段；与标题无关的内容删除、移动或改写，标题承诺但正文没有解释的内容补齐；必要时重写或重组段落，不受最小修改限制；
4. 逐段处理不需要逐段向用户确认或汇报。

### 局部优化

读取目标范围及必要上下文，完成内部诊断后直接修改。

指定段落、句子或小范围时，仍按「内容编写标准」处理，在授权范围内纠正错误、调整同一章节内的段落顺序与衔接、补齐必要内容，不因为范围较小而只做字面替换。局部修改默认沿用原有结构和措辞，只处理用户指出的问题及必要上下文；用户明确要求保留的内容视为冻结项，除非之后明确要求调整。精简前对照原文区分重复表达与独立信息，合并时保留各步骤独有的阶段、主体、条件、因果和结果，只删重复部分。发现需要改标题、增删或合并章节，或把内容移到其它章节时，按「标题结构审查」输出方案并结束本轮，不在局部修改里顺手调整结构。只有疑似技术问题、作者意图不明确或修改会超出指定范围时才暂停确认。

修改后按「对抗性复读」检查改动行，范围外的既有问题只说明，不顺手修改。完成后运行两条 `git diff` 检查（命令见「完成前验证」），不运行 `validate_markdown.py`：目标文件的范围外还有历史违规时，跑全文脚本会把范围外的问题一起报出来，和“不改范围外”的要求互相锁死。

### 完成前验证

撰写和整篇优化完成后，从头到尾重新通读全文，按「内容编写标准」逐项自查，再确认这些整篇级问题：

- 标题与用户确认的方案一致；
- 开头两段内定位、处境和读下去的理由齐备，判断先于例子出现，没有写成摘要、目录预告或换掉主题也能套用的模板；
- 没有跨段、跨节的重复结论，同一概念、角色、阶段和 API 的用词一致；
- 没有用「见「某节」」把读者支开；
- 精简判断做过：每节都在回答文章的问题，没有只是相关的内容；篇幅增长只来自补齐必要的前提、边界或示例；
- 优化时，原意、作者语气和冻结内容得到保留。

通读自查后按「对抗性复读」推翻一遍，再让独立评审对照「内容编写标准」复查一遍并给出问题清单，逐条处置；自查和复读都由本次改写者执行，会与自己的改动互相确认。最后运行校验：

```bash
rtk python3 .agents/skills/polish/scripts/validate_markdown.py <target-file>
rtk git diff --check -- <target-file>
rtk git diff --cached --check -- <target-file>
```

三条命令都在仓库根目录执行。`validate_markdown.py` 只查本文的 Markdown 规则；两条 `git diff` 查改动行的行尾空格和冲突标记，改动在工作区用 `--check`，已经 `git add` 过的用 `--cached --check`，漏掉后者会什么都查不出来。对已跟踪文件生效，新写的文章无法用 diff 检查。校验失败时修正问题并重新运行，通过前不得汇报完成；脚本覆盖不了的复杂嵌套列表仍需人工检查。

### 完成反馈

只报告实际发生的改动或产出、验证结果和仍需用户确认的事项，不重复诊断报告或展示完整 diff；整篇优化时说明篇幅变化，删减、移出和新增各是什么。
