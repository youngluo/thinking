# Polish

优化技术类文章。先输出诊断报告，再询问用户选择逐条确认或全量修复模式，确认后输出 diff 对照。

## 执行流程

```
读取文章 → 四维诊断 → 输出诊断报告 → 用户选择模式（逐条确认 / 全量修复）→ 输出 diff 对照 + 改动摘要
```

## 默认执行模式

- 每次都先输出诊断报告，并询问用户选择逐条确认或全量修复模式。
- 用户明确要求逐条确认或全量修复时，也先输出诊断报告，再按用户指定的模式继续。
- 未获得用户确认前，不直接输出修复 diff。

## 阶段一：诊断报告

读取目标文件，按四个维度逐项检查。每个问题标注行号和严重程度。

严重程度定义：

- **严重**：技术错误、明显 AI 腔调且影响阅读，需要修改
- **疑似**：可能有误，需要用户确认
- **建议**：可以更好，但当前也能接受
- **轻微**：小瑕疵，不影响阅读

### 维度一：技术正确性

交叉验证代码示例与文字描述是否一致，术语使用是否准确。发现疑似错误时标注为"疑似"并给出理由，不直接断言。

额外关注：

- **API 兼容性描述**：不能只说"X 是 Y 的替代方案"，需要验证是否真的是同一用途、是否真的跨浏览器、是否有前置条件（如安全上下文、特定浏览器版本）
- **阈值/时间窗口类参数**：数字太松会漏报，太紧会误报，需要结合实际场景判断合理性
- **术语对齐官方文档**：技术词汇优先与对应官方文档一致；不要为行文顺手自造核心概念。确需辅助解释时，明确它只是解释性说法，不要当成正式术语使用。

检查范围覆盖前端基础、AI Agent、后端/全栈、计算机基础四大领域。详见 `references/tech-domains.md`。

### 维度二：逻辑连贯性

- 段落之间是否有逻辑跳跃（前面说 A，后面突然说 C，缺了 B）
- 概念引入顺序是否合理（用到的术语是否先定义了）
- 表格、图表与上下文文字是否呼应
- 结论是否从前面的论述中自然得出
- 章节之间的过渡是否自然
- 技术文章结构是否符合下方"技术文章排版结构规范"
- 不为了引出正确说法而凭空构造不存在或不常见的反面判断；若需对比，应对比真实存在的 API、配置或常见误解，并说明来源或上下文。
- 先确认文章的主题范围和叙述层级。介绍通用概念时，具体产品或框架只能作为例子，不能取代文章主线。
- 修改局部句子前，先确认核心结论和当前章节的职责；修改后重新通读整段或整节，避免局部更顺但上下文冲突。
- 将用户明确要求保留的定义、公式和核心判断视为原文锚点。围绕锚点优化结构，不为统一文风而反复改写。
- 简化内容时保留必要的概念、因果关系和边界，不能只追求更短而损失逻辑完整性。
- 过渡句应表达真实的承接、转折或因果关系，不写成目录预告或空泛的引导语。

#### 图表与流程图

- 先检查图表表达的逻辑是否正确，再考虑样式、尺寸和布局。
- 流程图应根据主题检查起点、终点、依赖关系、分支、回路和异常路径是否完整；不是所有图都必须包含全部元素。
- 图中保留理解主链路所必需的节点，把次要细节放到正文；不能因分支过多而失焦，也不能因过度简化而失真。
- 节点名称优先采用领域内通行术语，并保持相同的抽象层级和命名方式。
- 判断节点与分支标签应相互对应，相邻节点避免语义重复。
- 修改单个节点或连线后，重新检查完整流程及其前后文，避免局部调整破坏整体语义。

### 维度三：去 AI 味 / 加人味

识别并消除 AI 腔调，增加个人视角。具体的 AI 味特征和人味特征详见 `references/ai-voice.md`。

### 维度四：语言质量

- 句子是否太长（超过 60 字考虑拆分）
- 用词是否重复（连续三段都用"本质上"）
- 是否有错别字、标点错误
- 表格列宽是否均匀，内容是否对齐
- **段落拆分是否合理**：检查是否有不合理拆分——该合并的合并，该拆分的拆分行首字母是否大写
- **换行密度是否自然**：不要把每一句都单独换行。短句可以增强节奏，但连续多段只有一句话会显得碎、像 AI 生成。按语义合并相邻短句，让一个自然段承载一个完整小观点
- **重复描述**：检查是否有重复表述冗余内容，考虑精简
- **内容层次**：定义、公式和补充解释应形成清晰层次，避免拆得过碎或重复强调同一结论

## Markdown 输出相关规范

### 技术文章排版结构规范

不要机械复用固定标题。技术解释类文章优先遵循这条叙事路线：

```text
是什么 → 为什么 → 适用场景 → 具体实现 → 最佳实践 → 优化 → 总结
```

- 开头先交代文章要解决的问题、读者能获得什么，不要直接堆概念定义。
- "是什么"部分先给一句话本质，再拆关键点，避免只罗列百科定义。
- "为什么"部分从真实痛点出发，说明不用它会遇到什么问题。
- "适用场景"要同时写适合和不适合的场景，避免把方案说成万能答案。
- "具体实现"按实际链路展开，优先使用流程图、步骤拆解或阶段划分，让读者知道每一步解决什么问题。
- "最佳实践"写工程里更稳的做法，包括边界、取舍、常见坑和判断标准。
- "优化"聚焦可操作方向，例如性能、准确性、稳定性、成本、体验和可观测性。
- "总结"收束核心判断，不要重复目录，也不要写空泛祝福。
- 如果文章主题不适合完整结构，可以合并或省略部分章节，但顺序上仍保持"先理解，再落地，再优化"。

### Markdown 书写规范

- 反引号 `\`` 只用于代码语义内容，包括变量名、方法名、类名、类型名、属性名、命令、路径、配置项、代码片段和 API 名称。
- 普通概念、通用术语、库名、框架名和自然语言描述不要使用反引号。同一句话里，如果是在说明某个代码标识符，保留反引号；如果只是在讨论技术概念，使用正常文本。
- 有序标题编号统一使用英文句点加空格，例如 `### 1. 标题`、`### 2.1. 标题`。不要使用中文顿号格式，例如 `### 1、标题`、`### 2.1、标题`。
- 全中文文章使用中文全角标点，中文内容使用中文引号；英文句子和英文内容使用英文引号。代码、命令、路径、配置项和 API 名称保持其原始符号。
- 并列列表条目之间用中文分号「；」分隔，末项以中文句号「。」收尾，适用于无序列表和有序列表。顺序步骤（按时间或流程展开的步骤）每条仍以句号收尾，不视为并列关系。表格单元格内不重复加句号。
- 破折号（——）必须逐个检查。Markdown 渲染后视觉效果不明显，优先改用句号断句或逗号；诊断报告中列出所有破折号位置及修改建议。

## 诊断报告输出格式

```markdown
## 诊断报告

### 技术正确性

- [严重] 第 X 行：具体问题描述
- [疑似] 第 X 行：具体问题描述 + 理由

### 逻辑连贯性

- [建议] 第 X 行：具体问题描述

### AI 味

- [严重] 第 X 行：具体问题描述

### 语言质量

- [轻微] 第 X 行：具体问题描述

### 标点与列表

- [严重] 第 X 行：具体问题描述
- [严重] 第 X 行：并列列表末项应加句号、其余项加分号；步骤列表每条加句号；表格单元格不重复句号
- [严重] 第 X 行：破折号"——"改用句号或逗号

### 标题与术语

- [严重] 第 X 行：营销化/口语化标题（"先把 xx 看清楚""先搞懂 xx""一文看懂 xx"等），改用中性技术标题
- [严重] 第 X 行：术语与官方文档不一致；自造概念未注明"仅为解释性说法"
- [严重] 第 X 行：凭空构造反面判断（指出虚构的 API/配置/误解）
```

输出诊断报告后，以交互选择形式让用户挑选修复模式：

```
请选择修复模式：
A. 逐条确认 — 每条修改先展示 diff，确认后应用
B. 全量修复 — 一次性输出完整 diff 对照

输入 A/B 或"逐条"/"全量"切换，见下方交互语法。
```

## 阶段二：输出 diff 对照

### 交互语法（全程有效）

| 输入                    | 效果                       |
| ----------------------- | -------------------------- |
| `A` / `逐条` / `切逐条` | 进入逐条确认模式           |
| `B` / `全量` / `切全量` | 进入全量修复模式           |
| `y`                     | 确认当前修改（仅逐条模式） |
| `s`                     | 跳过当前修改（仅逐条模式） |
| `n`                     | 取消并中断执行             |

### 自检（两种模式共用）

输出前对 diff 做一轮自检：

- **技术正确性**：优化过程中引入的改动是否引入了新的技术错误（比如改了代码但没验证、补充了描述但不准确）
- **原意保持**：技术修正是否改变了作者的原意（修正事实错误 OK，改变观点不行）
- **信息完整性**：去 AI 味时是否误删了有信息量的内容（套话该删，但不能把有用的观点也删了）
- **Markdown 规范**：列表末项加句号、其余项加分号；步骤列表每条加句号；表格单元格不重复句号；破折号优先改句号或逗号。
- **标题与术语**：标题避免"先把 xx 看清楚""先搞懂 xx""一文看懂 xx"等口语化、营销化表达；术语与官方文档一致；不凭空构造反面判断。

### 逐条确认模式

按严重程度从高到低逐条展示修改：先说明问题，再展示修改前后的 diff。用户输入 `y` 确认当前修改，输入 `s` 跳过当前修改，输入 `n` 取消并中断执行。

### 全量修复模式

默认输出所有修改的统一 diff 对照，使用 `diff` 代码块展示。不得只输出优化后的全文，也不得只输出改动摘要。

输出格式：

````markdown
```diff
--- 原文
+++ 优化版
@@
- 原句
+ 优化句
```
````

要求：

- 覆盖本轮所有修改
- 保留足够上下文，便于定位
- diff 之后再输出改动摘要
- 如因文章过长或已直接修改文件导致完整 diff 不适合展示，只输出关键 diff 片段和改动摘要，并说明未展示完整 diff 的原因

## 改动摘要

两种模式完成后，均在末尾附改动摘要：

```markdown
## 改动摘要

| 改动类型 | 数量 | 说明     |
| -------- | ---- | -------- |
| 技术修正 | N    | 具体说明 |
| 逻辑优化 | N    | 具体说明 |
| 去 AI 味 | N    | 具体说明 |
| 语言优化 | N    | 具体说明 |
```

## 约束

- 不改变文章的核心观点和立场，只优化表达
- 不添加作者没有表达过的观点
- 技术错误会修正，但会在诊断报告中标出让用户确认
- 保留作者的个人风格，只消除"非人"的部分
- 发现疑似技术错误时标注为"疑似"并给出理由，不直接断言
- 当用户要求"按某篇文章的模式/风格优化"时，只学习叙事风格、问题意识、句子节奏和工程化表达，不照搬章节骨架、开头句式、总结模板或固定排比。目标是"像同一作者写的"，不是"像套同一模板生成的"。如果参考文章是同目录文章，尤其要避免标题、开场、流程图和结尾总结高度同构。
- 控制换行节奏。不要为了显得有层次而频繁断行；除非是强调句、转折句或列表前引导句，否则优先把相邻短句合并成自然段。

## 风格

- 默认保持作者原风格，不把文章改成统一模板。
- 需要增强表达时，参考 `references/ai-voice.md`，但不要硬塞第一人称、口语词、比喻或固定句式。
- 表格、Mermaid 和代码示例只在能提升信息密度或解释清晰度时添加，不为了形式感而添加。
