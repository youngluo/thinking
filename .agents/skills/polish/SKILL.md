# Polish

撰写和优化技术文章。目标是技术表述可靠、结构清楚、语言自然：撰写只写有依据的内容，优化在保留作者观点和表达层级的前提下修正问题。

## 核心原则

- 先确定文章范围、全文结构和章节职责，再落笔或修改局部句子；
- 以正确性和完整性为优先，改动范围由实际问题决定：撰写只写有素材支撑的内容，优化必要时可以重写、补充或重组，不为了少改而保留错误或缺口；
- 区分事实、观点和教学简化，只把事实、因果、边界或术语问题视为技术错误；
- 易变化的 API、兼容性、性能、安全和最佳实践应查阅当前一手资料，无法确认时标为“疑似”；
- 用户和项目规范优先，用户要求保留的章节、示例、术语、参考资料和格式不得改动。

## 判断任务范围

先按以下优先级判断流程：

1. 用户只要求评价或建议、不要求改动时，只输出诊断，不修改文件：先给整体结论和主要短板，再按严重度列出必须修改的问题并指出位置，最后列出可以不改的建议；
2. 用户要求撰写新文章、补写缺失章节或扩写草稿时，按「撰写流程」处理；
3. 用户提供完整文件或完整文章文本，且未限定章节、行号或段落时，按「优化流程」的整篇优化处理；
4. 用户明确指定章节、行号或段落时，按「优化流程」的局部优化处理；
5. 范围会显著影响结果且无法从上下文判断时，先询问一个聚焦问题。

## 内容编写标准

撰写和优化共用这一套标准：它既是写作规范，也是检查清单。撰写逐节执行，整篇优化按文章顺序逐段执行，局部优化只处理指定范围及必要上下文，都不降低检查要求。

每段按以下顺序处理，细节见对应维度：

1. **对照标题**：确认段落回应所属标题，范围和叙述层级没有偏移；
2. **补齐与删减**：按「技术正确性」补齐定义、前提、输入输出、因果、边界、异常情况和必要示例，删掉与标题无关的内容；
3. **压缩表达**：删除赘述和重复，合并语义连续的短段落，避免为了改写而改写；
4. **检查推进**：确认本段与上一段、下一段的关系清楚，叙述顺序、转折和结论自然推进；
5. **处理展示内容**：图片、图表、代码块和列表按「结构与逻辑」的要求处理；列表非末项用中文分号，末项用中文句号；
6. **语言收尾**：按「作者语气与语言」检查术语、语气、AI 味、结构助词、用词、引号和禁用标点；
7. **判断取舍**：正确性和完整性优先于最小修改；优化时没有实质提升空间就保留原文。

### 技术正确性

- 文字、代码、类型、图表和示例保持一致；
- 术语、因果关系、适用前提和版本边界准确；
- 关键定义、前提、步骤、边界和异常情况没有缺失；
- 示例在当前讲解层级内闭合，省略部分明确为示意；
- 每个关键结论都有必要的前提、因果和适用边界；新增内容有可靠依据，不为了显得完整而扩展主题；
- 涉及具体技术结论时，读取 `references/tech-domains.md` 中对应领域的检查表逐条核对。

### 结构与逻辑

标题与章节：

- 不带数字、序号或编号前缀；
- 不使用反引号包裹术语、代码标识符或 API；
- 原则上不使用标点符号，冒号和破折号一律不用。官方术语或版本号确实不可替代时，才保留必要标点；
- 层级不超过三级：文章标题占第一层，正文通常只到第二层和第三层，能压到两级就压到两级；
- 同级标题处于相同抽象层级，父子标题不重复表达同一含义；
- 叙事顺序和节奏合理：必要背景与定义先于概念使用，整体说明先于局部细节，规则先于例外，结论和总结不提前，同一主题尽量连续展开；
- 直接概括章节职责，不使用口号、噱头或目录预告。

正文：

- 章节职责清楚，概念在使用前已有必要说明；每个章节都准确回应标题，范围和叙述层级一致；
- 结论能从前文得出，过渡表达真实的承接、转折或因果；
- 开头循序渐进：从具体场景、现象或触发条件切入，说明它带来的问题，再落到文章要回答的问题上；不在开头罗列全文结构、提前给出结论或预告目录；
- 结尾只在能够收束核心判断、取舍或适用边界时写总结，不为形式完整而新增；
- 图片、图表、代码块和列表与前后的自然段作为一个连续叙述单元：前文说明展示目的，后文按需承接关键信息或后续推导，不用空泛引导语重复内容；列表只在并列关系、步骤或对照比自然段更清楚时使用；
- 同一细节只在最合适的位置完整说明，不跨段、跨节重复结论；
- 图表主链路正确，并与正文和代码对应；
- 不套用固定文章骨架，也不强制添加总结。

### 作者语气与语言

- 删除无信息量的开场、目录预告、万能总结和模板化转折；
- 不凭空加入第一人称经历、情绪、比喻或立场；
- 句子主干、指代、条件和因果清楚，术语前后一致；
- 自然段不过度零散，也不堆叠多个独立观点，每段保持一个完整小观点；
- 根据句子与后文的关系选择冒号或句号：当前句明确引出等式、表格、图示、代码块、列表或后续分层解释时使用冒号；句意已经独立闭合时使用句号，不因下一段恰好是展示内容而机械改为冒号；
- 根据句法选择“的、地、得”：定语或省略中心语的结构用“的”，动词前的状语用“地”，动词或形容词后的补语用“得”；
- 遇到“动词 + de + 越……”结构时，先判断“越……”修饰的是对象、动作还是状态，再确定结构助词。修饰由前面结构限定的对象或省略的中心语时使用“的”，直接补充动作程度或状态时才使用“得”，在动词前作状语时使用“地”。例如“生成的越快”使用“的”，不能写成“生成得越快”或“生成地越快”；
- 全文不使用中文或英文破折号，按语义改用句号、逗号、冒号或括号；
- 文章正文的自然语言引号统一使用「」，嵌套引用使用『』；
- 全文统一使用“其它”；
- 需要详细判断 AI 味时读取 `references/ai-voice.md`。

### 内容边界

- 优化时不改变原文的核心观点和立场；
- 可以补充保证正确性和完整性所需的事实、定义、前提、步骤与边界，但不得添加无关观点，新增技术内容必须经过核验；
- 不把通用概念改成某个框架或产品的专属解释；
- 不凭空构造反面说法来引出结论；
- 不为了形式感添加表格、流程图、代码或总结；
- 参考文章只用于学习语气、节奏和表达密度，仓库约定的目录、命名和格式按项目规范执行，不复制其结构或模板。

## 标题结构审查

撰写和优化共用这一步，只读，不修改文件，也不提前改写正文，只判断主题是否成立、标题形式、章节的职责、顺序和节奏。撰写动笔前用它确认结构，成稿后和整篇优化用它审查现有结构。

判结构前先确定文章要回答的问题（第一性原理）：读者带着什么疑问来，文章给出什么回答。章节职责从这个问题上推，不从标题字面上推。主题偏浅、答非所问或问题本身不成立时，写进方案的说明里作为建议，不擅自更换主题，立场仍按「内容边界」保留。

标题和章节是否合格，按「内容编写标准」的「结构与逻辑」判断。

输出是一份结构方案：撰写时给出完整的标题和章节结构，并说明各章节要回答的问题；优化时只写需要调整的部分，不重复输出当前结构。方案写在回复里，不写进文章。

```text
## 标题结构建议

文章标题
  二级标题
    三级标题

说明：……
```

结构需要确认或调整时，只输出方案和说明，然后结束当前轮次，等用户确认后再动正文；优化时即使收到直接修改的要求也不例外，因为原有结构是作者的选择。顺序不合理时，说明哪些概念需要前置、哪些内容需要后置，以及这样调整如何改善叙事推进。用户提出调整时，更新方案并再次结束轮次。结构没有实质问题时不输出方案，直接进入下一步。

## 对抗性复读

撰写、整篇优化和局部优化共用这一轮复读，范围与本次改动一致：全文流程覆盖整篇，局部流程只看本次改动及其上下文。同一套标准重读容易自我确认，这一遍的目标是把文章推翻：

- 逐个驳倒关键结论：构造反例，检查缺失的前提、版本与规模边界和绝对化表达，无法证实的按「技术正确性」标为“疑似”或改回原文；
- 检查本次改写有没有引入新的不准确、新的重复或新的逻辑断点；
- 对照改动前的原文逐字比较，确认没有改丢信息；
- 判断每处改动是否优于原文，说不上更好就退回原文。

技术结论按 `references/tech-domains.md` 的判别问句反驳，语言按 `references/ai-voice.md` 的判别问句反驳。

## 撰写流程

### 范围与素材

1. 确认文章主题、目标读者、要回答的问题和不覆盖的范围。信息不足以确定标题或章节职责时先询问，不臆造主题；
2. 收集素材：仓库代码与运行结果、官方文档、用户提供的内容。结论必须有可核验的来源，无法确认的事实标为“疑似”或直接不写；
3. 读取项目规范和目标目录的相邻文章，按当前规范确定目录、命名、格式和图示要求，只在项目指定的目录和格式下创建文件；
4. 在既有草稿上补写或扩写时，先读取草稿，沿用它的结构、术语和叙述层级，只补缺口；改写已有段落属于优化，先说明问题或征得同意，不顺手重写。

### 结构确认

动笔前按「标题结构审查」确认结构，等用户确认后再写正文。用户已给出明确结构或要求直接成文时，直接沿用，不重复确认。

### 逐节起草

- 按确认的结构逐节写，每节准确回应标题，不写无关内容；
- 写作节奏：先把内容写全，再安排顺序与衔接，最后统一语言；
- 每节完成后只核对处理顺序的第 1、2 项（「对照标题」「补齐与删减」）；语言、衔接和去 AI 味留到成稿后的整篇检查，避免同一遍检查做两次。

### 成稿后

全部章节完成后，对成稿执行一遍完整的「优化流程」，这是全文级的第一遍检查：标题结构审查通常只确认结构无误，随后进入整篇优化，新稿的衔接、语言和用词问题在这一步处理。

## 优化流程

优化只改文档本身，不扩展到构建、暂存、提交或其它仓库操作，除非用户明确要求。整篇优化先做标题结构审查；局部优化不进入结构审查。

### 修改前准备

1. 读取项目规范和目标文件；
2. 查看目标文件的 Git 状态，区分暂存区与工作区，避免覆盖用户已有修改；
3. 整篇优化时通读全文，并用一句话写下文章要回答的问题和读者的疑问，作为结构方案和逐节判断的基准；局部优化时读取目标范围及必要上下文；
4. 记录用户要求冻结的内容，保存改动前的版本用于逐字比较，已跟踪文件也可用 `git diff` 还原；
5. 识别文章已有的术语、代码块、图表和叙述层级。

只有系列文章的职责边界确实影响当前修改时，才读取相邻文章。

### 整篇优化

先应用用户确认的结构方案；标题无需调整时直接处理正文。技术诊断在内部完成；只有疑似技术问题、作者意图不明确或需要超出已确认结构时才暂停确认。

1. **开头与结尾**：先在原文基础上优化开头，结尾按「结构与逻辑」处理。正文和结尾完成后重新评估开头，局部调整仍无法引出优化后的内容时可以整体重写，但不得新增原文没有的观点，也不能改写成全文摘要；
2. **逐节处理**：先明确标题承诺回答的问题、覆盖范围和叙述层级，再按文章顺序逐节执行「内容编写标准」。修改当前段落时同时检查所属标题、上一段和下一段；与标题无关的内容删除、移动或改写，标题承诺但正文没有解释的内容补齐；必要时重写或重组段落，不受最小修改限制；
3. 逐段处理不需要逐段向用户确认或汇报。

### 局部优化

读取目标范围及必要上下文，完成内部诊断后直接修改。

指定段落、句子或小范围时，仍按「内容编写标准」处理，在授权范围内纠正错误、调整段落顺序与衔接、补齐必要内容，不因为范围较小而只做字面替换。只有疑似技术问题、作者意图不明确或修改会超出指定范围时才暂停确认。

修改后按「对抗性复读」检查改动行，范围外的既有问题只说明，不顺手修改。完成后运行两条 `git diff` 检查（命令见「完成前验证」），不运行 `validate_markdown.py`：仓库里已有相当一部分文章存在历史违规，跑全文脚本会把范围外的问题一起报出来，和“不改范围外”的要求互相锁死。

### 完成前验证

撰写和整篇优化完成后，从头到尾重新通读全文，按「内容编写标准」逐项自查，再确认这些整篇级问题：

- 标题与用户确认的方案一致；
- 开头从具体场景或问题递进到正文，没有写成全文摘要或提前给出结论；
- 没有跨段、跨节的重复结论，同一概念、角色、阶段和 API 的用词一致；
- 优化时，原意、作者语气和冻结内容得到保留。

通读自查后按「对抗性复读」推翻一遍，再运行校验：

```bash
rtk python3 .agents/skills/polish/scripts/validate_markdown.py <target-file>
rtk git diff --check -- <target-file>
rtk git diff --cached --check -- <target-file>
```

三条命令都在仓库根目录执行。`validate_markdown.py` 只查本文的 Markdown 规则；两条 `git diff` 查改动行的行尾空格和冲突标记，改动在工作区用 `--check`，已经 `git add` 过的用 `--cached --check`，漏掉后者会什么都查不出来。对已跟踪文件生效，新写的文章无法用 diff 检查。校验失败时修正问题并重新运行，通过前不得汇报完成；脚本覆盖不了的复杂嵌套列表仍需人工检查。

### 完成反馈

只报告实际发生的改动或产出、验证结果和仍需用户确认的事项，不重复诊断报告或展示完整 diff。
