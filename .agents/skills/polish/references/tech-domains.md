# 技术正确性检查领域

## 通用检查原则

- 区分事实、观点和教学简化。事实错误需要修正；观点分歧只标注理由；教学简化可以保留，但不能误导关键机制。
- 检查结论是否依赖版本、运行环境、浏览器兼容性、部署形态、硬件资源或特定配置。缺少前提时，优先补充边界。
- 性能、安全、兼容性、最佳实践和生态趋势都可能随时间变化。无法确认时标为"疑似"，不要改成确定结论。
- 检查因果关系是否成立。不要把"相关"写成"导致"，不要把"常见做法"写成"唯一方案"。
- 检查术语是否混用。相近概念可以类比，但不能直接等同。
- 改写时优先保持作者原意。技术修正只修事实和边界，不替作者换立场。

## 需要标为疑似的情况

- 涉及最新版本、浏览器支持、框架 API 变化、模型能力、云服务限制、生态最佳实践。
- 涉及性能结论但没有基准、数据规模、运行环境或对照条件。
- 涉及安全结论但没有说明威胁模型、权限边界或部署环境。
- 涉及"一定"、"总是"、"完全替代"、"所有场景"、"跨平台通用"等绝对化表达。
- 涉及经验判断，但原文没有给出场景或约束条件。

## 领域检查清单

### 前端基础

| 主题 | 高风险检查点 |
| ---- | ------------ |
| React 原理 | 不要把 Render 和 Commit 混为一谈；不要说 Hooks 可以条件调用；不要把并发渲染理解成多线程并行执行；检查 useEffect、useLayoutEffect、memo、key 的描述是否准确 |
| Vue 原理 | 区分 Vue 2 的 Object.defineProperty 和 Vue 3 的 Proxy；不要把响应式追踪、虚拟 DOM diff、编译优化混成同一机制；检查 ref、reactive、computed、watch 的使用边界 |
| 浏览器机制 | 区分宏任务、微任务、渲染时机和 requestAnimationFrame；不要把 Layout、Paint、Composite 顺序写反；检查 Web API 是否需要安全上下文、权限或用户手势 |
| CSS | 检查盒模型、包含块、层叠上下文、BFC、Flex/Grid 规则是否混用；不要把 z-index 问题都归因于数值大小；检查选择器优先级是否准确 |
| 构建工具 | 区分开发服务器、打包、预构建和 Tree Shaking；不要把 Vite 简化成"不用打包"；检查 ESM、CJS、sideEffects、动态导入的描述是否准确 |
| TypeScript | 区分类型检查和运行时行为；不要把类型断言说成类型转换；检查泛型、条件类型、类型守卫、声明文件是否有运行时误解 |

### AI Agent

| 主题 | 高风险检查点 |
| ---- | ------------ |
| Agent 定义 | 不要把 Agent 简化成一次 function calling；也不要把所有带工具调用的聊天都称为完整 Agent。检查是否包含目标、状态、工具、循环和停止条件 |
| Agentic Loop | 区分推理、工具调用、结果回注和下一步决策；不要写成模型真的直接执行了工具；检查错误处理、重试和终止条件是否缺失 |
| 上下文管理 | 不要把上下文窗口等同于长期记忆；检查压缩、摘要、检索、重注入是否被混为一谈；注意 token 窗口不是可无限依赖的存储 |
| 提示词工程 | 区分系统提示词、用户提示词和补充材料的职责；检查外部内容的信任边界；不要把 JSON 格式约束等同于 schema 或业务校验；区分应用结果缓存和模型服务的上下文缓存 |
| 工具系统 | 区分工具 schema、调用权限、执行环境和结果返回；检查工具是否有副作用、权限控制、幂等性和审计需求 |
| 权限模型 | 检查 allow、deny、ask 等权限描述是否和具体系统一致；不要默认所有工具都能静默执行；涉及文件、网络、命令执行时要说明边界 |
| LLM 原理 | 不要把 Transformer、注意力机制、上下文窗口、RAG、微调混成一个概念；检查 token、embedding、temperature、幻觉等描述是否准确 |
| 模型能力 | 涉及最新模型、价格、上下文长度、工具能力和多模态能力时必须谨慎。无法验证时标为"疑似" |

### 后端/全栈

| 主题 | 高风险检查点 |
| ---- | ------------ |
| Node.js | 区分事件循环、异步 I/O、线程池、Worker Threads 和 Cluster；不要把单线程理解成没有并发；检查 Stream 背压、错误处理和资源释放 |
| 数据库 | 检查索引是否真的能命中查询；区分事务隔离级别、锁、MVCC 和一致性；不要把"加索引"写成万能优化 |
| 缓存 | 区分缓存穿透、击穿、雪崩和一致性问题；检查过期策略、失效策略、热点 key、缓存旁路和双写一致性 |
| 消息队列 | 区分 at-most-once、at-least-once、exactly-once 的语义；检查确认机制、重试、死信队列、顺序性和幂等性 |
| 微服务 | 检查服务发现、熔断、限流、重试、超时是否配套；不要把拆服务直接等同于提升稳定性；分布式事务要说明 Saga、TCC 等适用边界 |
| Docker/K8s | 区分镜像、容器、Pod、Deployment、Service、Ingress；不要把容器当虚拟机；检查资源限制、健康检查、滚动更新和配置管理 |
| API 设计 | 检查 REST、GraphQL、gRPC 的适用场景；不要把 RESTful 等同于任意 HTTP JSON；检查版本控制、错误码、幂等性、鉴权和限流 |

### 计算机基础

| 主题 | 高风险检查点 |
| ---- | ------------ |
| 设计模式 | 不要为了套模式而改写问题；检查模式意图、适用场景和代价是否说清楚；区分策略、状态、模板方法、装饰器和代理 |
| 数据结构 | 检查时间复杂度、空间复杂度和操作前提；不要忽略哈希冲突、树平衡、堆性质、图的有向/无向和权重条件 |
| 算法 | 检查边界条件、复杂度、稳定性和最优子结构；不要把贪心、动态规划、回溯、分治混用；示例代码应覆盖讲解所需的关键边界，省略部分要说明简化前提 |
| 网络协议 | 区分 HTTP/1.1、HTTP/2、HTTP/3、TCP、UDP、TLS、WebSocket 的层次；不要把 HTTPS 简化成"加密的 HTTP"而忽略证书和握手 |
| 操作系统 | 区分进程、线程、协程、并发、并行；检查虚拟内存、文件系统、锁、死锁和调度描述是否准确 |

## 常见误判

- 简化表达不等于错误。面向入门读者的类比可以保留，但需要避免把类比写成机制本身。
- 作者观点不同不等于技术错误。只有事实、因果、边界或术语明显不准确时才作为技术问题处理。
- 老版本经验不一定适用于当前版本。遇到版本敏感内容，补充版本前提或标为疑似。
- 最佳实践不是固定答案。不同规模、团队、性能目标和维护成本会导致合理选择不同。
- 代码能运行不代表描述准确；描述准确也不代表代码覆盖了边界。代码和文字要分别检查。
