# 微信小程序文章设计

## 背景

`apps/docs/experiences/浏览器原理/微信小程序.md` 目前只有 frontmatter（`createdAt`、`draft: true`、`order: 2`），正文待写。

`experiences/浏览器原理/` 目录下已有《浏览器渲染机制》，覆盖了浏览器侧的完整渲染链路。补充一篇《微信小程序》后，读者可以把“小程序里发生了什么”与“浏览器里发生了什么”对照起来看。同一目录下其它文章（如《Vue 渲染机制》《Vue 服务端渲染》）已经形成了稳定的写法，本文沿用同一风格。

## 目标

- 写一篇面向“有 Web 经验的前端工程师”的微信小程序原理文章。
- 文章以 6 节主线展开：`运行环境 -> 双线程模型 -> 小程序启动 -> setData 性能 -> 工程实践 -> 性能优化`。
- 文章只讲微信小程序，不展开支付宝/抖音/百度等多端实现。
- 文章以原理为主，代码示例为辅。
- 篇幅与目录同级文章相当（约 18-25KB）。
- 文章处于 `draft: true` 状态，写完由用户审阅后再去掉 draft。

## 非目标

- 不写小程序开发入门（如 WXML 语法速成、Page 生命周期一览）。
- 不写跨端框架（Taro、uni-app、kbone、Remax）的内部实现原理，只在“工程实践”里做一句话级别的横向参考。
- 不展开 TDesign / Vant Weapp 等组件库的使用方法。
- 不展开小程序服务端（云开发、微信云托管）的实现。
- 不展开 `wx.*` 全量 API 文档。
- 不复述微信官方文档中已经讲清的概念定义，只引用结论与边界。
- 不写和 Web 渲染的完整对比章节。运行环境里给一段“关键差异速查”，不展开。
- 不展开小程序审核、运营、商业化的内容。

## 受众与深度

- 读者画像：熟悉浏览器渲染、JS 引擎、React/Vue 渲染机制的前端工程师。
- 深度：原理级别。出现 API 时给“为什么要这样用”，不给完整参数表。
- 读者不需要：浏览器多进程模型、事件循环、模块化、闭包等基础概念解释。
- 读者需要：与 Web 经验的差异点（不必明说，但内容要服务这一点）。

## 写作风格约束

- 沿用目录中同级文章的写法：长文中文技术文章、大段叙述 + 代码块 + d2 流程图。
- 每节末尾用“容易慢在这里 + 常见优化”的固定结构收口（运行时、性能、setData 等小节）。
- 流程图用 ` ```text ` 文本链路，架构/对比图用 ` ```d2 `。d2 全局渲染参数（class 配色、容器、节点尺寸）由 `apps/docs/rspress.config.ts` 的 `d2PreRenderOptions` 统一管理，不在单篇文章里重复声明。
- d2 节点命名采用仓库 `d2PreRenderOptions` 已定义的语义类（`group`、`fail`、`ok`、`decision`）。需要时再用 `width` / `height` 控制节点尺寸。
- 代码块按 AGENTS.md 规则：函数/类型/类使用 `/** ... */`，函数体内部使用 `//`。
- 代码示例尽量短，每段不超过 15 行，能用伪代码就避免出现需要解释大量上下文才能看懂的真实代码。
- 标题和小节标题避免“先看 xx / 一文看懂 xx / 把 xx 搞清楚”之类的口语化、营销化表达。

### 第 1 节：运行环境

覆盖点：

- 微信客户端作为小程序的宿主：客户端原生壳 + JSCore/V8（逻辑层）+ WebView/原生渲染（渲染层）+ 自定义组件原生渲染。
- 运行环境与浏览器环境的区别：宿主进程由微信提供，JS 引擎、渲染线程、WebView 都不属于用户控制。
- 小程序技术栈构成：客户端原生壳承载逻辑层与渲染层之间的桥；逻辑层执行 JS；渲染层负责 WXML/WXSS 与原生组件。
- 基础库（`wx`）与用户代码的关系：基础库由微信发布、随客户端内置或独立下载；用户代码运行在 JSCore/V8 中。
- 客户端版本、基础库版本、用户代码版本：API 兼容矩阵；`wx.canIUse` 的意义。
- 为什么采用双线程模型（设计动机）：
  - 安全隔离：用户的 JS 不能直接操作真实 DOM。
  - 可控渲染：渲染由客户端原生层处理，跨端表现一致。
  - 防止主线程卡顿：逻辑层出错不会让渲染层跟着卡死。
  - 能力收口：所有 `wx.*` API 走原生桥，便于权限控制与合规审计。
- 小程序运行环境的能力边界：没有 DOM、没有 `window`，但有 WXML/WXSS/JS、自定义组件、原生组件、`wx` API、Worker、npm。

讲法：

- 用“小程序运行环境 = 客户端壳 + 逻辑层 + 渲染层 + 基础库”四件套介绍。
- 解释基础库、客户端、用户代码的版本关系，引出 `wx.canIUse`。
- 在讲完四件套后，先用一段讲清楚双线程的设计动机，为第 2 节做铺垫。
- 用一段“与 Web 的关键差异速查”收口（不展开成对比章节）：
  - 没有 `window/document`，但有 `wx` 全局；
  - JS 引擎是 JSCore（iOS）/ V8（Android）；
  - WXML 模板编译、WXSS 样式隔离、原生组件由客户端渲染；
  - 没有 Cookie，用 Storage；
  - 没有跨域，没有 `<iframe>`；
  - 渲染由原生层调度，不走浏览器主线程的 render pipeline。
- 容易慢在这里 + 常见优化：基础库版本过旧、API 兼容判断缺失、自带 `Promise` polyfill 缺失等。

### 第 2 节：双线程模型

覆盖点：

- 逻辑层（AppService / JSCore）：跑用户的 JS 代码（`app.js`、页面 `js`、自定义组件 `js`）、`wx` API 调用、事件回调处理、Worker。
- 渲染层（View / WebView）：跑 WXML 编译后的模板、WXSS 解析、原生组件渲染、Exparser 组件树。
- 客户端原生层（Native）：两个线程之间的桥、`wx` API 的实现、自定义组件原生容器、网络请求、媒体、文件、定位等系统能力。
- 通信链路：
  - 逻辑层 -> 渲染层：`setData`、事件总线。底层用 `evaluateJavascript` / JSI 把数据传到 WebView。
  - 渲染层 -> 逻辑层：用户事件（`bindtap`、自定义事件）、生命周期事件、滚动/手势回调。
  - 逻辑层 -> Native：`wx.*` API 调用。
  - Native -> 逻辑层：异步回调（`success` / `fail` / `complete`）。
- 关键概念：
  - Exparser：小程序自研组件框架，运行在原生层，不是 React/Vue 那一类 vdom diff 思路。
  - 虚拟 DOM 在小程序里的位置：渲染层有 vdom，逻辑层只有数据；`setData` 是一次“数据快照传输 + 渲染层 vdom diff + 真实组件树 patch”。
  - JSBridge / JSI：跨线程通信通道，`setData` 走的是这条路径，所以会序列化、有耗时。
- 双线程的代价：所有跨线程调用都涉及序列化、跨线程消息、JSBridge 调度。

讲法：

- 用一张 d2 图把客户端壳、逻辑层、渲染层画出来，标出三条通信路径。
- 先讲逻辑层和渲染层各自负责什么，再讲通信。
- 通信部分用一段代码 + 文字解释 `setData` 在这条链路上发生了什么：`Page` 调用 `setData` -> 基础库序列化 -> 跨线程消息 -> 渲染层收到 -> 触发 Exparser patch -> 通知原生层更新组件。
- 单独点出“逻辑层没有 vdom，只有数据”，这是后面 setData 性能那一节的基础。
- 容易慢在这里 + 常见优化：跨线程消息的序列化、消息频率、消息体积、Exparser 复杂 diff。

### 第 3 节：小程序启动

覆盖点：

- 启动入口：用户点击触发 -> 客户端拉起小程序 -> 准备运行环境。
- 资源准备：客户端读取本地小程序包、校验版本、基础库匹配、用户态信息（`scene`、`path`、`query`）。
- 逻辑层初始化：注入 `wx` 基础库 + 注入用户 `app.js`，执行 `App({ onLaunch, onShow, onHide })` 生命周期，`onLaunch` 内可发起首屏数据请求。
- 渲染层初始化：创建首屏页面 WebView、加载 WXML 编译产物 / WXSS / 自定义组件模板 / 原生组件、执行 `Page({ onLoad, onShow, onReady })`、触发首屏 `setData`。
- 首屏渲染流程：渲染层 Exparser 解析 WXML -> 生成 vdom -> 渲染组件树 -> 通知原生层绘制；逻辑层 `onLoad` -> 业务请求 -> `setData` -> 渲染层 patch。
- 冷启动 / 热启动 / 前后台切换：冷启动完全新开；热启动逻辑层保留、渲染层可能保留也可能重建（页面数量过多时会回收）；前后台 `onHide` / `onShow` 触发，渲染层不一定销毁。
- 启动耗时拆分：资源加载、JS 注入、`onLaunch` 执行、首屏 `setData` 落地、首帧绘制，每一段都可用 `wx.getPerformance` 单独打点。

讲法：

- 用一张 d2 图把启动主线画出来。
- 用 `text` 块给出启动链路。
- 讲清楚冷启动 / 热启动的差异，引出“保留页面数”设计存在的原因。
- 给出 `wx.getPerformance` 的 10 行内示例。
- 容易慢在这里 + 常见优化：`onLaunch` 同步阻塞、首屏依赖非首屏资源、首屏 `setData` 过大、分包未使用预下载、独立分包未使用。

### 第 4 节：setData 性能

覆盖点：

- `setData` 的真实工作流（在第 2 节的链路上展开）：
  1. `Page` 调用 `setData(data)`；
  2. 基础库在逻辑层把 `data` 与上一次数据合并；
  3. 序列化 + 跨线程消息（JSBridge / JSI）；
  4. 渲染层接收后写入渲染层数据池；
  5. Exparser 触发 vdom diff，得到最小 patch；
  6. 通知原生层更新组件树。
- 性能瓶颈分布：
  - 逻辑层序列化：JSON 体积、对象深度、循环引用。
  - 跨线程消息：体积 × 频率。频繁小 `setData` 比一次大 `setData` 更糟，消息调度有固定开销。
  - 渲染层 diff：组件树深度、被影响的组件数量。
  - 原生层更新：实际绘制成本。
- 数据结构对性能的影响：
  - 路径写法：`setData({ 'a.b.c': 1 })` 比 `setData({ a: { b: { c: 1 } } })` 更轻；
  - 避免把整张大列表一次性 `setData`；
  - 避免把 `this.data` 整个再 `setData` 回去。
- 行为约束：单次 `setData` 数据官方建议 ≤ 1MB（避免超限报错）；一次设置过多的 `setData` 会被节流；`setData` 回调语义是“数据已到达渲染层”，不是“已绘制到屏幕”。
- 设计原则：能合并就合并；能不传就不传；能不在主流程就不在主流程（高频更新用 `wxs` 响应式、用 `requestAnimationFrame` 切帧）。

讲法：

- 开头给一张 d2 图，把 setData 的 6 步画出来，把耗时大头标在“序列化 + 跨线程消息”两段。
- 给一段示例代码：循环里多次 `setData` vs 合并成一次 `setData`。
- 给一段示例代码：路径写法 vs 整体写法。
- 单独点出 `setData` 回调的语义差异。
- 容易慢在这里 + 常见优化：把整张大列表/整棵树 `setData`、循环里逐项 `setData`、滚动/动画中持续 `setData`、误用回调判断渲染完成。

- 构建与发布：开发者工具构建、本地预览、上传、审核、灰度、回滚；`project.config.json`、`sitemap.json`、`miniprogramRoot`；npm 支持、`miniprogram_npm`、Vite/Rollup 自定义构建的接入点。
- 跨端开发：原生 vs Taro vs uni-app vs Remax vs kbone 的取舍点（仅横向参考，篇幅克制）；跨端框架在小程序侧最终还是要跑回双线程模型。

- 调试工具：开发者工具的 Network、Storage、WXML、真机调试、Trace；真机 vConsole / `wx.setEnableDebug` 的取舍。

讲法：

- 容易慢在这里 + 常见优化：主包超限未拆、预下载规则粒度过粗、上报未做采样、错误只打 log 不上报。

### 第 6 节：性能优化

覆盖点：

- 启动性能：主包体积、分包预下载、独立分包；`onLaunch` 异步化；首屏不依赖非首屏资源；用 `wx.getPerformance` 打点。
- 首屏渲染：首屏数据预取（`onLaunch` 内发起，`onLoad` 之前到）；首屏 `setData` 体积控制；骨架屏、占位图、占位高度，避免布局抖动。
- 运行时性能：长列表使用 `recycle-view`、可滚动容器复用、避免 `wx:for` 嵌套；图片合适尺寸、`lazy-load`、WebP/AVIF、CDN；动画用 CSS / `transform` / `opacity`；高频事件 `bindscroll` 节流、`IntersectionObserver`、`wxs` 响应式。
- `setData` 专项（用一段清单总结第 4 节所有 setData 优化点，标注“详见第 4 节”，不重复展开）。
- 内存与崩溃：大数据（图片、长列表、缓存）及时释放；`setInterval` / `setTimeout` 在 `onUnload` 清理；全局状态收口。
- 性能诊断：`wx.getPerformance`、Trace 工具、vConsole、`setEnableDebug`；配合 `audits` 形成“开发期自检 + 线上监控 + 实验室 Trace”三位一体。
- 体验指标：首屏渲染时间（FP/FCP 替代）、可交互时间（TTI 替代）、滑动帧率、长任务数。

讲法：

- 每一维下用“容易慢在这里 + 常见优化”的固定结构。

- 收尾用一段话把整篇 6 节串起来。

- 沿用 `commit` skill 提交规范：写完由用户确认后用 commit skill 提交，commit message 遵循 Conventional Commits。

## 验证方式

- 文章写完后，先在文件内部自检：
  - frontmatter 格式正确（`createdAt`、`draft`、`order`）。
  - 6 节标题顺序与本设计一致。
  - 每个“容易慢在这里 / 常见优化”小节都存在。
  - d2 图的 class 只使用 `group` / `fail` / `ok` / `decision`。
  - 没有为引出正确说法构造的反面 API。
  - 没有营销化、夸张化的小节标题。
- 流程：文章写完后先由用户审阅内容；用户确认后再由用户决定是否走 commit skill 提交。
- `draft: true` 在用户审阅通过前不主动去除；是否去掉由用户决定。

## 风险与取舍

- 文章主题（双线程模型、`setData` 性能）容易写成“微信官方文档的扩写”。本设计在“写作风格约束”和“非目标”里已经明确不写开发入门、不复述官方概念，但仍可能滑向这个方向，需要在写完后做一次自检。
- d2 图越多，构建越慢。本设计把 d2 图控制在 6 张以内，避免对文档构建造成明显影响。
- 不写完整的“与 Web 渲染对比”章节是有意取舍：这类内容已经分散在各节中作为速查表，再加一章会显得凑数。
- 不展开跨端框架的内部实现是有意取舍：跨端框架不是小程序本身，展开会偏离主题；用一段话和一个对比表足够。
- 文章保持 `draft: true` 状态直到用户审阅通过；不要自动改 draft。
